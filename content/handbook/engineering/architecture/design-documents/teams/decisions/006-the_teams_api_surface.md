## 背景 {#context}

Teams には API が必要であり、GitLab のどちらのプロトコルにも提供すべき理由があります。GraphQL は新しいインターフェースを構築する場所です。REST にはメンバー API があり、大規模な管理のニーズを持つ顧客は、それを使って多くの操作を自動化しています。エンタープライズ向けの機能にとって、スクリプトによる付与管理は後であると便利なものではなく、初期から求められるものです。各プロトコルで何を扱えるかは作業量の問題ではなく、その線引きはプロトコルの境界と一致しません。

**きめ細かい権限を持つトークンには Organization の境界がありません。** エンドポイントの認可では、権限と境界の型を宣言します。現在使われている境界の型は project、group、instance、user です。organization は存在しません。これは、設計案が外部依存として記録しているのと同じ知見です。このため、インターフェースはスコープによって分かれます。

- **付与はグループまたはプロジェクトに存在する**ため、group または project の境界を宣言でき、今すぐ提供できます
- **Team と名簿の管理のスコープは Organization** であるため、実態に合う境界を宣言できません。`POST /organizations` は instance の境界でこれに対処していますが、そうすると、1 つの Organization 内で Teams を管理する許可を持つトークンのスコープを、インスタンス全体にする必要があります。Organization の作成には釣り合うと言えるかもしれませんが、日常的な名簿の編集には釣り合いません

2 つ目の問いは、REST で付与をどう表現するかです。[ADR-004](004-team_membership_is_an_ordinary_membership.md)では Team を新しい種類のメンバーとしているため、`POST /:id/members` に Team パラメーターを追加する案が考えられます。しかし、実際には成り立ちません。1 回の呼び出しで名簿のユーザーごとにメンバー行を作成するため、返すべき単一のメンバーがなく、API の中でも自動化に最も多用されるエンドポイントの契約を変えてしまうからです。

## 決定 {#decision}

**Teams は GraphQL と REST の両方で提供し、両者の境界はプロトコルではなくスコープで決めます。** group または project の境界を宣言できるものは、すべて両方に存在します。Organization をスコープとする管理は、その境界ができるまで GraphQL のみとします。

### GraphQL

- **Organization のインターフェース** — Organization の Teams とそのメンバーを取得するクエリ、および Team の作成、更新、削除とメンバーの追加、削除を行うミューテーション
- **名前空間のインターフェース** — 元の名前空間、付与者、付与日時、有効期限を含め、グループまたはプロジェクトの Team への付与を取得するクエリ、および割り当て、ロールの変更、取り消しを行うミューテーション
- Team 由来のメンバー行は、members コネクションに混在させず、専用のリレーションで公開します

### REST

付与はグループとプロジェクトのサブリソースとし、`POST /groups/:id/share` の形にならいます。ただし、Team への付与は共有ではないため、その名前は借りません。

| メソッドとパス | 目的 |
| --- | --- |
| `GET /groups/:id/teams` | このグループに直接ロールを付与された Teams |
| `GET /groups/:id/teams/all` | 祖先のグループから継承した付与を含めます |
| `GET /groups/:id/teams/:team_id` | 1 件の付与 |
| `POST /groups/:id/teams` | Team にロールを付与します。`team_id`、`access_level`、任意で `expires_at` と `member_role_id` を受け取ります |
| `PUT /groups/:id/teams/:team_id` | ロールまたは有効期限を変更します |
| `DELETE /groups/:id/teams/:team_id` | 取り消します |

`/projects/:id/teams` の下にも同じ 6 つを設けます。直接かすべてかの区別は、新しいパラメーターを作らず、`/members` と `/members/all` にならいます。同じ区別であり、呼び出し側がすでに理解しているためです。

**メンバーエンドポイントでは、Team 由来のメンバー行を含めるかどうかをオプトインにします。** `GET /:id/members` と `GET /:id/members/all` に、それらを含めるパラメーターを追加します。デフォルトの応答ではなくリレーションを通じて公開する GraphQL の選択と揃えます。この種の行には由来となる Team を含めます。そうしなければ、応答を解釈できません。

**どちらのインターフェースでも、権限はメンバーの権限を使い**、Teams 独自の並行した権限体系は作りません。ADR-004 は Team への付与にユーザーへの付与と同じ権限を使うと定めているため、これらのエンドポイントではメンバーエンドポイントと同じ権限を宣言します。メンバーを管理できるトークンは Team への付与も管理できます。これは見落としではなく、意図した結果です。

REST には、[ADR-007](007-parity_before_migration.md)の同等性確保の作業で、既存のエンドポイントがグループと並んで Team も受け入れる必要がある箇所すべてに、Team 対応を追加します。保護された ref、保護環境、承認ルールなどです。これらのエンドポイントはすでに REST であり、その契約の変更は省略できません。

### 先送りするものとその理由 {#deferred-and-why}

Team の作成、更新、削除、および名簿の管理は、すべて `/organizations/:id/teams` の下に置きます。形は争点ではありません。障害は、きめ細かい権限を持つトークンのスコープを Organization に限定できず、instance の境界で提供すると、操作に必要な範囲を大きく超える権限を与えてしまうことです。これは未計画ではなく、明示した依存関係によってブロックされているものとして追跡します。

## 影響 {#consequences}

### 利点 {#positive}

- 自動化に最も重要な操作を、自動化で使うプロトコルで利用できます。付与と取り消しは繰り返し行う管理操作であり、Team の作成はそれに比べてまれです
- 付与エンドポイントは実態に合うトークン境界を持つため、トークンのスコープを管理対象のグループやプロジェクトに限定できます
- 既存の契約は変わりません。メンバーエンドポイントには任意のパラメーターと任意のフィールドが追加され、現在の応答内の要素は何も移動しません
- GraphQL ではフィールドレベルの権限を追加作業なしに公開できるため、UI は認可のために再度通信せず、ユーザーが使えない操作部品を非表示にできます
- 先送りする半分には、すでにこの取り組みの外部依存となっている明確な障害があるため、期限を定めずに放置するのではなく、予定を立てられます

### 欠点 {#negative}

- **対応範囲に偏りがあり、その偏りは API から見えません。** Team を用意してからアクセスを付与するスクリプトには、両方のインターフェースが必要です。`/organizations` には `teams` サブリソースがない理由を説明するものがないため、制約ではなく実装漏れに見えます。その説明をドキュメントが担う必要があります
- 同じ状態に対する 2 つ目の書き込み経路ができるため、認可と具体化の処理は付与サービスだけに置かなければなりません。そうしないと REST と GraphQL が乖離します
- メンバーの権限を再利用すると、メンバー管理の権限変更によって、Teams への付与を行える人も暗黙に変わります。これは ADR-004 に照らして正しい動作であり、明記すべき結び付きです
- まだ固まりきっていないデータモデル上で、設計、レビュー、文書化、非推奨化の対象となるインターフェースが 2 つになります
