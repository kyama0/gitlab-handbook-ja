## ステータス {#status}

**提案中。**

## 背景 {#context}

Artifact Registry は、20 人以上のエンジニアが開発する 15 以上のパッケージフォーマット（OCI、Maven、npm、PyPI、NuGet など）をサポートします。AI エージェントがフォーマットの実装を書き、エンジニアは仕様の作成、アーキテクチャの方向付け、出力のレビューを行います。コードベースには、フォーマット数に応じて拡張でき、新しいコントリビューターが素早く参加でき、インシデント中にエンジニアがツールなしで関連コードを見つけられる構造が必要です。コードレビューだけに頼らず、アーキテクチャの境界を機械的に強制する必要があります。

[ADR-006](006_technology_stack.md)では、実装言語を Go としています。フォーマットの拡張メカニズム（Service Provider Interface と Capability Interfaces を備えた Module Pattern）は対象外です。この ADR は、プロジェクトのレイアウトと、それを強制するツールを決定します。

## 決定 {#decision}

機能ごとにパッケージを編成する `cmd/` + `internal/` プロジェクトレイアウトを使用します。この規約は、Container Registry を含む本番の Go プロジェクトで広く採用されており、Go 自身のツールチェーンに根ざしています。`internal/` には[コンパイラが強制する可視性](https://go.dev/doc/go1.4#internalpackages)があり、`cmd/` は慣例的なエントリーポイントのディレクトリです。

- 単一のエントリーポイントを `cmd/` の下に置きます。ここがコンポジションルートであり、フォーマットパッケージ、共有インフラストラクチャ、ルーターを結び付けます。
- すべてのアプリケーションコードを `internal/` の下に置きます。
- 各パッケージフォーマットを、`internal/format/<name>/` の下の独自のパッケージに置きます。
- 横断的なインフラストラクチャ（ストレージ、認証、名前空間解決、データアクセス、バックグラウンドジョブなど）を、`internal/` 直下の共有パッケージに置きます。

### 境界 {#boundaries}

4 つのルールによって構造を維持します。いずれもレビューではなく機械的にチェックします。

1. **モジュール外のコードは、そのモジュールの `internal/` パッケージをインポートせず**、パッケージ間で循環インポートを行うこともできません。Go コンパイラが両方を強制します。
1. **フォーマットパッケージは、別のフォーマットパッケージを決してインポートしません。** フォーマットをまたぐ動作は、コンポジションルートで結び付けます。depguard の `format-isolation` ルールが CI でこれを強制します。
1. **フォーマットパッケージは、SQL ドライバーを直接使用しません。** SQL は `internal/datastore/` に置き、フォーマットは datastore のインターフェースを通じてアクセスします。depguard の `no-direct-db` ルールが CI でこれを強制します。
1. **共有インフラストラクチャは、フォーマットパッケージを決してインポートしません。** 共有パッケージが必要なインターフェースを定義し、各フォーマットがそれを実装し、コンポジションルートが実装を注入します。依存関係は `cmd` → フォーマット → インフラストラクチャの方向に流れ、逆方向には流れません。そのため、共有コードはフォーマットに依存せず、フォーマット数に応じてインポートが増えることもありません。depguard の `no-reverse-dependency` ルールが CI でこれを強制します。唯一の例外は `internal/authz` で、独自の depguard ルールの下で、各フォーマットのルート文法を定義するリーフ（`internal/format/<name>/<name>route`）をインポートします。各リーフは `internal/format` 内から何もインポートしません。

depguard のルールはパスを汎用的に照合する（`internal/format/` 下のすべてのファイルに適用する）ため、フォーマットを追加する際に必要なのは、ルート文法のリーフに関する depguard のエントリ 2 つだけです。1 つは `internal/authz` によるインポートを許可し、もう 1 つはリーフの状態を維持します。単一のフォーマットのバックグラウンド処理も同じルールに従います。ロジックはフォーマットパッケージに置き、共有のスケジューリング基盤は、実際のフォーマットによって必要なパターンが明らかになってから構築します。

### 固定するパス {#locked-paths}

この ADR は、強制ルールと、それが参照するパスを固定します。対象は `cmd/`、`internal/`、`internal/format/<name>/`、`internal/datastore/`、および逆依存ルールが指定する共有パッケージです。固定したパスの名前を変更するには、depguard の設定も同時に更新する必要があります。

それ以外はすべて出発点です。フォーマットパッケージ内のファイルと命名方法、共有パッケージ内のファイル構成、その他の共有パッケージの名前が該当します。フォーマットパッケージは、デフォルトではフラットです。分離ルールがパスのプレフィックスで照合するため、フォーマットが自身のサブパッケージをインポートする場合、そのルールに許可エントリが必要であり、そのエントリによってすべてのフォーマットがそのサブパッケージにアクセスできるようになります。

**レイアウトは出発点であり、契約ではありません。** レイアウトに摩擦が生じる場合（たとえば、テストによってパッケージ境界の見直しが必要になる場合や、フォーマットの構造がデフォルトのファイル分割に適さない場合）、期待される対応は回避策を取ることではなく、レイアウトの変更を提案することです。特に AI エージェントは、本来の配置先ではないパッケージにコードを無理に押し込むのではなく、より適切な構成を提示するべきです。レイアウトの変更は、機能やバグ修正の作業にまとめず、独立した MR として取り込み、トレードオフ自体の妥当性をレビューします。これらのパス内のレイアウトを改訂しても、この ADR の改訂は不要です。

### 比較分析 {#comparative-analysis}

各パターンについて、5 つのフォーマットを備えたデモを作成しました（参考資料を参照）。3 つの結果が選択の決め手になりました。

- **フォーマットごとのコストは、その複雑さに応じて変わります。** Go Native はフォーマットあたり 2-6 ファイルを必要とし、代替案は単純なフォーマットを含め、すべてのフォーマットに 10-13 ファイルを課します。1 つのフラットなパッケージに少数のファイルを作る方が、フォーマットを追加する AI エージェントにとっても低コストです。DDD のデモでは、エージェントが作業をやり直す回数が最も多く、ファイル数やディレクトリをまたぐファイル作成との相関が見られました。
- **フォーマットが増えても、強制のための設定はほとんど増えません。** 新しいフォーマットを追加する際に必要なのは、そのルート文法のリーフに関する depguard のエントリ 2 つだけです。許可エントリが欠けていれば lint は失敗しますが、リーフのルールが欠けていても失敗しないため、レビューで検出する必要があります。どちらの代替案でも、フォーマットごとに人間が go-arch-lint の設定を更新する必要があり、その更新なしに追加されたフォーマットは、気付かれないままチェック対象外になります。
- **契約の境界面は維持されました。** 3 つのデモすべてで、フォーマットを追加しても共有インターフェースは変更されませんでした。そのため、アーキテクチャの選択によって安定した契約を犠牲にすることはありません。

ハンドラーのサイズは、アーキテクチャではなくフォーマットの複雑さによって変わりました。Go Native はフォーマットのハンドラーロジックを同じ場所に置くため、ハンドラーファイルが最も大きくなります（デモでは OCI が 797 行、npm が 916 行で、本番では 1,200 行から 1,800 行超になると予測されます）。

## 代替案 {#alternatives}

### Clean Architecture（レイヤー優先） {#clean-architecture-layer-first}

Clean Architecture は、コードを同心円状のレイヤー（domain、usecase、adapter）に編成し、go-arch-lint がレイヤー間のインポート方向を強制します。デモでは各フォーマットに 10-13 ファイルが必要で、コンポジションルートはフォーマットごとに約 30 行増加します。

デモによって、強制の仕組みの不足が明らかになりました。すべてのフォーマットで、管理 API のエンドポイントがサービス構造体を直接参照し、usecase レイヤーを迂回していました。go-arch-lint がチェックするのはインポートグラフであり、呼び出しグラフではありません。正しくインポートしたパッケージの誤ったメソッドへの呼び出しを検出できる、本番で使用されている Go のリンターはありません。規模が大きくなると、usecase レイヤーは実際のロジックとパススルーのスタブが混在する状態に劣化します。横断的な変更も、フォーマットごとに 1 ファイルではなく、2 ファイル（usecase と adapter）に及びます。

**却下した理由：** usecase レイヤーは約束する分離を提供せずにオーバーヘッドを増やし、現在の Go ツールではこの不足を解消できないためです。

### DDD + Hexagonal Architecture（境界づけられたコンテキスト優先） {#ddd--hexagonal-architecture-bounded-context-first}

DDD + Hexagonal は、フォーマットごとに 1 つの境界づけられたコンテキストにコードを編成し、それぞれにドメインエンティティ、アプリケーションサービス、ポート、アダプターを置きます。go-arch-lint が、コンテキスト間とレイヤー間の境界を強制します。デモではすべてのフォーマットに、複雑さにかかわらず正確に 13 ファイルが必要でした。

デモによって、重複を強いられることが明らかになりました。アーキテクチャが、フォーマットのアダプターから共有アダプターをインポートすることを禁じているため、すべてのフォーマットのアダプターが同じ認証情報の抽出を再実装しました。アーキテクチャの枠内に解決策はありません。また、DDD の戦術パターン（集約、値オブジェクト、リポジトリ）は Go の型システムにうまく対応しないため、集約の不変条件は規律に依存し、学習の難しさは 3 案の中で最も高くなります。

**却下した理由：** 固定的な 13 ファイルの構造は、単純なフォーマットにも複雑なフォーマットと同じ負担を課し、アーキテクチャで解消できない重複を強いるためです。

## 影響 {#consequences}

### 利点 {#positive}

- **コンパイラが強制する分離：** `internal/` の可視性に設定は不要で、検出漏れもありません。
- **複雑さに比例するフォーマットごとのコスト：** 単純なフォーマットは、複雑なフォーマットより低コストです。
- **最小限の強制設定：** 新しいフォーマットを追加する際に必要なのは、そのルート文法のリーフに関する depguard のエントリ 2 つだけです。
- **横断的な変更の増幅が小さいこと：** 横断的な変更は、フォーマットごとに 1 ファイルに及びます。

### 欠点 {#negative}

- **フォーマットパッケージ内の内部構造は規定しません。** フォーマットパッケージごとにファイルの構成が異なる可能性があります。これは一貫性の問題であり、正しさの問題ではありません。コンパイラと depguard は、引き続き境界を越えるすべてのインポートを防ぎます。一貫性は、リファレンス実装、コントリビューションガイド、適合性テスト（各フォーマットが必要なインターフェースを実装し、ルートを登録し、動作に関する契約を満たすことのテスト）によって保ちます。
- **大きなハンドラーファイルは、計画的に分割する必要があります。** 本番規模では、複雑なフォーマットのハンドラーが 1 ファイルに収まらなくなり（Container Registry の本番の manifests ハンドラーは 1,848 行）、中程度のフォーマットもそうなる可能性があります。クライアント API のハンドラーと管理 API のハンドラーを分けるなど、分割は機械的に行い、パッケージ内に留めます。切迫した状況で気付くのではなく、計画しておく必要があります。
- **テストのオーバーヘッドは未計測です。** デモにはテストがありませんでした。しかし、テストは本番コードの大部分を占め（Container Registry のハンドラーのテスト対コード比率は 2.3 倍）、パッケージ境界、インターフェースの配置、ファイルの分割を定期的に変えます。フォーマットが完全なテストスイートを備えると、フォーマットごとのレイアウトが変わる可能性があります。
- **depguard は重複を検出できません。** フォーマットパッケージの内部や相互間で重複するコードは、3 つの候補のいずれでも、引き続きレビューが必要です。
