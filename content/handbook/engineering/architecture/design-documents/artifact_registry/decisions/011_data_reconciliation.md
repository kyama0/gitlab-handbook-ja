## コンテキスト {#context}

コンテンツアドレッサブルストレージ（[ADR-008](008_content_addressable_storage.md)）は、データベース内のレコードとストレージ内のオブジェクトという、2 つの信頼できる情報源を保持します。
これらは次のような場合に食い違うことがあります。

- ストレージへの書き込みとデータベースのコミットの間にクラッシュすると、レコードのないオブジェクトが残ります。
- 移動後の削除に失敗すると、ステージングオブジェクトが残ります。
- オペレーターや別のプロセスがレジストリの外でオブジェクトを変更または削除すると、レコードが存在しないコンテンツや誤ったコンテンツを指します。
- 参照追跡のバグによってアーティファクトがなくなった後も参照が残ると、blob は回収されなくなります。また、参照を早期に削除すると、次のガベージコレクションでデータが失われます。

リモートキャッシュでも同じように不一致が発生します。
コンテンツアドレッサブルストレージは、取得元にかかわらずすべての blob を同じ方法で保存するため、同じ機能で対処できます。

不一致には次の 3 つの機能で対処します。

| 機能 | 動作 |
| --- | --- |
| ガベージコレクション（GC） | 最後の参照がなくなった blob を回収します |
| アップロードパージング | 放棄されたアップロードのステージングオブジェクトとレコードを削除します |
| データ検証 | レコードのないオブジェクト、アーティファクトがなくなった後も残る参照、およびレコードとオブジェクトのその他の不一致を検出し、報告します。他の文書では調整サービスと呼ばれています |

GC が何を回収するかは [ADR-010](010_data_retention.md)で、その方法は [ADR-025](025_garbage_collection.md)で決定します。
この ADR は、各機能の提供時期と、延期した機能を後から提供できるようにスキーマとストレージレイアウトで何を保持すべきかを決定します。
ソフト削除されたアーティファクトを期限切れにすることは、調整ではなく保持の処理です。両方の情報源はデータの状態について一致しており、削除すべきと定めているのはポリシーだけだからです。

## 決定 {#decision}

**GC とアップロードパージングをデータ検証より先に提供します。データ検証は延期しますが、独自の追跡機構なしに後から提供できるよう、スキーマとストレージレイアウトは必要な情報を保持します。**

アップロードパージングは、[GC ジョブ](025_garbage_collection.md#jobs)の 1 つとして実行します。

### 常に満たすべき条件 {#what-must-always-hold}

| # | 制約 | 機械的に検証可能か |
| --- | --- | --- |
| 1 | **GC とアップロードパージングは、データベースから処理対象を見つけます。** ストレージを一覧取得することなくデータベースレコードから候補を選択し、各スイープはインスタンスごとではなく、インスタンス群全体に対して 1 回スケジュールします。 | はい。どちらもストレージを一覧取得せず、実行インスタンス数を増やしてもスイープの実行頻度は増えません |
| 2 | **放棄されたアップロードは、そのレコードから見つけます。** すべてのアップロードセッションはデータベースに有効期限を持つため、アップロードパージングが削除対象を見つけるのに、それ以外の情報は不要です。 | はい。すべてのアップロードセッションレコードに有効期限があり、パージはレコードだけから期限切れのセッションをすべて見つけます |
| 3 | **ストレージキーから対応するレコードを特定できます。** blob キーはネームスペースハッシュとコンテンツハッシュを、ステージングキーはネームスペースハッシュとアップロード ID を保持するため、どちらもデータベースを参照せずに読み戻せます（[ADR-008](008_content_addressable_storage.md)）。blob のハッシュを再計算することで、そのコンテンツを検証します。データ検証は、独自のマッピングなしに、オブジェクトとレコードを双方向に照合します。 | はい。このレイアウトが生成するすべてのキーを解析すると、その生成元のネームスペースハッシュと、コンテンツハッシュまたはアップロード ID に戻せます |
| 4 | **ネームスペースの blob をページごとに読み取れます。** GC とデータ検証はどちらもネームスペースを 1 つずつ処理するため（[ADR-022](022_namespace_decoupling.md)）、スキーマは 1 つのネームスペースの blob をサイズに上限のあるページとして提供します。 | はい。1 つのネームスペースの blob の 1 ページを取得する際に読み取る行数には上限があります |
| 5 | **すべての取得元に 1 つの仕組みを使います。** 各機能は、クライアントがアップロードした blob もリモートキャッシュが取得した blob も同じように扱い、フォーマットごとの派生形を持ちません。 | はい。どの機能も blob の取得元を読み取りません |

### GC を先に提供する理由 {#why-gc-ships-first}

- **GC の後付けは高コストです。** Container Registry は本番で数年間運用した後、何十億ものオブジェクトが存在し、その参照を何も追跡していないシステムに[オンライン GC](https://gitlab.com/gitlab-org/container-registry/-/blob/master/docs/spec/gitlab/online-garbage-collection.md)を追加しました。新しいサービスなら最初から組み込めます。
- **機会は今です。** データ量が少なければ、GC のバグが危険にさらすオブジェクトは少なく、GC と API トラフィックの間でストレージやデータベース接続の競合が少なく、データを手動で調べられます。GC と API の競合状態はどの規模でも存在しますが、その代償はサービスが新しいときに最も小さく、この機会は再び訪れません。
- **孤立した blob は増える一方です。** GC がなければ、何からも参照されていない blob を解放するものがありません。Container Registry は GitLab.com で何十億ものオブジェクトと数十ペタバイトの規模に成長しました（[ADR-003](003_system_requirements.md)、[ADR-002](002_storage_deduplication_scope.md)）。
- **GC は参照追跡を実証します。** 参照の追加、削除、参照が残っていないことの確認、削除という参照ライフサイクル全体を使用する唯一の機能です。早期に実行することで、データ量によってバグの代償が大きくなる前に、スキーマが参照を正しく追跡していることを示せます（[ADR-007](007_database_schema.md)）。

### データ検証を延期できる理由 {#why-data-validation-can-wait}

データ検証は、不一致が発生した後にそれを検出するもので、何も防ぎません。
GC は何からも参照されていない blob を回収し、アップロードパージングは放棄されたアップロードを回収します。
データ検証は、クラッシュや移動後の削除失敗によってレコードなしで残ったオブジェクト、アーティファクトがなくなった後も残る参照、ストレージの破損、レジストリ外で行われた変更、GC やアップロードパージングのバグを検出します。
これらを正しい状態と区別するには本番のベースラインが必要であり、GC を先に実行することでそれが得られます。
制約 3 と 4 により、その間に発生した不一致もデータベースとストレージだけから検出できます。
どちらかが欠けていれば、データ検証に独自の追跡機構が必要になり、より早く提供しなければなりません。

### 導入の進め方 {#adoption-path}

1. GC とアップロードパージングを先に提供します。GC は [ADR-025 の段階](025_garbage_collection.md#adoption)に従って削除を有効にします。
1. データ検証は報告から始めます。検出した各不一致をログとメトリクスに記録し、自動修復は行いません。
1. 修復は後のイテレーションで実施します。

## 検討した代替案 {#alternatives-considered}

### 何もしない：3 つすべてを延期する {#do-nothing-defer-all-three}

不採用です。データのないサービスに GC を組み込む一度きりの機会を恒久的な後付け作業と引き換えにし、実トラフィックで検証されていない参照追跡スキーマを提供し、修正するものがないまま孤立した blob が増えるからです。

### データ検証を GC と同時に提供する {#ship-data-validation-with-gc}

不一致に気付かない期間をなくせます。
不採用です。データ検証には、GC を実行することでしか得られない本番のベースラインが必要であり、GC と異なり一度きりの機会がないため、相応のリスク低減なしにスコープを広げるからです。

### アップロードパージングを延期する {#defer-upload-purging}

放棄されたアップロードによってステージングオブジェクトとセッションレコードが蓄積します。これは衛生上のコストであり、正確性に関するコストではありません。
不採用です。ステージングオブジェクトを参照できるものはないため、パージに確認のための待機期間も、ロック下での再確認も不要です。
GC ジョブをもう 1 つ追加して実行します。

### ストレージの一覧取得から候補を見つける {#find-candidates-by-listing-storage}

ストレージを走査し、各オブジェクトをデータベースと比較します。
不採用です。Container Registry では、データベースで参照を追跡するようスキーマを再構築するまで、ストレージの一覧取得に使うメモリがストレージとともに増え、各インスタンスでのスイープが同じ作業を繰り返していました。
コストは変更量ではなく、ストレージ全体に応じて増えます。

## 帰結 {#consequences}

### ポジティブ {#positive}

1. GC は、データ量が増える前に、実トラフィック下で参照追跡が正しいことを示します。
1. GC の並行性のバグを発見して修正するコストは、データ量が少ないときに最も小さくなります。
1. データ検証を、独自の追跡機構なしに後から提供できます。

### ネガティブ {#negative}

1. データ量が必要とするより前に、GC のスキーマサポートとバックグラウンドジョブを構築します。
1. データ検証を提供するまで、未参照の blob と放棄されたアップロード以外の不一致に気付きません。
1. データ検証を提供するまで、参照されている blob を早期に削除する GC のバグは、クライアントがそのアーティファクトを要求したときにしか見つかりません。データ量の少なさは影響を受けるアーティファクト数を制限しますが、気付かない期間は制限しません。
