## 背景 {#context}

Artifact Registry は、大規模な企業組織と GitLab.com にサービスを提供します。この ADR は、サービスが依存するインフラ機能と、対応するよう設計する規模を記録します。[ADR-006](006_technology_stack.md)で、各機能に使用する技術を選定し、任意または先送りとするものを記録します。

## 決定 {#decision}

Artifact Registry は、任意または先送りと記載した行を除き、以下の機能に依存します。各機能はサービス全体を支えるものです。1 つの形式や機能だけが必要とする能力は、ここではなく、その仕様に記載します。

| 機能 | サービスで必要とする目的 |
| --- | --- |
| バックグラウンドジョブ処理 | 移行、ライフサイクルポリシーの実行、一括操作など、リクエスト内で完了できない作業です。再試行と監視も、この機能に含みます。 |
| リレーショナルデータベース | 永続的なメタデータです。アーティファクト、リポジトリとリポジトリコレクション、アクセス制御ルール、ライフサイクルポリシーの状態、ガベージコレクションがたどる参照を含みます。 |
| ブロブストレージ | [ADR-002](002_storage_deduplication_scope.md)で定めたスコープで重複排除する、コンテンツアドレス可能なアーティファクトデータです。GitLab の統合オブジェクトストレージをサポートします。 |
| コンテンツ配信ネットワーク | 任意であり、デプロイ環境によって異なります（[ADR-006](006_technology_stack.md#4-content-delivery-network-cdn)）。ブロブのダウンロードをエッジでキャッシュし、オリジンの負荷、ダウンロードの遅延、エグレスコストを減らします。 |
| 分析エンジン | 任意であり、MVP の対象外です。なくてもサービスは完全に機能します（[ADR-006](006_technology_stack.md#5-analytics-engine-clickhouse)）。本番データベースとは別に、長期的なイベントレコードを集計し、クエリします。 |
| キャッシュ | 頻繁に読み取るデータ、レート制限とクォータのカウンター、分散ロック、一時的な共有状態です。 |
| イベントバス | 先送りします。MVP では直接 API を呼び出します（[ADR-006](006_technology_stack.md#7-event-bus)）。アーティファクトへのすべての操作についてイベントを公開し、それらのイベントから作業を開始して、他の GitLab コンポーネントと連携します。 |

## パフォーマンス、規模、運用上の制約 {#performance-scale-and-operational-constraints}

### 想定する利用特性 {#expected-usage-characteristics}

- 読み取りが多く、アップロード、タグの更新、ライフサイクルポリシーの操作による継続的な書き込みがあります。
- 偏りが強く、アクセスの集中するリポジトリやアーティファクトは一部に限られ、めったに読み取られないものが多数あります。
- デプロイの集中や大規模なパイプラインなどの CI/CD ワークロードによって、急増が発生します。
- 大規模な組織は、数千のリポジトリと数百万のアーティファクトを保持します。

### パフォーマンスと信頼性の主な目標 {#key-performance-and-reliability-goals}

- 企業のワークロードでも操作の応答性を維持し、負荷が高まったときは広範囲に障害を起こさず、予測可能な形で性能を低下させます。
- 同時実行数が多くても、アップロード、ダウンロード、ガベージコレクション、ライフサイクルポリシーは、安全かつ正確に動作します。
- 一覧表示、検索、バージョン解決などのメタデータ操作は、Organization ごとに数百万のアーティファクトがある規模でも機能します。
- バックグラウンド処理は、ピーク時の未処理作業を許容時間内に解消します。

### 容量と成長に関する考慮事項 {#capacity-and-growth-considerations}

サービスは空の状態から始まり、顧客の導入や、Container Registry と Package Registry からの移行に伴って成長します。Artifact Registry の占める割合が増加しても、3 つのレジストリを合わせた負荷はおおむね安定するため、現在の GitLab.com のレジストリ指標を、このサービスの設計規模の基準とします。

- **トラフィック**：定常状態で毎秒数千の API リクエストがあり、CI のバースト時のピークには毎秒 1 万数千から数万程度まで拡大します。
- **バックグラウンドジョブのスループット**：毎秒数十から数百のジョブがあり、クリーンアップ操作時にピークが発生します。
- **ストレージのスループット**：アップロードは数百 MB/s、ダウンロードは数 GB/s です。
- **データ量**：数十ペタバイトのアーティファクトデータ、ブロブストレージ内の約 10 億のオブジェクト、大規模な Organization ごとの数百万のアーティファクトにより、PostgreSQL のデータセットは TB 規模になります。
- **アクセスパターン**：アーティファクトデータは、最初のプッシュとプルのサイクルの後はめったに読み取られず、大半がコールドまたはアーカイブのストレージクラスに落ち着きます。既存のレジストリでは 80% 超が該当します。ストレージクラスの移行は、プラットフォームが処理します（[ADR-010](010_data_retention.md#storage-class-transitions)）。

詳細なインフラのサイジング、デプロイトポロジー、環境固有の SLA は、この ADR の対象外です。
