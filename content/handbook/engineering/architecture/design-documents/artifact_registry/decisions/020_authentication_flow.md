## ステータス {#status}

**提案中**

この ADR は、呼び出し元のアイデンティティを確立する方法である **認証** のみを扱います。
**認可**（ロール、ポリシー評価、ロール割り当て）は、[ADR-021: 認可](021_authorization.md)で扱います。

## コンテキスト {#context}

クライアントは、自身の GitLab Rails インスタンスが専用の API エンドポイントを通じて、または Rails 自体がユーザーに代わって動作する場合はプロセス内で発行する短命のトークンを使い、Artifact Registry に対して認証します。
Artifact Registry は、これらのトークンをローカルで検証し、発行には関与しません。

Auth Platform チームとの契約は、6 つの要件（R1〜R6）を定める [Artifact Registry と Auth Platform のインターフェイス合意](/handbook/engineering/architecture/design-documents/artifact_registry/agreements/auth/)です。
この ADR は、認証の要件である R1（トークン交換）、R2（トークン検証）、R3（トークンペイロード）を適用します。

## 決定 {#decision}

**Artifact Registry は、GitLab Rails が専用のトークン交換 API エンドポイントを通じて、または Rails 自体がユーザーに代わって動作する場合はプロセス内で発行する短命のトークンを、ローカルで検証することでクライアントを認証します。**

### イテレーションのスコープ {#iteration-scope}

最初のイテレーションは、1 つのインスタンスが 1 つの信頼アンカーを持つ、同一境界のトポロジー（`.com ↔ .com`、`SM ↔ SM`）を対象とします。
Rails は Cloud Connector v1 キーでトークンに署名し、すべてのトークンはプリンシパルの起点として組織を指定し、ペイロードから `gitlab_instance_uid` を省略します。
多数の Self-Managed インスタンスが 1 つの SaaS Artifact Registry を共有するクロス境界のトポロジーは、後続のイテレーションで扱います。

### 常に満たすべき条件 {#what-must-always-hold}

| # | 制約 | 機械的に検証可能か |
| --- | --- | --- |
| 1 | **リクエスト処理中に GitLab インスタンスへコールバックしません。** 発行者の鍵は帯域外で同期します。 | はい。鍵をキャッシュした後は、GitLab インスタンスに到達できない状態でもリクエストを認証できます |
| 2 | **信頼された発行者からのトークンだけがエンドユーザーを認証します。** Artifact Registry は、クライアントの長命な GitLab 認証情報を受け付けることも交換することもありません。 | はい。署名、アルゴリズム、オーディエンス、有効期限の検証に失敗するトークンと、長命な GitLab 認証情報を拒否します |
| 3 | **トークンは短命です。** どのトークンも 12 時間を超えて存続せず、CI/CD ID トークンから発行したものや CI ジョブのペイロードに発行したものは、そのジョブより長く存続しません。 | はい。発行から 12 時間を超えて有効なトークンはなく、ID トークンから発行したトークンやジョブペイロードに発行したトークンは、そのジョブのタイムアウトまでに期限切れになります |
| 4 | **トークンは、自身の組織のネームスペースにしかアクセスできません。** トークンの組織は、ネームスペースの所有者アンカーと不透明な値として比較し、一致する必要があります。 | はい。別の組織のトークンは、ネームスペースをスコープとするすべてのルートで拒否されます |
| 5 | **ビルドメタデータは、リクエストの判定に使いません。** 取得元は CI ジョブが交換時に提示する認証情報だけであり、データベースからは取得せず、値の欠落や形式の不正はビルドメタデータなしを意味します。 | はい。ビルドメタデータが欠落している、または形式が不正なトークンは、ビルドメタデータのないトークンと同じように認証されます |
| 6 | **サービス間の呼び出しは、その接続に必要なすべてのレイヤーを提示します。** 匿名モードはありません。 | はい。必須レイヤーのいずれかが欠けた呼び出しは拒否されます |
| 7 | **拒否したサービストークンについては、何も明かしません。** トークンの欠落と誤りは、呼び出し元からは同じに見えます。 | はい。どちらにも同一のレスポンスを返します |
| 8 | **サービストークンを、ダウンタイムなしにローテーションできます。** 現在の値と次の値を同時に受け付けます。 | はい。ローテーション中は、どちらの値でも認証できます |
| 9 | **開発用認証情報を、トークン交換や認可の強制と同時に使用しません。** | はい。それらを組み合わせた設定は読み込みに失敗します |
| 10 | **Kubernetes のピアは、その経路が有効で、アイデンティティが許可リストに含まれ、ルートがオプトインしている場合にのみ受け入れます。** 検証に失敗したクラスター発行トークンを、エンドユーザートークンとして再試行することはありません。 | はい。いずれかが欠けたピアは拒否されます |

### 非本番開発モード {#non-production-development-mode}

上記の決定は、実際のアーティファクトを提供するすべてのデプロイメントに適用されます。
Artifact Registry には **非本番開発モード** もあり、ローカルチェックアウトやテスト環境など、トークンを発行または署名できる GitLab インスタンスがない環境でも実行できます。
デフォルトではオフです。

このモードでは、Artifact Registry は Rails が発行したトークンの代わりに、静的な開発用認証情報に対して認証します。
その 3 つの特性は、上記の決定に反します。

1. **プリンシパルを確立しません。** [R3 ペイロードクレーム](#token-payload-r3)を一切持たないため、この認証情報で認証されたリクエストは、サブジェクトのないアイデンティティに解決されます。
1. **短命で発行されるものではなく、長命で静的です**。そのため、[帰結](#consequences)に記載した、短い有効期間を根拠とする考え方は適用されません。
1. **サービストークンとしても使われます**。[GitLab Rails から Artifact Registry の内部 API へ](#gitlab-rails-to-the-artifact-registry-internal-api)の接続において、本番デプロイメントが使用するヘッダーに格納します。
   開発者はその接続の認証情報も保持するため、[2 つのレイヤー](#the-two-layers)で説明するデプロイ認証情報とは異なります。サービストークンのレイヤーは引き続き適用され、同じ比較と、詳細を明かさない拒否を行います。

このモードは実際のプリンシパルを受け入れず、本番データも保持しないため、なりすます対象も、アクセスできる価値のあるものもなく、3 つとも許容されます。
この ADR が対象とするトポロジーでは、このモードを使用しません。

[ADR-021](021_authorization.md#non-production-development-mode)に記載する理由から、1 つのスイッチで、このモードと認可を強制しない構成を一緒に選択します。

## アーキテクチャ上の制約 {#architectural-constraint}

[インターフェイス合意](/handbook/engineering/architecture/design-documents/artifact_registry/agreements/auth/#no-callbacks-during-request-processing)に定める **リクエスト処理中のコールバック禁止** が、この決定の根拠です。
リクエストトークンの検証に必要なものはすべて、トークンに含まれるか、すでにローカルにキャッシュされていなければならず、ローカルでステートレスな検証は最適化ではなく、厳格な要件です。
これは、SaaS Artifact Registry から Self-Managed インスタンスに到達できない可能性がある、境界をまたぐ場合に特に重要です。
制約が対象とするのは GitLab インスタンスであり、Artifact Registry とともにデプロイする依存関係ではありません。定期的な鍵の同期（[トークン検証](#token-validation-r2)を参照）は、リクエスト処理の外で行います。

## 認証フロー {#authentication-flow}

Rails がトークンを発行し（R1）、Artifact Registry は、定期的に同期してキャッシュする信頼された発行者の公開鍵を使って、ローカルで検証します（R2）。
クライアントは自身の GitLab インスタンスから直接トークンを取得するため、Artifact Registry がクライアントの長命な認証情報を見ることはありません。

## トークン発行 (R1) {#token-issuance-r1}

Rails は、クライアントの認証情報を受け付け、Artifact Registry 用の短命のトークンを返す、専用のトークン交換 API エンドポイントを公開します。
Rails 自体がユーザーに代わって動作する場合は、代わりにプロセス内で同じトークンを発行します。

1. **認証情報。** エンドポイントは、最初のイテレーションでトークンを発行する唯一のプリンシパル型である `User` に解決される、標準的な GitLab API 認証情報を受け付けます。
   デプロイトークンのようにユーザーに解決されない認証情報は受け付けません。
   型付けされた `sub` クレーム（[トークンペイロード](#token-payload-r3)を参照）により、意味を変えずに他のプリンシパル型を後から追加できます。
1. **クライアント側の交換。** クライアントが自身の GitLab インスタンスからトークンを取得して提示し、Artifact Registry が交換を実行することはありません。
1. **有効期間。** トークンの有効期間は最大 12 時間で、デフォルトは短く設定します。
   クライアントは、この上限まで任意の有効期間を要求できるため、長いビルドの途中で期限切れになるのを防げます。
1. **有効化。** Artifact Registry を有効にしていない組織では、トークン交換は失敗すべきです（R1、SHOULD）。
   これは利用可能性のゲートにすぎず、組織レベルの設定を持つ Rails 側で発行時に確認します。
   アクセスは Unit Primitives やアドオンに依存しません。クレジットベースの課金モデルでは、Artifact Registry アドオンが存在しないためです。
   Artifact Registry 側では、トークンをネームスペースに結び付けます。トークンの組織である `gitlab.origin_id` は、ネームスペースの所有者アンカーの `entity_id` と一致する必要があります（[ADR-001](001_organizations_as_anchor_point.md)）。
   これは、組織を認識する必要のない、不透明な値の比較です。
1. **CI/CD ID トークンの交換。** CI ジョブは、その CI/CD ID トークンを認証情報として提示できます。
   別の依拠当事者向けに発行された ID トークンが交換されないように、ID トークンはトークン交換専用の固定された単一のオーディエンスを持ち、完全一致で照合する必要があります。
   プリンシパルはジョブを実行するユーザーであり、他のすべての認証情報と同じチェックを行います。
   発行したトークンは、ジョブより長く存続できません。
   ジョブトークンも引き続き並行して受け付けますが、ジョブトークンの交換にはビルドメタデータが含まれません。
1. **プロセス内での発行。** Rails がすでにユーザーに代わって動作し、クライアントがエンドポイントを呼び出せない場合は、プロセス内でトークンを発行できます。
   例として、サインイン済みユーザーに代わって動作する Ruby クライアント（[ADR-014](014_frontend_to_artifact_registry.md)）と、ジョブスクリプトが認証情報を交換する前に Runner が必要とする、CI ジョブペイロード内のレジストリ認証情報があります。
   トークンはエンドポイントが発行するものと同じで、発行者、鍵、クレーム、オーディエンスも同じであるため、Artifact Registry は変更せずに検証し、引き続き発行には関与しません。
   各サーフェスは、エンドポイントの発行ルールを適用します。ユーザーはトークンが示す組織のメンバーであり、その組織で Artifact Registry が有効であり、トークンの有効期間は最大 12 時間で、CI ジョブのトークンはジョブのタイムアウトを超えません。
   エンドポイントのユーザーごとのレート制限は、プロセス内での発行には適用されません。
   発行処理が IAM トークンサービスに移るときは、これらのサーフェスも移行します。

## トークン検証 (R2) {#token-validation-r2}

トークンは、GitLab インスタンスの Cloud Connector キーで署名された JWT です。
Artifact Registry は、自身の GitLab インスタンスという 1 つの **信頼された発行者** を設定し、その発行者の公開鍵を帯域外で同期します。
各トークンの署名をキャッシュ済みの鍵で検証し、署名アルゴリズムを固定し、オーディエンスが誤っている、または期限切れのトークンを拒否します。

鍵は定期的にリフレッシュする必要があり、リフレッシュに失敗した場合は古い鍵を短時間保持し、鍵の提供元の一時的な不調によって、その他の点では有効なトークンを拒否しないようにします（[R2](/handbook/engineering/architecture/design-documents/artifact_registry/agreements/auth/#r2--token-validation)）。

Cloud Connector v1 キーを再利用することで、最初のイテレーションはシンプルに保たれます。新しい鍵配布インフラが不要なためです。
ターゲット状態では鍵の提供を GATE に移しますが、キャッシュ済みの信頼された鍵で署名を検証するという、Artifact Registry の動作は変わりません。

## トークンペイロード (R3) {#token-payload-r3}

トークンのペイロードは [AUTH-021](https://gitlab.com/gitlab-org/architecture/auth-architecture/design-doc/-/blob/main/decisions/021-modular-service-token-payload-schema.md)で定義します。
この ADR は、ペイロードの次の特性に依存します。

1. **トークンだけで認証できます。** Artifact Registry が呼び出し元を確立するために必要なものはすべてトークンに含まれるため、コールバックは不要です。
1. **プリンシパルは型付けされています。** `sub` は型を含めてプリンシパルを示すため、意味を変えずに `User` 以外のプリンシパル型にクレームを拡張できます。
   `gitlab` のアイデンティティクレームは、プリンシパルの起点、その起点の ID、起点内のプリンシパルの ID を示します。
1. **1 つのトークンで両方のサービスを利用します。** トークンは Artifact Registry と relationships API のオーディエンスを含むため、Artifact Registry は変更せずに転送できます（[サービス間認証](#service-to-service-authentication)を参照）。
1. **ビルドメタデータは、提示した認証情報から取得します。** `gitlab.job` クレームは、交換した認証情報が CI/CD ID トークンだった場合にのみ存在します。その値はそのトークンからコピーし、データベースからは取得しないため、IAM トークンサービスも同じコピーを行えます。
   認可上の意味はありません。
   利用側は、これらのクレームのいずれかの値が欠落している、または形式が不正である場合、オブジェクト全体を「ビルドメタデータなし」として扱い、それを理由にリクエストを失敗させません。
1. **認可に関するクレームは ADR-021 で扱います。** このトークンは呼び出し元が *誰* であるかを確立し、*何ができるか* は別途評価します。
   認可で、パーソナルアクセストークンと CI ジョブトークンの違いなど、取得元の認証情報の種類も考慮するかどうかも、ADR-021 で扱う問いです。

## サービス間認証 {#service-to-service-authentication}

複数の接続を介した GitLab サービス間の呼び出しには、独自の答えが必要です。
このセクションでは、まず共通のパターンを示し、その後に各接続が何を運ぶかを説明します。

### 2 つのレイヤー {#the-two-layers}

1. **サービストークン。** 「呼び出し元のプロセスは信頼されたピアサービスか」に答えます。静的で対称な共有シークレットを、定時間で比較します。
   アイデンティティを含まないため、結果は受け入れか拒否だけです。
1. **呼び出し元のアイデンティティ。** 「呼び出しは誰のために動作するか」に答えます。呼び出しが誰かのために動作する場合にのみ存在します。
   現在はエンドユーザーのトークンであり、[トークン検証](#token-validation-r2)に従って検証します。

適用するレイヤーは、接続によって異なります。
エンドユーザーに代わって行う呼び出しは、両方を運びます。
ユーザーが開始したものでない呼び出しには、2 番目のレイヤーで運ぶアイデンティティがないため、サービストークンだけが呼び出し元を認証します。
どのレイヤーが適用される場合も、すべてが必須です。いずれか 1 つでも失敗すると、呼び出しを未認証として拒否し、匿名モードはありません。
サービストークンが単独で何かを認可することはありません。エンドユーザーのアイデンティティがある場合、認可はそのプリンシパルに基づきます（[ADR-021](021_authorization.md)を参照）。

1. **認証情報名はサービスごとに異なります。** 各サービスは受け付けるサービストークン認証情報に名前を付けるため、リクエストログから、どの呼び出し元がどのサービスにアクセスしたかを確認できます。
1. **サービストークンはデプロイ認証情報です。** 呼び出し元サービスにシークレットとしてプロビジョニングし、エンドユーザーから見えることはありません。
   [非本番開発モード](#non-production-development-mode)が唯一の例外です。
1. **ヘルスチェックは両方のレイヤーをスキップします**。そのため、Kubernetes のプローブは認証情報なしで動作します。

### Artifact Registry から relationships API へ {#artifact-registry-to-the-relationships-api}

両方のレイヤーが適用されます。
relationships API は、IAM の `iam-data-access` サービスです。

それぞれがエンドユーザートークンを独立して検証します。Artifact Registry は入口で自身のオーディエンスに対して検証し、relationships API は自身の側でもう一度検証します。

データパスでは、Artifact Registry がクライアント自身のトークンを変更せずに転送するため、ユーザーのアイデンティティがエンドツーエンドで流れます。
これには、呼び出し元自身への権限付与に基づいてリポジトリ一覧の可視範囲を制限する、リクエストごとのルックアップも含まれます。IAM は、呼び出し元自身の組織に属するサブジェクトについてのみ、そのルックアップを許可します。

ロール割り当ての読み取りや変更を行う管理フローと UI フローは、代わりに Rails GraphQL ラッパーを通ります。このラッパーは、Rails のトークン発行者から relationships API 用の独自のトークンを要求します。

### GitLab Rails から Artifact Registry の内部 API へ {#gitlab-rails-to-the-artifact-registry-internal-api}

サービストークンだけが適用されます。
内部 API は、[ADR-009](009_api_design.md#gitlab-api)で定義する、Rails 向けのサーフェスです。
その呼び出しはエンドユーザーに代わって行うものではないため、2 番目のレイヤーで運ぶアイデンティティはありません。
ここでのサービストークンは暫定的な仕組みです。方向性については、[将来の作業 / 未解決の議論](#future-work--open-debates)を参照してください。

### 同じクラスター内のサービス：Kubernetes サービスアカウントトークン {#services-in-the-same-cluster-kubernetes-service-account-tokens}

Artifact Registry と同じ Kubernetes クラスター内で実行するサービスは、Rails が発行したトークンもサービストークンも使わずに、自身として Artifact Registry を呼び出せます。
この経路は、[将来の作業 / 未解決の議論](#future-work--open-debates)に未解決項目を記載する、より長期的な取り組みの最初のステップです。
デフォルトではオフで、運用担当者がデプロイメントごとにオンにするスイッチで制御します。

1. **認証情報は、呼び出し元に投影されたサービスアカウントトークンです**。エンドユーザートークンと同様に、クラスターが公開した鍵に対してオフラインで検証します。
1. **発行者が検証器を選択します。** エンドユーザートークンも同じヘッダーで送られるため、トークンの発行者によって、どの検証を受けるかが決まります。
   検証前に発行者を読み取るのは選択のためだけであり、選択した検証器は引き続きすべてを確認し、拒否したトークンを別の経路にフォールバックせずに拒否します。
1. **アイデンティティは、SPIFFE ID として表現するサービスアカウントです**。トークンのサブジェクトから導出します。
   そのサービスアカウントとして実行するすべての Pod が、同じアイデンティティを共有します。
1. **SPIFFE ID の許可リストが、信頼境界のすべてです。** 検証済みのトークンでも、ID がリストにない場合は拒否します。
   呼び出し元はエンドユーザーに代わって動作せず、組織を指定しないため、GitLab のプリンシパルは確立されません。受け入れられた呼び出し元が何を実行できるかは、[ADR-021](021_authorization.md#services-in-the-same-cluster)に記載します。
1. **各ルートがオプトインします。** この呼び出し元を受け入れないルートは、トークンにかかわらず拒否します。

## 検討した代替案 {#alternatives-considered}

トークンの仕組みは [インターフェイス合意](/handbook/engineering/architecture/design-documents/artifact_registry/agreements/auth/)から導かれ、Auth platform は自身の側で代替案を比較検討しました。
Artifact Registry 側では、次の 2 つの選択肢が不採用となりました。

1. **何もしない：GitLab の認証情報を直接受け付ける。** Artifact Registry は、クライアントが現在送信するパーソナルアクセストークンとジョブトークンを受け付けることになります。
   その認証情報の検証にはリクエストごとに GitLab インスタンスを呼び出す必要がありますが、[コールバック禁止の制約](#architectural-constraint)がこれを禁じていること、および Artifact Registry が長命な認証情報を保持することになるため、不採用です。
1. **Artifact Registry が交換を実行する。** 長命な認証情報を受け取り、リクエスト処理中に GitLab インスタンスを呼び出すことになるため、同じ 2 つの理由で不採用です。

`gitlab.job` のビルドメタデータの取得元は、Authentication チームとともに決定しました（[AUTH-021](https://gitlab.com/gitlab-org/architecture/auth-architecture/design-doc/-/blob/main/decisions/021-modular-service-token-payload-schema.md)）。
交換エンドポイントは IAM トークンサービスに移行する予定ですが、このサービスは Rails データベースから CI ジョブのレコードを読み取れず、複数のパッケージクライアントは認証情報を 1 つしか送信できないため、クレームはジョブが交換時に提示する認証情報から取得する必要があります。
次の 3 つの選択肢を比較検討しました。

1. **自己証明（SLSA または npm provenance）。** ジョブがメタデータとアーティファクトのダイジェストを結び付ける in-toto ステートメントを作成して署名し、Artifact Registry が検証します。
   事実を公開されたバイト列と結び付ける唯一の選択肢であり、公開経路でのアーティファクトのすり替えが防御対象の脅威になった場合の発展経路として残します。
   現時点では不採用です。すべてのパッケージフォーマットに対する公開側のツール、ステートメントのスキーマ、新しい検証経路が必要になるためです。
1. **Artifact Registry が ID トークンを 2 つ目の認証情報として検証する。** 同じ信頼できる情報源をアクセストークンとともに提示します。
   Maven、npm、Docker の各クライアントは認証情報を 1 つしか送信できず、ID トークンを交換処理に通せば、トークン 1 つと信頼された鍵の 1 セットを維持できるため、不採用です。
1. **現在はデータベース、後に JWT ジョブトークンからクレームを取得する。** トークンサービスは認証基盤の一部であり、個別の機能のデータベーステーブルに依存してはいけないこと、JWT ジョブトークンのロールアウトは FY28 より前には予定されていない破壊的変更であること、および汎用の発行経路に Artifact Registry 固有のクレーム構築処理が残ることを理由に、不採用です。

ID トークンは、CI ジョブがすでに保持する認証情報の中で、GitLab が署名し、`gitlab.job` のすべてのクレームを含み、発行が他のロールアウトに依存しない唯一の認証情報です。
これらのクレームは公開されたバイト列について何も証明しないため、来歴ではなくビルドメタデータと呼びます。

## 帰結 {#consequences}

### ポジティブ {#positive}

1. **リクエスト処理中は Rails の可用性に依存しません**：検証がローカルでステートレスであるため、Artifact Registry は、発行元の GitLab インスタンスに到達できない場合もリクエストを認証できます。
1. **短命のトークンは影響範囲を限定します**：Artifact Registry は、クライアントの長命な GitLab 認証情報を扱わず、短命のトークンだけを扱うため、漏えいしたトークンはすぐに期限切れになり、漏えいしたパーソナルアクセストークンよりも露出範囲がはるかに小さくなります。
1. **プラットフォームの方向性と整合します**：Artifact Registry は独自のフローを維持するのではなく、プラットフォームのトークン交換と検証のプリミティブを利用します。

### ネガティブ {#negative}

1. **暫定状態では GitLab インスタンスへの接続が必要です**：Artifact Registry はトークンを検証するために、リクエストごとではなく帯域外で、GitLab インスタンスから発行者の鍵を同期します。
   最終状態では GitLab インスタンスへの接続を一切必要としないことが目標であり、ターゲット状態では GATE から鍵を提供することで実現します。
1. **Cloud Connector v1 の仕組みを再利用します**：暫定状態では、GATE が発行した鍵ではなく、既存の Cloud Connector v1 キーに依存します。
1. **発行したトークンは期限切れ前に失効できません**：ローカルで検証し、コールバックもブロックリストもないため、発行元の認証情報が発行直後に失効しても、トークンは期限切れまで有効です。たとえば、フィッシングされたパーソナルアクセストークンが 12 時間のトークンに交換された場合です。
   デフォルトの有効期間の短さによって緩和し、ベータでは受け入れるトレードオフとします。より強い送信者バインディング（DPoP など）や鍵のローテーションは、将来の堅牢化として実施できます。
   CI/CD ID トークンは、同じ露出を持つ 2 つ目の Bearer 認証情報を追加します。持ち出された ID トークンは、その保持者なら誰でも、別のジョブからでも、ジョブのタイムアウトまで交換でき、発行したトークンはその ID トークンのビルドメタデータを持ち、そのユーザーとして動作します。
   認可の範囲は、トークンがすでに付与する範囲を超えません。ID トークンはジョブトークンと同様にマスクおよび秘匿化し、交換のたびに監査記録を残し、トークンサービスでの単回使用の追跡と送信者バインディングにより、この問題を解消します。
1. **Artifact Registry が有効な組織のすべてのジョブは、デフォルトで ID トークンを取得します**。これは GitLab 自身が受け付ける Bearer 認証情報であり、ジョブ内のすべてのスクリプトから見える環境変数に格納します。
   ジョブトークンと同じマスキングとドキュメントが必要であり、選択した変数名で ID トークンをすでに宣言しているジョブと衝突する可能性があり、Self-Managed と Dedicated ではインスタンス全体に適用されます。
   これは [CI のアンビエント認証情報](https://gitlab.com/gitlab-org/architecture/auth-architecture/design-doc/-/blob/main/proposals/004-ambient-credentials-in-ci.md)の目標に反します。アンビエント認証情報が利用可能になれば、この経路を置き換えます。
   ビルドメタデータが存在するのは ID トークンが提示された場合だけなので、その網羅性はデフォルトの発行に依存します。

### 緩和策 {#mitigations}

- Artifact Registry の検証ロジックは、暫定とターゲットの発行者で同じです。変わるのは発行者の鍵の取得元だけであり、移行の影響範囲を限定します。

## 将来の作業 / 未解決の議論 {#future-work--open-debates}

これらの認証に関する問いは未解決であり、最初のイテレーションのスコープ外です。

1. **クロス境界の発行者の鍵と `gitlab_instance_uid`。** クロス境界のフォローアップでは、多数の Self-Managed インスタンスが 1 つの信頼アンカーの背後にあるため、トークンで発行インスタンスを識別する必要があります。
   `gitlab_instance_uid` または同等のものの再導入と、それに伴う検証モデルの変更は未解決です。
   SaaS Artifact Registry に接続するリモート Runner のためにジョブトークンを自動交換することも、このフォローアップに含まれます。
1. **ターゲット状態のサービス認証情報。** サービストークンは暫定的な仕組みです。
   方向性は、共有シークレットを相互 TLS とワークロードアイデンティティに置き換え、SPIFFE 形式の呼び出し元識別子を使用し、GitLab Unified Request Token（[URT](https://gitlab.com/gitlab-org/architecture/auth-architecture/design-doc/-/blob/main/glossary.md)）で呼び出し元のアイデンティティを伝えることです。
   どちらの方向性も決定されておらず、URT はまだ存在しません。
   相互 TLS を再検討する条件を含む、クラスター内のトランスポートセキュリティについては、[ADR-024](024_infrastructure_delivery.md#transport-security)に記載します。
1. **クラスター内サービスの呼び出し元の組織スコープ。** [同じクラスター内で受け入れられた](#services-in-the-same-cluster-kubernetes-service-account-tokens)サービスアカウントは、それを許可するルートが到達するすべての組織で動作します。
   設定や署名付きクレームによって、呼び出し元をそのサービス提供先の組織に結び付ける方法は未解決です。
