## 背景 {#context}

サービスがダウンロードをリダイレクトする場合（[ADR-005](005_artifact_delivery_mode.md)）、署名付き URL を返し、クライアントは CDN または blob ストレージから直接バイト列を取得します。
そのため、サービスは、どの CDN をどのストレージの前段に置けるか、どのクライアントが CDN を迂回するか、サービスが観測できないダウンロードをどうネームスペースに帰属させるかを決める必要があります。
代わりにサービスがダウンロードをストリーミングする場合は、URL に署名せず、CDN を使わず、転送全体を観測できるため、この ADR は適用されません。

Container Registry は GitLab.com で何年もこの方法でダウンロードを配信し、月間数十ペタバイトの外向き転送と 85% を超える CDN キャッシュヒット率を実現してきました。
Artifact Registry は同じ設計を採用します。
各デプロイメントの blob ストレージと CDN は [ADR-006](006_technology_stack.md)で選択し、この ADR はすべてのペアリングが満たすべきルールを定めます。

## 決定 {#decision}

**CDN は同じプロバイダーの blob ストレージの前段に配置し、サービスはすべてのダウンロード URL に対し、オブジェクト全体を 1 つの単位として署名します。リダイレクトされたダウンロードは、クライアントが変更できるものではなく、プロバイダーのアクセスログ内のオブジェクトパスから、そのネームスペースに帰属させます。**

### 常に満たすべき条件 {#what-must-always-hold}

| # | 制約 | 機械的に検証可能か |
| --- | --- | --- |
| 1 | **CDN は自身のプロバイダーの blob ストレージの前段に配置します。** デプロイメントでは、Google Cloud CDN と GCS、CloudFront と S3 のように、同じプロバイダーの blob ストレージとのみ CDN を組み合わせます。 | はい。別のプロバイダーの blob ストレージの前段に CDN を配置する設定は、起動時に拒否されます |
| 2 | **CDN は、キャッシュヒット時を含め、配信前に署名を確認します。** 有効な署名なしに、プライベートな blob がキャッシュから出ることはありません。 | はい。署名が欠落、改変、または期限切れのリクエストは、オブジェクトがキャッシュされている場合も拒否されます |
| 3 | **署名によってキャッシュが分割されることはありません。** 1 つのオブジェクトに対するすべての署名付き URL は、署名や有効期限にかかわらず同じキャッシュエントリを読み取ります。 | はい。キャッシュ済みのオブジェクトに対して署名した 2 つ目の URL は、キャッシュから配信されます |
| 4 | **CDN は大きなオブジェクトをキャッシュします。** コンテナレイヤーやその他の大きなアーティファクトは数十ギガバイトに達するため、ペアリングは少なくとも 50 GB のオブジェクトをキャッシュします。 | いいえ。上限は CDN プロバイダーが設定します |
| 5 | **署名付き URL は、1 つのオブジェクト全体を対象とします。** サービスは短いプレフィックスではなく、オブジェクトの完全な URL に署名するため、署名はネームスペースハッシュを含むパス全体を対象とします。 | はい。サービスが発行する各署名付き URL は、ちょうど 1 つのオブジェクトへのアクセスを許可します |
| 6 | **帰属はパスだけから判定します。** クライアントは署名の対象外のものを変更できるため、署名付き URL のクエリ文字列には帰属データを含めません。 | はい。どの署名付き URL も、パスの外にネームスペースやユーザーなどの帰属データを含みません |
| 7 | **すべてのクライアントリクエストについて、完全なオブジェクトパスをログに記録します。** CDN と blob ストレージのどちらが配信した場合も、アクセスログにすべてのクライアントリクエストの完全なオブジェクトパスを記録します。 | はい。どちらの経路のダウンロードも、完全なオブジェクトパスを含むアクセスログのエントリを残します |
| 8 | **ペアリングの切り替えは設定変更で行います。** サポートされるペアリング間の移行にアプリケーションの変更は不要です。 | はい。サポートされる各ペアリングは、設定だけで選択し、同じビルドで実行します |

### サポートされるペアリング {#supported-pairings}

CDN と blob ストレージは、同一ネットワーク内のキャッシュフィル、ネイティブな署名付き URL の検証、運用上の整合性のため、1 つのプロバイダーから提供されます。
サービスはサーバー側ですべての URL に自ら署名します。CDN URL には CDN のネイティブな方式を、直接取得する URL にはストレージプロバイダーのネイティブな方式を使用します。

### 相互作用パターン {#interaction-patterns}

CDN を前段に配置した場合、リダイレクトはクライアントを次のいずれかの経路に送ります。

- **プロバイダーのネットワーク外にいるクライアントは CDN に向かいます。** CDN は署名を確認し、キャッシュヒット時はそこから配信し、ミス時はプロバイダーのネットワークを介して blob ストレージからキャッシュを埋めます。
- **プロバイダーのネットワーク内にいるクライアントは、blob ストレージに直接アクセスできます。** プロバイダーのネットワークを介して blob ストレージから配信するほうが、CDN 配信より低コストです。迂回はペアリングごとのオプションです。価格差が小さい場合、ルーティングは利点なしに複雑さを増やします。

### ダウンロードメタデータの伝播 {#download-metadata-propagation}

リダイレクト後、サービスはダウンロードを観測できません。クライアントが完了したか、何バイト取得したか、失敗したかを把握できません。
結果はプロバイダーのアクセスログに記録します。CDN が配信したリクエストは CDN のログに、直接取得したリクエストは blob ストレージのログに記録します。
オブジェクトパスはネームスペースハッシュを保持するため（[ADR-008](008_content_addressable_storage.md#storage-path-strategy)）、すべてのログエントリから blob を所有するネームスペースを特定できます。
制約 5〜7 により、現在および将来のすべてのペアリングでこれが成立します。

## 結果 {#consequences}

### プラス面 {#positive}

1. **大規模環境で実証済みです**：この設計は GitLab.com の Container Registry と同じです。
1. **リダイレクトをまたいで帰属を判定します**：署名されたパス内のネームスペースが、リダイレクトモードによって GitLab.com に生じる可視性のギャップを埋めます。

### マイナス面 {#negative}

1. **ペアリングが結合されます**：CDN は blob ストレージプロバイダーに結び付きます。デプロイメントは通常、すべて GCP またはすべて AWS であるため、制限になることはほとんどなく、[クロスプロバイダー CDN](#cross-provider-cdn-for-example-cloudflare)も引き続き可能です。
1. **大規模運用時の CDN 配信コストがかかります**：プロバイダーネイティブの CDN は、配信した GiB ごとに段階制で課金するため、トラフィック量が大きいと CDN が大きなコストになり得ます。

## 代替案 {#alternatives}

### 何もしない：CDN を使わない {#do-nothing-no-cdn}

すべてのダウンロードを blob ストレージに直接リダイレクトします。
不採用です。無視できないトラフィック量では、CDN は blob ストレージの外向き転送を削減し、エッジキャッシュによってダウンロードのレイテンシを低減し、可用性を高めるからです。

### クロスプロバイダー CDN（例：Cloudflare） {#cross-provider-cdn-for-example-cloudflare}

すべてのストレージプロバイダーの前段に 1 つの CDN を配置することで、デプロイメント間の設定の違いを減らします。
Container Registry 規模でのコスト分析では、Cloudflare の従量制ではない配信により、大幅な削減の可能性が示されました。

延期します。Cloudflare には、署名付き URL を検証するカスタムインフラ（WAF ルールまたは Worker）、手動でのキャッシュキーストリッピング、誰も検証していないダウンロードメタデータの抽出方法が必要だからです。
ネットワークをまたいでキャッシュを埋めるコストは、同一ネットワーク内で埋めるよりも大幅に高くなります。
Artifact Registry はゼロトラフィックから始まるため、現時点ではコスト削減は重要ではありません。

この選択肢は閉ざされていません。制約 1 を見直すことで、後からクロスプロバイダー CDN を新しいペアリングとして追加できます。
