## 概要 {#summary}

Debian と RPM のクライアントは、すでに保持するキーによる OpenPGP 署名がメタデータに付いている場合にのみ、リポジトリを信頼します。この ADR は、両方の形式に 1 つのキー設計を定めます。キーは、ネームスペースと 1 つの形式に属し、各ホスト型リポジトリと、ホスト型のメンバーだけを持つ各仮想リポジトリが、自身の形式のキーを選択します。秘密キーは暗号化された認証情報であり、コードは署名機構を通じてのみアクセスします。キーは有効期限のない RSA とし、サポートするすべてのクライアントが受け入れられるようにします。レジストリは、ホスト型のコンテンツから構築したメタデータだけに署名し、パッケージには署名しません。ローテーション時は、クライアントに両方のキーを提供し、それぞれのペースで移行できるようにします。

## 動機 {#motivation}

Debian と RPM のリポジトリ形式は、どちらもリポジトリのメタデータに署名するキーを必要とします。apt は、各インデックスのハッシュを列挙した `Release` ファイルの署名を検証し、各インデックスは、各パッケージのハッシュを列挙します。`dnf` は、他のメタデータファイルのチェックサムを列挙した `repomd.xml` の署名を検証します。両方のクライアントが受け入れるのは OpenPGP だけです。

1 つの決定がなければ、各形式の仕様が、暗号化、暗号化キーのローテーション、シュレッディングのコードを伴う独自のキーを設計します。誤った設計のコストを大きくする特性が 3 つあります。

1. **キーが顧客の信頼の起点になります。** 各クライアントは、自身で公開キーのコピーを保持します。レジストリはそのコピーを変更できないため、キーを変更するたびに、すべてのクライアントに影響します。
1. **アルゴリズムはクライアントが決めます。** apt、rpm、`dnf` が受け入れるキー種別の集合はそれぞれ異なり、リリース間でも変わります。サポートするリリースの 1 つが拒否するキーは、一部の顧客が使えないキーです。
1. **FIPS の下にある署名用のシークレットです。** キーが漏洩すると、誰でも顧客のクライアントが信頼するメタデータに署名できます。また、署名は Go の FIPS モジュール内で実行する必要があります。

### 目標 {#goals}

- Debian と RPM に 1 つのキー設計を使い、暗号化、暗号化キーのローテーション、シュレッディングの仕組みを共通にします。
- サポートするすべてのクライアントリリースが、FIPS モードでも署名を検証できます。
- RPM の各ホストで新しいキーを 1 回確認することを除き、公開されたキーに従うクライアントを壊さずに、顧客がキーをローテーションできます。
- ネームスペースを暗号学的にシュレッディングすると、その署名キーを破壊します。

### 対象外 {#non-goals}

- パッケージへの署名。パッケージの署名は、引き続き公開者の担当です。
- 顧客のキーのインポートと、秘密キーのエクスポート。
- KMS または HSM のバックエンド。
- キーのエンドポイント、ローテーション時の重複期間の長さ、`Valid-Until` の期間、キー切り替え時の顧客への通知といった、形式ごとの詳細。これらは Debian と RPM の仕様で決めます。

## 提案 {#proposal}

**Debian と RPM に 1 つの OpenPGP キー設計を使います。キーは、形式固有のテーブルに格納する、1 つの形式のネームスペースリソースであり、ホスト型リポジトリ、またはホスト型のメンバーだけを持つ仮想リポジトリが選択します。キーは、コードが署名機構を通じてのみアクセスする、暗号化された認証情報です。レジストリは、ホスト型のコンテンツから構築したメタデータだけに署名します。**

この決定では、次の制約を定めます。

| 制約 | 機械的に検証可能か |
|---|---|
| 署名キーは、ネームスペースと 1 つの形式に属します。署名する各 Debian または RPM リポジトリは、自身の形式のキーを選び、ローテーション中は 2 つ目も選びます。 | はい：スキーマは、他の形式のキーの選択を拒否します。 |
| キーは、ネームスペースレベルのルートで管理します。リポジトリが選択するキーの変更には、ネームスペースに対する `create_repository` が必要で、[ADR-021](021_authorization.md#permissions)の定めに従って認可します。権限は追加しません。 | はい：リポジトリレベルのロールしか持たない主体は、キーを作成したり、選択を変更したりできません。 |
| 秘密キーは、暗号化キーのローテーションとシュレッディングの対象になるよう、暗号化された認証情報としてのみ保存します。読み取るのは署名機構だけです。 | はい：すべてのキーテーブルが暗号化キーのローテーションの対象となり、署名機構以外のコードが秘密キーを読み取ることはありません。 |
| 秘密キーを受け入れたり、返したりするルートはありません。 | はい：管理 API のリクエストやレスポンスに、秘密キーを含めません。 |
| キーは、OpenPGP v4 の 3072 または 4096 ビットの RSA とし、すべての署名で SHA-256 以上を使い、有効期限を設けません。 | はい：生成されたキーはこれらの特性を持ち、サポートするすべてのクライアントリリースが、その署名を検証します。 |
| Go 標準ライブラリが、FIPS モジュール内で RSA キーを生成し、署名を計算します。v4 のキーフィンガープリントが SHA-1 を使うため、署名コードは、SHA-1 を禁止するゲートの外に置きます。 | はい：FIPS モジュールを有効にした状態で、署名コードは指定したサイズの RSA を生成し、その署名を検証できます。 |
| レジストリは、[`ProtonMail/go-crypto`](https://github.com/ProtonMail/go-crypto) の RSA の経路だけを使います。 | はい：そのほかの部分をインポートするコードはありません。 |
| レジストリは、ホスト型のコンテンツから構築したメタデータだけに署名し、パッケージのバイト列は変更しません。リモートリポジトリは、アップストリームのメタデータと署名を変更せずに中継します。仮想リポジトリがキーを選択するのは、すべてのメンバーがホスト型の場合だけであり、リモートのメンバーの追加は拒否します。 | はい：パッケージはアップロード時のハッシュを維持し、中継したアップストリームの署名はアップストリームのキーで検証でき、キーを持つ仮想リポジトリはリモートのメンバーを拒否します。 |
| 監査ログを実装した後は、キーの作成、ローテーション、削除は、いずれも顧客の信頼の起点を変えるため、監査イベントを出力します。 | はい：監査ログを実装した後は、各キー管理ルートが、その監査イベントを出力します。 |
| ホスト型 Debian または RPM リポジトリの作成では、その形式のキーを指定するか、キー管理操作でデフォルトとした、その形式の 1 つのキーである、ネームスペースのデフォルトキーを選択します。キーを生成することはありません。選択できるキーがなければ、作成は失敗します。それ以外のリポジトリの作成には、キーは不要です。 | はい：形式ごとに、作成時は指定されたキー、指定がなければデフォルトキーを選択し、どちらもなければ失敗し、生成はしません。 |

利点：

- Debian と RPM が、1 つの暗号化経路、1 つの暗号化キーローテーションツール、1 つのシュレッディング経路を共有します。異なるのは、キーテーブルだけです。
- ある形式のキーは、他の形式のリポジトリから選択できないため、侵害の影響が 1 つの形式内に留まります。
- キーは、すでに提供している列レベルの暗号化を再利用し、新しいストレージの依存先を必要としません。
- 後からスキーマを変更せずに、署名機構の背後の保存されたキーを KMS に置き換えられます。
- SHA-256 を使う RSA-3072 は、サポートするすべてのリリースの apt、`dnf`、FIPS モードで検証を通過します。
- パッケージは、アップロード時のバイト列とコンテンツハッシュを維持します。

欠点：

- 署名中、秘密キーはレジストリのメモリ内に存在します。ラップされたコピーは、保持期間が過ぎるまでバックアップに残ります。
- `go-crypto` は、標準ライブラリ以外では初めての暗号ライブラリです。RSA 署名では呼び出さない `circl` のコードをリンクします。
- SHA-1 のキーフィンガープリントは FIPS ゲートの下では panic を起こすため、署名コードには専用の CI ジョブが必要です。
- キーを共有すると、その形式内で侵害の影響も共有します。分離が必要なリポジトリは、専用のキーを選択します。
- 1 つのキーを両方の形式に使うことはできません。Debian と RPM で 1 つの信頼の起点を求めるネームスペースは、キーを 2 回作成し、ローテーションします。
- `dnf` のホストが、パッケージに対してもレジストリのキーを信頼するようになる場合があるため、漏洩したキーでそのホスト向けのパッケージに署名できる可能性があります。RPM の仕様では、そのインポートが実行されないよう、先に公開者のキーをインポートするよう顧客に伝えます。
- リモートのメンバーを持つ仮想リポジトリは、アップストリームのインデックスを結合するため、この ADR の下では署名できません。クライアントの検証方法は、その仕様で決めます。
- モノリスのユーザーは、新しいキーを信頼する必要があります。新しいリポジトリ URL に移るとき、各クライアントがそれを追加します。

## 設計と実装の詳細 {#design-and-implementation-details}

### キーはネームスペースリソースである {#the-key-is-a-namespace-resource}

ネームスペースは、ある形式の署名するすべてのリポジトリに 1 つの信頼の起点を提供することも、あるリポジトリに専用のキーを与えることもできます。キーは、他のネームスペースレベルのリソースと並んで存在します（[ADR-009](009_api_design.md)）。キーの作成、ローテーション、削除は、顧客の信頼の起点を変えるため、監査ログを実装した後は、それぞれ監査イベントを出力し、[ADR-010](010_data_retention.md#audit-log-retention)が管理操作として保持します。

Debian と RPM のキーは、形式データについて [ADR-007](007_database_schema.md#data-organization) が定めるとおり、別々の形式別テーブルに格納します。リポジトリは他の形式のキーを選択できないため、侵害の影響が 1 つの形式内に留まります。暗号化、暗号化キーのローテーション、シュレッディングのコードは共有します。リポジトリが選択しているキーは削除できません。

キーの選択は、リポジトリ設定のフィールドですが、ネームスペースのキー管理として認可します。そのため、リポジトリの Manager は、分離のために本番用リポジトリが選んだキーに、自身のリポジトリを向けられません。キーを指定する作成でも、デフォルトを使う作成でも、同じルールで選択し、ネームスペースに対する `create_repository` が必要です。

### キーは署名機構の背後にある認証情報である {#the-key-is-a-credential-behind-a-signer}

秘密キーは、レジストリの列レベルの暗号化の下にある、キー行の認証情報です。ネームスペースキーが、行のデータキーをラップします。ネームスペースの暗号学的シュレッディングは、ネームスペースキーとともにキーを破壊します。利用停止中のネームスペースも pull を提供するため（[ADR-022](022_namespace_decoupling.md)）、レジストリはシュレッディングするまで署名を続けます。

コードは、署名機構に署名を要求し、最初の署名機構は保存されたキーを使います。後から KMS または HSM の署名機構を追加すれば、秘密キーがレジストリに入ることはありません。KMS は、自身の検証済み境界内で署名を計算し、その境界は、レジストリの Go モジュールについての認証の主張には含まれません。そのため、KMS の署名機構を提供するのは、選択した KMS が CMVP の Active リストにある FIPS 140-3 証明書を持つ場合だけです。

### アルゴリズムはクライアントが決める {#the-clients-choose-the-algorithm}

RSA は、サポートするすべてのクライアントリリースが、FIPS モードでも警告なしで受け入れる、唯一のキー種別です。ECDSA P-256 は、リリース時点の Ubuntu 24.04 で警告が出て、Ed25519 は RHEL 8 と FIPS モードの RHEL 10 で失敗します。apt 3 のデフォルトポリシーは、RSA-2048 を 2030 年まで受け入れるため、RSA-3072 は、それ以降も受け入れ可能であり、KMS での署名コストも RSA-4096 より低くなります。RSA-4096 は、モノリスのキーサイズを期待する顧客向けの設定です。キーが期限切れになると apt と `dnf` が検証できなくなるため、キーには有効期限を設けず、代わりにローテーションで置き換えます。

### ライブラリが OpenPGP のフレーミングを記述する {#a-library-writes-the-openpgp-framing}

クライアントが固定するのは OpenPGP の形式であり、暗号処理ではありません。Go 標準ライブラリが、FIPS モジュール内で RSA 署名を計算します。`go-crypto` は、その周囲のフレーミングである、パケット、キーフィンガープリント、アーマー、クリア署名を記述します。Debian と RPM の両方が署名コードを呼び出すため、形式のパッケージではなく、共有コードに配置します（[ADR-023](023_code_structure_and_enforcement.md)）。

v4 形式ではフィンガープリントが SHA-1 に固定され、FIPS ゲートの下で panic を起こすため、署名コードはゲート付きパッケージの外に置き、独自の FIPS モードのチェックを設けます。これは、新しいセキュリティ上重要な暗号処理をゲート付きパッケージに置くという、FIPS の方針の例外です。レジストリは、自身が生成したキーについてのみフィンガープリントを計算するため、攻撃者が選んだキー素材がそこに届くことはなく、署名の安全性はフィンガープリントではなく RSA 署名に依存します。未使用の `circl` コードは検証済みモジュールの境界外にあるため、検証に影響しません。

Security は、次の条件でフレーミングに `go-crypto` を使うことを認めます。標準ライブラリがダイジェストと署名の両方を計算し、インポートのチェックによって `circl` の機能を使用しない状態に保ち、脆弱性スキャンが依存先を対象にし、エンコーディングの独立したチェックとして、各クライアント自身の `gpg` が出力を検証します。

レジストリが行うのは、キーの生成と署名だけです。OpenPGP の最もリスクが高い部分である、他者が提供したキーやメッセージの解析は行いません。キーのインポートを提供する場合は、インポートするキーを攻撃者が選べるため、Security が `go-crypto` と SHA-1 フィンガープリントを再レビューします。

### レジストリはホスト型コンテンツから構築したメタデータだけに署名する {#the-registry-signs-only-metadata-built-from-hosted-content}

- ホスト型リポジトリは、`Release` ファイルと `repomd.xml` に署名します。
- すべてのメンバーがホスト型の仮想リポジトリは、レジストリがメタデータを構築するため、選択したキーで結合後のメタデータに署名します。リモートのメンバーの追加は拒否するため、署名されたリポジトリが署名なしに変わることはありません。
- リモートリポジトリは、アップストリームのメタデータと署名を変更せず中継するため、クライアントはアップストリームの公開者のキーで検証します。
- レジストリは、パッケージに署名しません。新しい署名はブロブのハッシュを変えます（[ADR-008](008_content_addressable_storage.md)）。また、各署名は独自の作成日時を持つため、1 回のアップロードに 2 回署名すると、重複排除できません。

### ローテーションではクライアントに両方のキーを提供する {#a-rotation-gives-clients-both-keys}

署名するリポジトリは、ローテーション用に 2 つ目のキーを選択し、クライアントは両方の公開キーを取得できます。レジストリの署名方法は、クライアントによって異なります。

- **Debian は、両方のキーで署名します。** apt はキーを取得できないため、クライアントは、ユーザーが変更するまでキーを保持します。サポート対象のすべてのリリースで、apt は片方のキーだけを信頼している場合でも 2 つの署名を受け入れます。apt の[統合テスト](https://github.com/Debian/apt/blob/3.0.3/test/integration/test-releasefile-verification#L163-L170)でこの動作を確認できます。
- **RPM は、1 つのキーで署名し、両方を公開します。** `dnf5` は二重の署名を拒否するため、レジストリは署名を新しいキーに切り替え、両方の公開キーを公開します。検証に失敗した `dnf` クライアントは、キーを再取得し、新しいキーのインポートを求めます。そのため、重複期間の長さにかかわらず、RPM の各ホストで新しいキーを 1 回確認します。

## 代替案 {#alternative-solutions}

### 何もしない {#do-nothing}

各形式の仕様が、独自のキーを設計します。各形式について、事前に必要な合意が少なくなります。

**却下理由。** 2 つの設計では、暗号化、暗号化キーのローテーション、シュレッディングのコードも 2 組になります。各仕様で、クライアントと FIPS の調査も繰り返す必要があります。

### モノリスの設計をコピーする {#copy-the-monoliths-design}

モノリスの Debian レジストリは、ディストリビューションごとに、有効期限のない RSA-4096 キーを生成します。キーとランダムなパスフレーズを 1 つのインスタンスシークレットで暗号化し、GnuPG を通じて署名します。この設計には実績があります。

**却下理由。** レジストリにはディストリビューションオブジェクトがなく、キーはネームスペースリソースです。1 つのインスタンスシークレットでは、ネームスペースごとにシュレッディングできず、保存したパスフレーズも同じシークレットで開くため、利点はありません。GnuPG は Go の FIPS モジュールの外で署名します。モノリスにはローテーションがないため、キーを変更すると、すべてのクライアントが一度に使えなくなります。

### リポジトリごとに 1 つのキー {#one-key-per-repository}

モデルは単純であり、漏洩の影響は 1 つのリポジトリに限られます。

**却下理由。** 10 個のリポジトリを持つ顧客は、10 個のキーを配布し、10 回ローテーションします。リポジトリは、引き続き専用のキーを選べるため、ネームスペースリソースでは、そのコストを必須にせず、この選択肢を維持できます。

### 両方の形式に 1 つのキーテーブル {#one-key-table-for-both-formats}

1 つのテーブルが Debian と RPM のキーを保持します。1 つのキーで Debian の `Release` ファイルと RPM の `repomd.xml` に署名できるため、ネームスペースは両方の形式に 1 つの信頼の起点を提供でき、キーの保存、暗号化、ローテーションも 1 回で済みます。

**却下理由。** Product は、両方の形式をまたぐ 1 つのキーを求める顧客を確認していません。Product の必須要件である、ある形式のリポジトリ間で 1 つのキーを共有することは、形式ごとのテーブルで満たせます。共有キーは、形式間で侵害の影響も共有します。

### アップストリームのメタデータに再署名する {#re-sign-upstream-metadata}

リモートリポジトリ、またはリモートのメンバーを持つ仮想リポジトリが、アップストリームの署名を検証し、顧客のキーで署名します。クライアントが信頼するキーは 1 つになり、アーキテクチャによるフィルタリングやインデックスの結合も引き続き可能です。

**選ばなかった理由。** apt と `dnf` にとって、アップストリームの署名は、公開者に対するクライアントの唯一の検証手段です。検証せずに署名すると、不正なミラーが顧客のキーで署名されてしまいます。先に検証するには、アップストリームのキーを設定する場所が必要ですが、どの仕様でも設計していません。後の ADR で、中継の制約を修正して許可することはできます。

### 最初から KMS または HSM のキーを使う {#a-kms-or-hsm-key-from-the-start}

秘密キーがレジストリに入ることはありません。

**却下理由。** クラウドごとに独自のプロバイダーが必要であり、すべての署名が従量制のネットワーク呼び出しになります。署名機構のセクションで定めるとおり、KMS の署名機構には FIPS 140-3 証明書も必要です。署名機構の設計により、この選択肢は残します。

### 手書きの OpenPGP エンコーダー {#a-hand-written-openpgp-encoder}

レジストリに新しい依存先は増えず、すでに Cloud CDN URL 用の手書きの署名機構を保持しています。

**選ばなかった理由。** OpenPGP のフレーミングは、URL の署名よりはるかに大きく、独自のセキュリティレビューが必要です。これは、`go-crypto` がレビューを通過しなかった場合の代替策です。

### ECDSA P-256 または Ed25519 のキー {#ecdsa-p-256-or-ed25519-keys}

署名が小さくなります。

**却下理由。** Ed25519 は、サポートするクライアントリリースで失敗し、P-256 は、そのうち 1 つで警告が出ます。また、`go-crypto` は FIPS モジュールの外にある `circl` で Ed25519 に署名します。

### レジストリが RPM パッケージに署名する {#the-registry-signs-rpm-packages}

顧客の署名手順が不要になります。

**却下理由。** 署名のたびにブロブのハッシュが変わり、パッケージごとに署名機構の呼び出しが 2 回必要になり、アップロードの遅延が増えます。後から、そのコストを明記したオプトインとして追加することは可能です。
