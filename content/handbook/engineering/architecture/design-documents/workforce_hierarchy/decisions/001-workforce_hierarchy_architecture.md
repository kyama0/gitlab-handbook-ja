## 背景 {#context}

顧客は Workday などの HR システムで人員を組織化しています。GitLab のグループはその構造と一致しないため、
GitLab は、どのユーザーが顧客の組織のどの部分に属しているかを把握できません。

[設計ドキュメント](../_index.md)は、次の制約を定めています。

- セットアップ後は手作業なしで同期を実行します。
- 新しい HR ソースを追加しても、テーブルや API を変更しません。
- HR 上の人物を GitLab ユーザーに関連付け、管理者による上書きにも対応します。
- 利用側は、GraphQL と再利用可能なサービスを通じて階層を読み取ります。
- 統合は、GitLab.com、Self-Managed、Dedicated、およびエアギャップ環境のインスタンスで動作します。
- 階層はアクセス権を付与しません。
- 目標規模は、テナントごとに 50,000 人と 10,000 ユニットです。

## 検討した選択肢 {#options-considered}

| 選択肢 | 不採用または採用とした理由 |
| --- | --- |
| マネージャーを介して関連付けた人物のツリー（[MR 261107](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261107)） | 不採用です。指揮命令系統は頻繁に変わります。マネージャーによる 1 本のツリーでは、1 つの階層タイプしかサポートできません |
| **ユニットのツリーを、ユニットタイプごとに 1 本設ける** | **採用です。** ユニットは安定しています。自由記述のユニットタイプにより、スキーマを変更せずに複数の階層をサポートできます |
| Teams やグループをストレージとして使用する | 不採用です。どちらもアクセス権に関する意味を持ちます |
| **分離された読み取り専用の参照データ** | **採用です。** 権限チェックが読み取ることはないため、アクセス権を変更できません |
| 差分同期 | 不採用です。HR レポートは完全なスナップショットです |
| **日次の完全なスナップショットを取得し、変更された行のみを書き込む** | **採用です。** 各実行で自己修復できます。変更のない行は Siphon にイベントを送信しません |
| ClickHouse に先に取り込む | 不採用です。Rails は PostgreSQL 内の現在の状態を必要とします。第 2 の経路は Siphon と重複します |
| PostgreSQL に履歴を保存する | 不採用です。履歴の読み取りは ClickHouse が処理し、Siphon がすべての変更を配信します |
| **PostgreSQL に現在の状態を保存し、Siphon を通じて ClickHouse に複製し、ClickHouse に履歴を保持する** | **採用です。** Rails 内の取り込み経路とエクスポート経路をそれぞれ 1 つにします |
| [Integration Factory](https://gitlab.com/gitlab-org/orbit/experiments/glintf-design) | 現時点では採用しません。実験段階であり、これを使用して稼働している本番統合はありません。後で再評価できます |

## 決定 {#decision}

**ワークフォース階層は、ユニットの読み取り専用参照データです。ベンダーに依存しないソースから取得する日次の完全なスナップショットで
PostgreSQL を更新します。Siphon が PostgreSQL を ClickHouse に複製し、ClickHouse が履歴を保持します。GraphQL は ClickHouse から読み取り、
ClickHouse を利用できない場合は PostgreSQL の現在の状態を読み取ります。**

### 目的と命名 {#purpose-and-naming}

- 階層は参照データです。プリンシパルでもコンテナーでもありません。グループや
  [Teams](../../teams/_index.md)とは分離します。
- コードは `Workforce` 名前空間を使用します。ワークフォースの概念には、
  [Organizations](../../organization/_index.md)との混同を避けるため、「organization」という名前を使用しません。

### テナント {#tenant}

- GitLab.com ではルートグループ、Self-Managed と Dedicated では組織をテナントとします。
- GitLab.com も後に組織をテナントとして使用するように移行します（[ワークアイテム 634509](https://gitlab.com/gitlab-org/gitlab/-/work_items/634509)）。
- テナントは 1 つのソースを持ちます。複数のワークフォース階層を持てますが、ユニットタイプごとには最大 1 つの階層となります。
- 統合はテナントレベルでのみ設定します。サブグループやプロジェクトには伝播しません。

### データモデル {#data-model}

テーブルは `gitlab_main_org` 内で `workforce_` プレフィックスを使用し、テナントをシャーディングキーとします。

| エンティティ | 属性 |
| --- | --- |
| 階層 | テナント、統合、ユニットタイプ、最終同期のステータスと日時 |
| ユニット | 外部 ID、名前、タイプ、親、祖先パス、マネージャーの外部 ID、マネージャーのユーザー |
| 人物 | 外部 ID、氏名、照合されたユーザー |
| ユニットのメンバーシップ | 人物、ユニット、タイプ |
| 不備 | 対象種別、理由、ロケーター。最新の実行分のみ |
| ID の上書き | 人物の外部 ID、ユーザー |

- ユニットタイプごとに、ユニットのツリーを 1 本設けます。人物はタイプごとに最大 1 つのユニットに所属します。ユニットは最大 1 人のマネージャーを持ちます。
- ユニットタイプは自由記述です。コストセンターなどの新しいタイプを追加しても、スキーマの変更は不要です。
- 階層は、1 つのユニットタイプに属するユニットを保持します。テナントは、ユニットタイプごとに最大 1 つの階層を持ちます。
- テナントは 1 つのソースを持つため、1 回の同期実行でテナントのすべての階層を更新します。
- ユニットの親は同じタイプです。バッチの合間も含め、ストアに循環が存在することはありません。
- 祖先パスは [`traversal_ids`](https://docs.gitlab.com/development/namespaces/)と同様に機能し、サブツリーを
  1 回の範囲スキャンで取得できます。
- 人物のマネージャーは保存しません。マネージャーを持つのはユニットのみです。
- ユーザーを削除すると、関連付けを解除し、そのユーザーの ID の上書きを削除します。人物とメンバーシップは残ります。
- ID の上書きは、人物の行ではなく、人物の外部 ID を参照します。人物がスナップショットに含まれなくなっても残り、
  その人物が再び現れたときに適用します。

### ソース {#sources}

すべてのソースは、ベンダーに依存しない共通の契約を実装します。ソースは、ユニット（ID、名前、親 ID、マネージャー ID）と
人物（ID、名前、業務用メールアドレス、タイプごとのユニット ID）を返します。

1. **Workday RaaS API。** 顧客が作成する 2 つのレポートです。Integration System User の OAuth 2.0 リフレッシュトークンを使用します。
   顧客は、レポートで公開する列を制御します。
1. **Workday RaaS ファイル。** エアギャップ環境のインスタンス向けに、同じレポートをアップロードします。ファイル形式はプロバイダーによって異なるため、
   各ファイルインポートは特定のプロバイダーに結び付きます。

### 同期 {#sync}

- 日次で実行し、手動トリガーにも対応します。テナントごとに同時に実行できるのは 1 回です。GitLab.com のみ、手動実行に 30 分のクールダウン期間を設けます。
- 最初に完全なスナップショットを取得して検証します。失敗した場合は何も変更しません。
- ソースが信頼できる唯一の情報源です。完全かつ有効なスナップショットは、人物やユニットの大部分を削除する場合でも、
  受け取ったとおりに適用します。誤ったスナップショットから復旧するには、ソースを修正して手動同期を開始します。
- 最大 5,000 行のバッチで適用し、ユニットをルートからリーフの順に処理した後、人物、メンバーシップの順に処理します。削除は最後に行います。
  スナップショット全体にまたがるトランザクションはありません。実行を再開すると、同じ状態に収束します。
- 変更のない行は書き込まないため、Siphon はその行に関するイベントを受け取りません。
- 無効な行は、下の表のとおり不備として記録します。実行自体は成功します。
- ログには、テナントと実行の識別子、および件数を記録します。個人データは記録しません。

| 無効な行 | 結果 |
| --- | --- |
| ID が欠落または重複している人物やユニット | その行を除外します |
| 親が不明、または親子関係が循環しているユニット | ユニットは親を持たない状態で残り、ルートになります |
| マネージャーが人物データに存在しないユニット | ユニットはマネージャーを持たない状態で残ります |
| ユニットが空か、不明なユニットが指定された人物 | 人物は、そのタイプのメンバーシップを持たない状態で残ります |
| 別の人物と同じ業務用メールアドレスを持つ人物 | 人物は未照合のまま残ります |

不備は読み取り結果に表示しません。実行開始時に不備を消去し、終了時に書き込みます。

### ID の照合 {#identity-matching}

- 照合には、差し替え可能な戦略を使用します。
- 候補は、テナントのユーザーのみです。GitLab.com ではルートグループ階層のメンバー、それ以外では
  組織のアクティブなユーザーです。
- 最初の戦略は、業務用メールアドレスと GitLab の確認済みメールアドレスの照合です。メールアドレスは永続化もログへの記録もしません。
- 管理者による上書きは、人物の外部 ID をキーとして保存します。戦略より優先し、同期をまたいで保持します。
- 未照合は正常な状態であり、不備ではありません。

### ストレージと履歴 {#storage-and-history}

- PostgreSQL は現在の状態を保持します。取り込みは引き続き Rails で行います。
- Siphon がテーブルを ClickHouse に複製します。第 2 のエクスポート経路は設けません。
- ClickHouse が履歴を構築します。方法はまだ定義していません。後に別の決定で、
  たとえば 緩やかに変化するディメンション（SCD）の仕組みを使う方法を定義できます。

### 読み取り API {#read-api}

GraphQL はユニットごとに、名前、タイプ、親、マネージャーのユーザー（未照合の場合は `null`）、直接のメンバー、および
子孫を含むメンバーを返します。メンバーは GitLab ユーザーです。

- 任意で時点を指定すると、過去の状態を選択できます。デフォルトは現在の状態です。
- ClickHouse がある場合、すべての読み取りに ClickHouse を使用します。現在の状態は、Siphon のレプリケーション遅延の分だけ PostgreSQL より遅れます。
- ClickHouse がない場合、PostgreSQL の現在の状態を読み取ります。特定時点の読み取りはエラーを返します。
- リゾルバーは再利用可能なサービスを呼び出します。ほかの機能からも、そのサービスを直接利用できます。
- すべての読み取りで認可を行います。
- HR の識別子、HR 上の人物名、メールアドレス、未照合の人物は返しません。
- 読み取り専用です。目標規模において、メンバーを含むサブツリーを 1 ページあたり 100 ms 未満で取得します。

### データ保護 {#data-protection}

- 保存する HR 属性は、[データモデル](#data-model)にあるものだけです。
- 統合は、OAuth 2.0 リフレッシュトークンなど、ソースの設定と認証情報を保存します。
  認証情報は保存時に暗号化します。
- 統合を削除すると、テナントのすべての階層データをバッチで削除します。無効化した場合はデータを保持します。
- 統合と上書きの変更は監査します。
- 履歴の保持と消去は、履歴に関する別の決定で定義します。

## 結果 {#consequences}

### 利点 {#positive}

- 新しいソースやユニットタイプを追加しても、テーブルや API を変更しません。
- 完全なスナップショットを適用するたびに、過去の失敗した実行や部分的な実行の結果を修復します。
- Siphon が唯一のエクスポート経路です。変更のない行は、レプリケーションや履歴に負荷を加えません。
- エアギャップ環境のインスタンスでも、ファイルインポートにより同じデータを取得できます。
- 権限チェックが階層を読み取ることはないため、階層がアクセス権を変更することはありません。

### 欠点 {#negative}

- 管理者が手動同期を開始しない限り、HR の変更が GitLab に反映されるまで最大 1 日かかります。
- 変更された行が少ない場合でも、実行のたびに完全なスナップショットを取得して検証します。
- スナップショット全体にまたがるトランザクションはありません。実行中は、部分的に適用されたスナップショットが読み取り側に見える場合があります。
- ソースからのスナップショットが誤っていても有効であれば、修正済みのスナップショットが同期されるまで、人物やユニットが削除されます。
- ClickHouse がある場合、現在の状態は、Siphon のレプリケーション遅延の分だけ PostgreSQL より遅れます。
- ClickHouse がない場合は履歴がなく、特定時点の読み取りはエラーを返します。
- 一致する確認済み GitLab メールアドレスがない人物は、管理者が上書きを追加するまで未照合のままになります。
- テナントは複数のソースを組み合わせることができません。
- 履歴の振る舞いは、まだ記述されていない別の決定に依存します。
