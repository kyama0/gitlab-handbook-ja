## 概要 {#summary}

GitLab は、単一のドメイン（`gitlab.company.com`）の背後でモノリスとして提供されます。
Duo Chat や Work Items などの製品領域は、
モノリスのビルドとリリースのサイクルに密接に結合しています。この設計
ドキュメントでは、製品領域を独立して
開発、ビルド、バージョン管理、デプロイできるマイクロフロントエンド（MFE）プラットフォームを提案します。
エンドユーザーには違いが見えず、すべてが 1 つのドメインと 1 つの
ログインの背後に留まります。

## 動機 {#motivation}

### 問題 {#problems}

- **モノリスへの結合。** フロントエンドの変更は、どんなに小さくても、
  モノリス全体のリリースが必要です。Duo Chat の 1 行の修正も、
  データベースマイグレーションと同じパイプラインを待ちます。
- **チーム間の結合。** すべてのチームが 1 つの Webpack 設定、1 つの依存関係
  ツリー、1 つの CI パイプラインを共有します。ある領域でリントチェックが失敗すると、
  すべてのデプロイが阻まれます。
- **独立したバージョン管理がない。** 単一の製品領域だけをアップグレードまたは
  ダウングレードする仕組みがありません。ロールバックには、
  モノリス全体のロールバックが必要です。
- **外部モジュールに UI を提供する経路がない。** LabBench モジュール（個別に
  デプロイされるサービス）には、GitLab のシェルに UI を組み込む標準的な方法が
  ありません。各モジュールが独自の統合方法を考案しています。

### 目標 {#goals}

1. 製品チームが、モノリスをリリースせずに、自分たちの領域の UI 変更を
   デプロイできます。
2. MFE の複数のバージョンが共存できます。アップグレードとダウングレードは、
   バージョンを選択して行います。
3. セルフマネージド環境とエアギャップ環境のインストールは、すでに利用しているものと同じ
   リリースチャネルを通じて MFE を受け取ります。

### 対象外 {#non-goals}

- **単一ドメインのルーティング（GATE）。** モジュールを
  1 つのドメインの背後に配置するルーティング層は GATE プロジェクトが所有し、独自のスケジュールを持ちます。
  GATE が利用可能になるまでは、モノリスにマーケットプレイスの
  URL を設定し、そのオリジンを CSP に追加します。
- **モジュールの検出。** モノリスは、どの LabBench
  モジュールがデプロイされているかをまだ検出できません。当面、マーケットプレイスの場所はモノリスの設定で
  指定します。
- **特定の製品領域の移行。** 各領域は引き続きプラットフォームの利用側であり、
  所有するチームで追跡します。このドキュメントは
  プラットフォームを扱い、移行は扱いません。

### 現在の制約 {#constraints-today}

- **単一ドメインがまだない。** GATE がすべてのデプロイ
  方式（Omnibus から Kubernetes まで）のルーティングを提供するまでは、モノリスに
  マーケットプレイスの URL を設定し、そのオリジンを CSP に追加して、そこから MFE を
  埋め込めるようにします。
- **モジュールを検出できない。** モノリスは、どのモジュールが
  デプロイされているかを検出できません。マーケットプレイスの場所はモノリスの設定で指定し、
  マニフェストは検出なしで機能する必要があります。

## 決定事項 {#decisions}

- [ADR 001: ツールのリポジトリ戦略](decisions/001_tooling_repository_strategy.md) -
  密接に結合したツールにはモノレポ、独立したユーティリティにはポリレポを使用します。
  MFE アプリケーションコードをどこに置くかという未解決の問いも記載しています。
- [ADR 002: 再利用可能なテストのアプローチ](decisions/002_reusable_testing_approach.md) -
  モノリス、MFE、LabBench モジュールで共有する、ユニット、統合、
  ブラウザー駆動の各レイヤーを備えた単一の `@gitlab/frontend-tests` パッケージです。
  2026-11-18 の改訂で、テストは `@gitlab/mfe-shell` を通じてマウントし、ホスト側は
  マーケットプレイスのインデックスに従い、`mfe-scripts create` でセットアップのひな形を生成することになりました。
- [ADR 003: モジュールに含めるパッケージ化と配信](decisions/003_module_carried_packaging_and_serving.md) -
  LabBench モジュールは、単一のソースプロトコルを介して MFE を提供します。モノリスは
  カタログを取得し、自身のオリジンから配信します。モジュールは、モノリスが所有する
  語彙の範囲内で配置場所を宣言します。
- [ADR 004: パッケージのライフサイクル](decisions/004_packages_group_and_shared_setup.md) -
  再利用可能なパッケージは `gitlab-org/frontend/toolkit` に置き、
  `@gitlab/frontend-config` を通じてセットアップを共有し、
  公開、保守、廃止に関する共通のプロセスに従います。ADR 001 のツール用
  モノレポを単一のパッケージに改めます。

- [ADR 005: MFE アプリ間の通信](decisions/005_mfe_inter_app_communication.md) -
  MFE アプリケーション間の通信は先送りにします。プラットフォームが扱うのは、シェルと MFE の間の
  通信だけです。通信チャネルや共有状態のソリューションを追加する前に、
  `#g-ui_platform` で新しい要望を提起してください。

- [ADR 006: マウント契約 v1 とその拡張性](decisions/006_mount_contract.md) -
  ADR 003 で未定義だったマウント契約を確定します。6 つの `MountProps` キー、マニフェストが宣言しホストが提供するクライアントとフィーチャーフラグ、名前空間付きのケイパビリティ ID、利用側を壊さずに契約を拡張するためのメジャー/マイナーのルールを定めます。
- [ADR 007: オブジェクトストレージ上の静的なプル型ソースとしてのマーケットプレイス](decisions/007_marketplace.md) -
  専用のモジュールを持たないマイクロフロントエンドに、GitLab が運用する単一のソースを用意します
  （UI を持つモジュールは自ら UI を配信します。ADR 003）。レビュー済みで追記専用のロックファイルが
  すべてのバージョンをダイジェストで固定し、単一の公開プロセスがバージョンごとに不変のオブジェクトを書き込み、各インスタンスが取得します。
  最終的なバックエンドはオブジェクトストレージで、移行期には GitLab Pages を使います。
  ソースへの書き込みに必要な 12 の対策を定めます。
- [ADR 008: バージョン選択とインスタンスごとのオーバーライド](decisions/008_version_overrides.md) -
  開発サーバー、インスタンスのオーバーライド、ソースのデフォルトの順に解決します。
  オーバーライドは `mfe_version_overrides` に保存し、変更は管理者 REST API を通じてのみ行い、サーバー側で再検証して監査イベントを記録します。
  Sidekiq の定期ジョブがカタログを最新に保ち、単一の判定メソッド `Renderable.can_render?` がすべての画面でレンダリングの可否を決めます。
- [ADR 009: ホストランタイムの管理責任](decisions/009_host_runtime.md) -
  `@gitlab/mfe-shell` は、モノリス、開発用ホスト、テストのすべてで使う唯一のホストランタイムです。
  モノリスにはアプリケーション名を持たないアダプターを置きます。
  `runtimeFactory` を差し替えられる設計にしておくことで、契約を変更せずにビルド時に統合するホストも実現できます。
- [ADR 010: ひな形生成の責務](decisions/010_scaffolding.md) -
  `@gitlab/mfe-scripts create --into` がすべての構成でフロントエンドのひな形を生成し、
  `mfe-scripts source` がモジュールの配信用ソースを構成します。
  リポジトリジェネレーターと LabBench は、個別のテンプレートを保持せず、バージョンを固定したコマンドに委譲します。
  検証ツールと CI テンプレートはそれぞれ 1 つです。ADR 004 の「新しいパッケージをどう作成するか？」をアプリケーション向けに具体化し、ADR 004 からもこの ADR を参照します。
- [ADR 011: 国際化](decisions/011_internationalization.md) -
  各 MFE は英語の原文をキーとする vue-i18n カタログを所有し、CI を通じて `gitlab-ee` とは別の単一の共有
  Crowdin プロジェクトに文字列を送り、翻訳を取り込みます。移植した文字列にはモノリスの翻訳を引き継ぎ、
  翻訳を変更できる人は段階的に制限します。新しい文字列を誰が翻訳するかは、ローカリゼーションチームと引き続き検討します。

## MFE としての抽出に向けてアプリケーションを準備する {#preparing-your-application-for-mfe-extraction}

モノリス内のフロントエンド領域を所有するチームは、現在から MFE と互換性のある
パターンに近付けることで、将来の移行コストを減らせます。
これらの手順は、いずれも MFE プラットフォームの完成を前提とせず、
それぞれが独立してコードベースを改善します。

### 共有ユーティリティを抽出する {#extract-shared-utilities}

純粋で再利用可能な関数を、モノリスから
[`@gitlab/frontend-utils`](https://gitlab.com/gitlab-org/frontend/utils)へ移します。
アプリケーションが抱えるモノリス内部からのインポートが少ないほど、
抽出時に切り離す範囲が小さくなります。すでに移行済みの例には、
`parseBoolean` と `normalizeHeaders` があります。

### テストカバレッジを統合テストに移す {#shift-test-coverage-to-integration-tests}

コンポーネントをマウントし、依存関係をすべてモック化するユニットテストは、
テストスイートを内部実装に結合させます。レンダリング結果を通じて
ユーザーに見える動作を確認する統合テストは移植可能であり、アプリケーションがモノリス内で動作しても単独で動作しても、
テストは同じように機能します。
フィクスチャ、MSW リクエストハンドラー、Jest 設定などの共有テスト基盤には、
[`@gitlab/frontend-tests`](https://gitlab.com/gitlab-org/frontend/tests)を使用し、
両方の環境で同じテストインフラストラクチャが機能するようにします。

### HAML からのデータ注入を最小限にする {#minimize-haml-data-injection}

HAML から Vue のマウントポイントに渡す `data-*` 属性は、1 つひとつが Rails のレンダリングレイヤーとの結合点です。マウント時の入力を最小限に保ち、代わりに API 呼び出しを利用してください。マウント契約は、[ADR 006](decisions/006_mount_contract.md)で確定しています。ホストが渡すのは、ページのリソース、宣言されたクライアント、配置の props、宣言されたフィーチャーフラグ、設定、サービスだけです。プロジェクトパス、フィーチャーフラグ、ユーザー権限などの情報について、サーバーがレンダリングする HTML 属性への依存が少ないほど、アプリケーションを抽出しやすくなります。

### リソースの種類による分岐を減らす {#move-away-from-resource-kind-checks}

現在、多くのアプリケーションは HAML から `isGroup` や `isProject` などのフラグを受け取り、それを使って分岐します。
たとえば、グループとプロジェクトでクエリを切り替えたり、場所に応じて異なる形式の URL を組み立てたりします。
モノリスでは、ページがレンダリング対象を常に把握しているため、この方法が機能します。アプリケーションを抽出すると、
この前提は成り立ちません。ホストが渡す `context.resources` は、アプリケーションが**どこに**マウントされるか
（グループやプロジェクトのパス）を伝えますが、リソースの**種類**は伝えません。

[ADR 006](decisions/006_mount_contract.md)では、
リソースの種類を契約の明示的な項目に含めない理由を説明しています。契約に含めると、現在ある `isGroup` を使った
すべての分岐に公式の入力元ができ、アプリケーションが読み取るようになった契約フィールドは削除しにくくなります。
今後、組織など名前空間の種類が増えると、種類による分岐の一つひとつが、後で見直す必要のある結合点になります。

そのため、種類を確認する箇所には、抽出後に新たな入力が必要です。ただし、こうした確認のほとんどは、実際には
「グループかどうか」を知るためのものではありません。別の問いに答える近道として種類を使っており、通常は API から
その答えを直接得られます。こうした分岐を今のうちに API の応答を使う形に変えれば、アプリケーションの抽出時に
その依存関係を解消する作業が不要になります。

これを可能にするのが `namespace(fullPath)` クエリです。グループとプロジェクトのどちらのパスも受け付けるため、
アプリケーションは受け取ったパスの種類を知らなくても、同じクエリを使えます。

#### 権限 {#permissions}

よくあるパターンとして、`isGroup ? canAdminGroup : canAdminProject` のように、種類に応じて確認する権限を
選びます。コードが実際に必要とするのは、現在のユーザーがその操作を実行できるかどうかです。
`namespace.userPermissions` では操作ごとに可否を確認できます。コンポーネントは必要な権限を直接問い合わせられるため、
リソースの種類を確認する必要がなくなります。

#### リンク {#links}

グループのルートは `/groups/` 以下にあり、プロジェクトのルートはそうではないため、URL を手作業で組み立てるのも
よくあるパターンです。API はどの名前空間についても `webPath` と `webUrl` を返すため、URL の形式は API に任せます。
そうすれば、ルーティングが変わってもアプリケーションを変更せずに済みます。

#### クエリ {#queries}

一部のコンポーネントは `groupFooQuery` と `projectFooQuery` を持ち、種類に応じて一方を選びます。
同じデータを `namespace(fullPath)` のフィールドで取得できる場合は、そのフィールドを使い、
2 つのクエリを 1 つにまとめます。

最初の 2 つを組み合わせた例です。

```graphql
query namespaceContext($fullPath: ID!) {
  namespace(fullPath: $fullPath) {
    webPath
    userPermissions {
      adminLabel
    }
  }
}
```

```javascript
// Before
const homePath = isGroup ? `/groups/${fullPath}` : `/${fullPath}`;
const canManageLabels = isGroup ? canAdminGroup : canAdminProject;

// After
const homePath = namespace.webPath;
const canManageLabels = namespace.userPermissions.adminLabel;
```

#### API でまだ対応できない場合 {#when-the-api-has-no-answer-yet}

グループとプロジェクトで別々のクエリしか用意されていない検索など、一部の分岐はまだ置き換えられません。
この場合に不足しているのは API の機能です。アプリケーション側で個別の回避策を実装するのは避けてください。
こうしたケースを見つけたら、対応に着手できるようチームに共有してください。それまでは、分岐を共有状態や
マウント時の入力に置かず、必要とするコンポーネント内に留めてください。API が対応したときに
分岐を見つけて削除しやすくなります。

リソースの種類の確認が現時点でどうしても必要な場合、技術的には、独自の配置用 props を通じてホストから
フラグを渡せます。推奨はしません。フラグは契約の対象外なので、プラットフォームはテストもサポートもせず、
その依存関係はアプリケーション側が管理します。API の機能が充足するまでの暫定措置とし、
ほかの実装で踏襲するパターンにはしないでください。

## 代替案 {#alternative-solutions}

### 何もしない {#do-nothing}

製品領域はモノリスのリリースサイクルに結合したままになります。チームは
独立してデプロイできません。外部モジュールには標準的な UI の提供経路がありません。
Vue 3 の採用には、モノリス全体の移行が必要です。

**利点:** 新しいインフラストラクチャを構築、運用する必要がありません。

**欠点:** チームと領域の数が増えるほど、
結合によるコストが増大します。

### iframe {#iframes}

各領域を、モジュール独自のドメインを指す iframe に読み込みます。

**利点:** 強力に分離されます。JavaScript のスコープを共有しません。
**欠点:** UX が低下します（共有ナビゲーションがなく、スクロールバーが二重になり、
postMessage なしでは認証を共有できません）。アクセシビリティと
パフォーマンスに悪影響があります。「1 つのドメイン」という要件を満たしません。

### ビルド時の統合（npm パッケージ） {#build-time-integration-npm-packages}

各領域を npm パッケージとして公開し、モノリスの
Webpack ビルドにコンパイルして組み込みます。

**利点:** ランタイムフェデレーションのオーバーヘッドがありません。ビルドグラフが 1 つです。
**欠点:** 独立したデプロイやロールバックを実現できません。領域の変更には、
引き続きモノリスのリリースが必要です。外部モジュールには役立ちません。
