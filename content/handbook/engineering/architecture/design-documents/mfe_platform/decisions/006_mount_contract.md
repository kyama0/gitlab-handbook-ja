## 背景 {#context}

ADR 003 §7 では、マウント契約は未定義のままでした。各 expose は `mount(el, props)` と `unmount(el)` をエクスポートし、ページ上のすべてのアプリケーションに 1 つの Module Federation ランタイムを使い、GitLab が注入するクライアントを構築します。ただし、ホストが*何を*注入するか、アプリケーションが必要なものを宣言するかどうかは、2 つ目の利用側ができるまで先送りしていました。

その段階に達しました。今、契約を明文化するのは、ある程度複雑なアプリケーションなら必要になる、次の 3 つの要件があるためです。

- **ページに属する GraphQL クライアント。** GitLab にクエリするアプリケーションは、ページの Apollo キャッシュと単一の ActionCable コンシューマーを共有する必要があります。アプリケーションごとに 2 つ目のクライアントを用意すると、サブスクリプションが倍増し、キャッシュが分かれます。
- **ページのスコープの把握。** 大半の機能は、プロジェクトまたはグループに作用します。ホストは、ページがどのリソースを対象としているかを知っています。アプリケーションは知らず、調べるために DOM や `gon` をスクレイピングしてはいけません。
- **範囲を限定したインターフェース。** プロトタイプでは、アプリケーションの API プロキシに紐付けた、生の `axios` インスタンスを渡していました。記録された懸念（gitlab-org/gitlab#634099）は、「シェルがすべてを与え、アプリケーションが必要なものを取る」方式が、HAML のデータ属性の無制御な増大を繰り返すことです。アプリケーションが読み取れるページの情報は、すべてホストが永続的に維持しなければならない契約です。
- **別経路に頼らないフィーチャーフラグ。** アプリケーションのコードは、モノリスのコードと同じように GitLab のフィーチャーフラグで分岐します。フラグをスロットの props として 1 つずつ転送したり、アプリケーションに `gon.features` を読み取らせたりすると、ページの情報と同じ、範囲の定まらないインターフェースになります。ホストは、アプリケーションがどのフラグに依存するかを把握できず、フラグの名前変更や削除で、アプリケーションの動作が気付かれずに変わります。

### 制約 {#constraints}

- マニフェスト（ADR 003）は、すでにアプリケーションの宣言のためのインターフェースであり、2 つ目の宣言の仕組みを作ってはいけません。
- ホストは現在 GitLab モノリスですが、将来は独立した開発用ページになる可能性があります。契約にモノリスの内部構造を漏らしてはいけません。
- アプリケーションはすべての GitLab ユーザーに配信するため、ホストはアプリケーションのコードを実行する前に、マウントを拒否できる必要があります。
- Vue 2 と Vue 3 のページが同じランタイムをホストします。契約はフレームワークに依存しません。

## 決定事項 {#decisions}

### 1. `MountProps` の構造 {#1-the-shape-of-mountprops}

各 expose は、`mount(el: HTMLElement, props: MountProps): void | Promise<void>` と `unmount(el: HTMLElement): void` をエクスポートします。`MountProps` は、次の 6 つのキーだけを持ち、呼び出し前にホストがすべてを凍結します。

| キー | 内容 | 設定するもの |
| --- | --- | --- |
| `context` | `resources`：`{ id, fullPath }` の GID として表したページのリソース。最も外側から順に並べます（グループ、次にプロジェクト）。`basePath`：アプリケーションをマウントする URL プレフィックス | ページに基づいてホストが設定 |
| `clients` | マニフェストが宣言し、**かつ**ホストが提供するクライアントのみを遅延構築します。`http`、`graphql`（安定版）、`moduleApi`（実験的） | ホスト |
| `props` | この配置に対応するマニフェストの `placement[].props` を、スロット自身の props で上書きしたもの | マニフェスト、次にホスト |
| `features` | マニフェストが宣言する各フィーチャーフラグについて、ホストがこのリクエストに対して評価した真偽値（決定 3） | ホスト |
| `preferences` | `locale`（`Gitlab::I18n` のコード）と `theme`（`light` または `dark`） | ホスト |
| `services` | `reportError(error, context?)` と `track(event, data?)` | ホスト |

それ以外は何も渡しません。契約に含まれないページの情報を必要とするアプリケーションは、契約のマイナーバージョン更新を提案します（決定 5）。DOM や `gon` を読み取りません。

### 2. クライアントは検出せず、宣言する {#2-clients-are-declared-not-discovered}

マニフェストの `clients` 配列は、アプリケーションが必要とするものを指定します。ホストは、アプリケーションが初めてそのクライアントを読み取ったときに、自身のインスタンスからクライアントを生成します。

- `http`：GitLab API 向けの、ホストの認証済み HTTP クライアントです（モノリスでは axios インスタンスであり、CSRF と認証情報はホストが提供します）。
- `graphql`：すぐに使用でき、ページのキャッシュと ActionCable リンクを共有する、ホストの **Apollo クライアントインスタンス**です。アプリケーションは、その `query`、`mutate`、`watchQuery`、`subscribe` を呼び出し、`cache` は不透明なものとして扱います。独自の `ApolloClient` を構築したり、独自のリンクでインスタンスをラップしたり、バージョン固有のキャッシュ API に依存したりしてはいけません。アプリケーションがホスト提供のリンクファクトリーから自身のクライアントを組み立てる代替案は、アプリケーションごとに 2 つ目のキャッシュと 2 つ目の Cable コンシューマーを再び導入してしまうため、却下しました。
- `moduleApi`（マニフェストでは `module_api`）：GitLab のオリジンを通じてプロキシする、アプリケーション自身のモジュール API に紐付けた HTTP クライアントです。これは**実験的**です。プロキシがユーザーのアイデンティティを転送しないため、モノリスでは `mfe_module_api_proxy` フラグの背後でのみ提供し、GitLab.com では無効のままにします。AUTH-021 で追跡するアイデンティティの作業とともに、安定版に昇格します。

宣言したクライアントをホストが提供しない場合は、`client_unavailable` でマウントを拒否します。
宣言していないクライアントは、単に `clients` に存在しません。

### 3. フィーチャーフラグはページから読まず、宣言する {#3-feature-flags-are-declared-not-read-from-the-page}

マニフェストの `features` 配列には、アプリケーションのコードがその値で分岐する GitLab のフィーチャーフラグを、フラグの定義名で列挙します（YAML 定義と同じ `duo_chat_redesign` など。ホストは大文字小文字を変換しません）。ホストは、アプリケーションをレンダリングするリクエストごとに、宣言された各フラグが現在のユーザーまたはページのいずれかのリソースに対して有効かどうかをサーバーで評価し、結果を `features` で渡します。レコードは凍結し、宣言された名前だけを持ちます。アプリケーションが宣言しなかったフラグは存在せず、アプリケーションはフラグを得るために `gon.features`、`glFeatures`、DOM のいずれも読み取りません。

宣言されたフラグにホスト側の定義がなければ `false` と評価し、カタログは警告問題 `unknown_feature`（ADR 008）を記録するため、管理者は、フラグの削除後も残った宣言を確認できます。これは拒否ではありません。フラグは計画に従って削除するため、削除済みのフラグによってアプリケーションが停止してはいけません。作成側は、フラグ削除後のリリースで宣言を削除します。

アプリケーションを画面にレンダリングするかどうかを決めるフラグ（プラットフォーム自身のフラグや機能の展開フラグ）は、ホストの担当であり、宣言しません。`features` に含めるのは、アプリケーション自身が分岐に使うものだけです。独立した開発用ホストは、自身の設定からこれらを設定します。

### 4. ケイパビリティと語彙は別の名前空間にする {#4-capabilities-and-vocabulary-are-separate-namespaces}

- マニフェストの `requires` は、所有者で名前空間を分けた**ケイパビリティ ID**を列挙します（1.0 で存在するのは `shell.history` だけです。`navigation` と `route` の配置に許可し、スロットには許可しません）。シェルは、リモートを読み込む前に、`unknown_requirement` と `requirement_not_granted` を拒否します。
- 配置の語彙（パネル、props やイベントを持つスロット、権限の語）は、ADR 003 §4 の決定どおり、ホストが所有します。`admin` などの権限の語は、ケイパビリティではありません。配置をレンダリングするかどうかを決めます。

### 5. バージョン管理と拡張性 {#5-versioning-and-extensibility}

- 契約の**メジャー**バージョンは、マニフェストの `schema` 番号です。1.0 はこのドキュメントです。
- **マイナー**バージョンでは、クライアント、ケイパビリティ ID、語彙のエントリ、`services` のメソッドを追加でき、実験的な ID を安定版に昇格できます。削除や名前変更は行いません。
- ホストは、認識する ID のレジストリ（`@gitlab/mfe-shell/contract` に同梱する `capabilities.v1.json` と `vocabulary.v1.json`）を保持します。`mfe-scripts validate` は、同じファイルに対してマニフェストを検証するため、作成側は、本番ではなく CI で未知の ID を知ります。
- 拒否コードも契約の一部です。`unknown_requirement`、`requirement_not_granted`、`unknown_client`、`client_unavailable`、`duplicate_version`（ページに同じアプリケーションの 2 つのバージョンがある場合）があります。ホストは、これらをマウント要素にレンダリングし（`data-mfe-state="refused"`）、`reportError` を通じて報告します。

### 6. アプリケーションごとに 1 つのランタイムと 1 つのスコープ {#6-one-runtime-one-scope-per-application}

1 つの Module Federation ランタイムが、ページ上のすべてのアプリケーションに対応します（ADR 003 §7）。ホストは、クラス `.mfe-<name>` と、`data-mfe-app`、`-version`、`-source`、`-state` をマウント要素に追加します。アプリケーションの CSS には、ビルド時にそのクラスをプレフィックスとして付けます（ADR 003 §8）。`unmount` は要素を空にする必要があり、まだマウント中の要素に 2 回目の `mount` を行うと例外を送出します。

## 検討した代替案 {#alternatives-considered}

- **「シェルがすべてを与える」。** ページのすべての情報を持つ単一のコンテキストオブジェクトです。却下理由：HAML 時代のデータ属性の乱立を再現し、すべての追加が、気付かれない契約変更になります（gitlab-org/gitlab#634099）。
- **ホスト提供のリンクファクトリーから構築する、アプリケーションごとの Apollo クライアント。** 却下理由：ページごとにキャッシュが 2 つになり、ActionCable のサブスクリプションが倍増する一方、ホストのインスタンスを使う場合に対する利点はありません。
- **スロットの props や `gon.features` から取得するフィーチャーフラグ。** 却下理由：ホストは、アプリケーションがどのフラグに依存するかを把握できず、新しいフラグのたびに場当たり的な prop が増え、名前変更や削除をしたフラグが、誰も気付かないまま消えます。
- **自由形式の文字列としてのケイパビリティ。** 却下理由：所有者の名前空間とレジストリがなければ、タイポが本番に入り、CI ではなく実行時に失敗します。

## 影響 {#consequences}

- 契約を通じてマウントするアプリケーションは、独自の GraphQL クライアント、HTTP クライアント、コンテキストを受け渡す仕組みを持ちません。ホストが、プロジェクトやグループを `context.resources` で渡します。
- アプリケーションのフィーチャーフラグへの依存はマニフェストで確認できます。ホストは、リクエストごとに 1 回評価し、フラグ削除後も残った宣言は、黙って `false` にするのではなく報告します。
- 新しいページの情報やクライアントは、場当たり的な prop ではなく、レジストリエントリ、バリデーターのルール、変更履歴の行を伴う、明示的な契約のマイナーバージョン更新になります。
- 独立した開発用ホストは、自身の設定から 6 つのキーを提供することで、契約に準拠した任意のアプリケーションをマウントできます。
- `module_api` クライアントは実験的な状態で提供します。それを必要とする機能は、アイデンティティを転送する作業が取り込まれるまで、GitLab.com で有効にできません。

## 後のマイナーバージョンで検討する事項 {#open-for-a-later-minor}

- GraphQL のサブスクリプションではなく、生のチャネルが必要なアプリケーション向けの WebSocket または ActionCable クライアント。
- 配信経路（ADR 003 §3）が、すでに検証しているダイジェストを公開した後の、リモートエントリの Subresource Integrity。
- 利用側が必要としたときの、より豊富な `preferences`（タイムゾーン、週の開始曜日）。
