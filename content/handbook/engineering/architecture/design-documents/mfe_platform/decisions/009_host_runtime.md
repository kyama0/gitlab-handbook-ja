## 背景 {#context}

ADR 003 の第 7 節では、ページ上のすべてのアプリケーションを 1 つの Module Federation ランタイムで処理し、
注入するクライアントは GitLab が構築すると定めています。ADR 006 では、マウント時にホストが何を渡し、
どのようにマウントを拒否するかを確定しています。どちらも、**この処理を行うコードを誰が管理するか**には触れていません。

この問いを放置すると、好ましくない形で答えが決まってしまいます。マイクロフロントエンドを埋め込む各画面
（管理ページ、ページスロット、機能パネル）に、最初に必要としたアプリケーションに合わせた個別の
マウントコードが生まれます。プラットフォームの契約は文書上（ADR 006）では 1 つでも、コード上では
複数になります。すると、提供側はモノリス、ローカル環境、テストでそれぞれ異なるホストをデバッグする
ことになります。

### 制約 {#constraints}

- 同じアプリケーションは、モノリス、スタンドアロンの開発用ホスト、テストのすべてで同じように
  マウントできる必要があります。
- モノリスでは、本番と開発の両方で Rspack を使ってビルドと配信を行い、フォールバック用に webpack 4 の設定を、
  オプトイン用に Vite の経路を維持し、テストには Jest を使います。ホストランタイムは特定のバンドラーの
  フェデレーションプラグインに依存できません。
- ADR 006 の拒否ルール（不明な要件、許可されていない要件、不明または利用できないクライアント、
  重複するバージョン）は、どのホストでも同じように拒否できるよう、必ず 1 か所だけに記述します。
- モノリスにアプリケーション名を持たせてはいけません。新しいアプリケーションを追加する際は、
  カタログに項目を追加するだけで済みます。

## 決定事項 {#decisions}

### 1. `@gitlab/mfe-shell` が唯一のホストランタイム {#1-gitlabmfe-shell-is-the-only-host-runtime}

`@gitlab/mfe-shell` パッケージ（ツールキット、ADR 004）は、「ページにマウント要素がある」状態から、
「アプリケーションの `mount(el, props)` が実行された」状態までの処理をすべて担います。

- ページごとに単一の Module Federation ランタイム。このパッケージにバンドルし、各ホストが固有の
  フェデレーションプラグインやランタイム依存関係を持つ必要をなくします。
- リモートをマニフェスト URL から登録する処理。ADR 008 の開発サーバーとオーバーライドをソースとする場合も含みます。
- ADR 006 のマウント契約。`MountProps` の構築と凍結、クライアントの遅延構築、ケイパビリティのチェック、
  拒否コード、マウント要素の `.mfe-<name>` クラスと `data-mfe-*` 状態属性、`unmount` を扱います。
- モノリス、`mfe-shell dev-host`、パッケージが提供側向けに同梱するテスト用ユーティリティなど、
  すべてのホストに共通する動作。

このパッケージにランタイム依存関係はありません。モノリスが使用するどのバンドラーでもそのまま利用できる
ES2019 の出力を提供し（`@gitlab/frontend-utils` がビルド出力を検証する際と同じターゲット）、
Jest 向けの `require` 用ビルドを含む `exports` マップを通じて API を公開します。各パッケージが個別に
選ぶターゲットに代わる、ツールキットの全パッケージ共通のトランスパイルターゲットは、ツールキットで別途決定します。
決まり次第、このパッケージも採用します。

### 2. モノリスにはアダプターだけを置く {#2-the-monolith-keeps-an-adapter-nothing-more}

モノリス自身がマイクロフロントエンドのために持つコードは、ページごとに 1 回 `MfeShell.init` を呼び出す
アダプターに絞ります。モノリスの HTTP クライアント、Apollo クライアント、エラーレポーターとトラッカー、
ユーザーのロケールとテーマ、サーバーがレンダリングしたカタログ項目を渡します。アダプターにはアプリケーション名や
アプリケーション固有の分岐がなく、カタログに掲載されるどのアプリケーションにも同じコードを使います。
マイクロフロントエンドをレンダリングする画面は、サーバーで解決した配置項目を持つマウント要素をレンダリングし、
残りをシェルに任せます。

サーバーとシェルが共有するのはルールで、判定そのものは共有しません。配置先にレンダリングするかどうかを
最終的に判断するのは、ADR 008 の `Renderable.can_render?` です。検証済みマニフェストのカタログ内のコピーと、
サーバーだけが参照できる権限の語およびフラグに基づいて拒否条件を評価し、条件を満たさない配置は
レンダリングしません。シェルは、アプリケーションコードが実行される前に、ブラウザーが実際に読み込んだ
マニフェストに対して同じ条件をもう一度評価します。2 度目の確認は判定をやり直すためではなく、
開発サーバーまたはオーバーライドのマニフェストがカタログ内のコピーと異なる場合に検出するためのものです。
サーバーがないホスト（開発用ホスト、テスト）ではこれが唯一の確認です。ルール自体は、
`@gitlab/mfe-shell/contract` の 1 か所に記述し、サーバー側のチェックはそのルールと同じように動作します。
サーバーがレンダリングしたページでシェルが拒否した場合は、両者の判定が一致しなかったことを示すため、
拒否コードを添えて `services.reportError` で報告します。

### 3. ビルド時に統合するホストに向けた差し替え箇所 {#3-a-seam-for-a-build-time-host}

`ShellOptions.runtimeFactory` を使うと、ホストはバンドル済みのランタイムに代わり、独自のフェデレーションランタイムを
提供できます。現在はテストで使用しています。将来、モノリスが自前の Rspack 設定にバンドラーレベルの
フェデレーションプラグインを組み込み、ビルド時にフェデレーションを行う際も、マウント契約やアプリケーションを
変更せずに統合する方法になります。そのホストができるまでは、ほかにこの差し替え箇所を使うものはありません。

## 検討した代替案 {#alternatives-considered}

- **モノリスをビルド時の Module Federation ホストにする。** 現時点では採用しません。モノリスの Rspack ビルドに
  ホスト設定が必要で、webpack のフォールバック、Vite の経路、Jest にも個別の設定が要り、複数の動作を
  揃える必要があるためです。`runtimeFactory` を通じて、後で採用できるようにしておきます。
- **シェルを共有せず、アプリケーションごとにフェデレーションランタイムを持つ。** 却下しました。1 つのページで
  ランタイムが重複し、ADR 006 の拒否ルールを 1 か所に記述できないためです。
- **ホストランタイムをパッケージ化せず、モノリス内で提供する。** 却下しました。スタンドアロンの開発用ホストと
  提供側のテスト用ユーティリティで再実装が必要になり、提供側が開発対象のバージョンを固定できないためです。

## 影響 {#consequences}

- 提供側は 1 つのパッケージを使って開発し、開発用ホスト、テスト、本番で同じマウント動作を確認できます。
- 別の GitLab 製品やモノリス外のページなど、他のホストも同じ形のアダプターです。独自のクライアントと
  カタログ項目を `MfeShell.init` に渡すことで、すべてのアプリケーションを変更せずに利用できます。
- アプリケーションのマウント方法を変更するときは、ツールキットでレビューし、バージョン付きのパッケージとして
  リリースします。モノリスは依存関係のバージョンを更新して取り込みます。各画面で取り込むべき
  モノリスの変更は発生しません。
- プラットフォームのためにモノリスに加える差分は、アダプター、マウント要素、依存関係です。
  フェデレーションの設定は追加しません。
- ビルド時に統合するホストが今後必要になれば、別の契約を作らずに `runtimeFactory` の実装で対応します。
