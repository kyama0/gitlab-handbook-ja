## 背景 {#context}

ADR 003 により、インスタンスは設定済みのソースからカタログを取得します。ADR 007 により、GitLab.com の
共有ソースが 1 つになり、アプリケーションごとに複数のバージョンとデフォルトを掲載します。
インスタンス側には 2 つの問いが残っています。

- ソースに複数のバージョンが掲載されているとき、開発者がローカルの開発サーバーを実行しているとき、
  管理者がソースのデフォルトと異なるバージョンを希望するときに、**どのバージョンを配信するか**。
- **問題のあるリリースをどのように停止するか**。モノリスをデプロイせず、ソースのデフォルト変更も待たずに、
  1 つのインスタンスで数分以内に停止する方法が必要です。

解決ルールと管理者による制御は、インシデント時にオンコールエンジニアが操作する部分です。そのため、ルールは
少数で予測可能であり、トークンと `curl` で操作できる必要があります。

### 制約 {#constraints}

- カタログは多くのリクエストで読み込まれます。管理用サイドバーは、すべての管理ページで全アプリケーションの
  バージョンを解決します。解決にかかるコストを低く抑え、リクエスト処理中にソースを直接呼び出してはいけません。
  唯一の例外は決定事項 3 のコールドキャッシュの構築です。リースと時間制限のもと、リクエストごとではなく
  プロセスごとに 1 度だけ行います。
- インスタンスが配信するのは、ソースに掲載され、公開されたダイジェストと一致するバージョンでなければなりません。
  管理者が選べるのは掲載バージョンの中からであり、任意のバージョンを指定することはできません。
- GitLab.com はセル単位でデプロイされます。クラスタ全体の設定が設けられるまで、「インスタンス」はセルを指します。
- アプリケーションの問題を管理者が確認できる必要があります。マイクロフロントエンドをレンダリングするどの画面でも、
  問題がレンダリング可否に与える影響は同じでなければなりません。

## 決定事項 {#decisions}

### 1. 解決順序は開発サーバー、オーバーライド、デフォルト {#1-resolution-order-dev-server-override-default}

アプリケーション `name` では、以下のうち最初に該当するバージョンを配信します。

1. **ローカルの開発サーバー**。開発環境に限り、ADR 003 の第 6 節に従って検出します。
2. **インスタンスのオーバーライド**。`name` にオーバーライドが存在し、**かつ**そのバージョンがソースに引き続き
   掲載されており、**かつ**掲載されたマニフェストのダイジェストがオーバーライドとともに保存したダイジェストに
   等しい場合に使用します。
3. **ソースのデフォルトバージョン。**

ソースに掲載されていないバージョンをリクエストすると、404 を返します。オーバーライドのバージョンが
一覧から消えた場合は、理由を `override_unavailable` としてデフォルトを配信します。掲載されたダイジェストが
変わった場合は、理由を `override_digest_mismatch` としてデフォルトを配信します。どちらの場合も警告をログに
記録し、`gitlab_mfe_override_unavailable_total{app,reason}` を増やすため、古いバージョン固定が黙って
無視されることはありません。マーケットプレイスのオブジェクトは不変なので（ADR 007）、通常ダイジェストが
不一致になることはありません。不一致が起きた場合、不変性を強制しないソースが同じバージョンを上書きして再公開したか、
ソースとインスタンスの間で何らかの要因によりバイト列が変わったかのどちらかです。そのため、インスタンスは新しい
ダイジェストを信用せず、デフォルトにフォールバックします。この事象を見過ごさず、ログとメトリクスに記録します。

### 2. オーバーライドはテーブルに保存し、管理者 API でのみ変更する {#2-overrides-live-in-a-table-and-change-only-through-the-admin-api}

オーバーライドは、管理者がそのインスタンスで継続的に使うバージョンを選択する仕組みです。インシデントを
前提とした一時措置ではありません。ローリングリリースよりも固定バージョンを好む組織はバージョンを固定し、
ローリングリリースを好む組織はデフォルトを使います。ロールバックも同じ仕組みの用途の 1 つです。
テーブルは選択とその来歴を保存し、モデルには有効期限を設けません。オーバーライドは
`mfe_version_overrides` の行で、アプリケーション名ごとに 1 行です。固定したバージョン、固定時の
マニフェストのダイジェスト、設定した人と時刻を記録します。テーブルの
スキーマは `gitlab_main_cell_setting` です。したがって、GitLab.com のオーバーライドは、他のインスタンス設定と
同様、クラスタ全体の仕組みができるまでは、それを保持するセルに適用されます。

行は管理者 REST API を通じてのみ変更します。

- `GET /api/v4/admin/mfe/apps` は、すべてのアプリケーションについて、ソースの稼働状況、デフォルト
  バージョン、現在配信中のバージョンとその理由（`dev`、`override`、`default`、および
  オーバーライドが選ばれなかった場合の理由）、設定されていればオーバーライド、掲載されたバージョン、
  宣言された配置、要件とクライアント、レンダリング可否、および問題を一覧表示します。
- `PUT /api/v4/admin/mfe/apps/:name/override` に `{ "version": "…" }` を渡すとバージョンを固定します。
  サーバーは現在の一覧を使って再検証し、掲載されていないバージョン、マニフェストが無効なバージョン、
  重大度がエラーの問題を抱えたアプリケーションのバージョンは 422 で拒否します。
  EE はインスタンス監査イベント `mfe_version_override_set` を記録します。
- `DELETE /api/v4/admin/mfe/apps/:name/override` はデフォルトに戻します。EE は
  `mfe_version_override_reset` を記録します。
- `POST /api/v4/admin/mfe/catalog/refresh` はカタログの即時更新を要求します。

どのエンドポイントも管理者権限を必要とし、プラットフォームが無効な間は 404 を返します。
API に REST を採用することで、インシデント時にパーソナルアクセストークンと `curl` で復旧できます。
管理 UI（このプラットフォーム上のアプリケーション）は、この API のクライアントの 1 つであり、
別の書き込み経路にはなりません。

### 3. Sidekiq の定期ジョブでリクエスト処理とは別にカタログを更新する {#3-the-catalog-is-refreshed-by-a-sidekiq-cron-not-on-the-request-path}

定期ワーカーは毎分、設定されたすべてのソースからカタログを更新します。ソースからの取得に失敗した場合は、
最後に正常取得した一覧を保持し、そのソースを異常とマークします。また、デフォルトとオーバーライドの全バージョンの
マニフェストをキャッシュに事前読み込みし、`gitlab_mfe_catalog_last_success_timestamp_seconds` を記録します。
プラットフォームが無効なときやソースが設定されていないときは、何も行いません。

ページのレンダリングには、定期ジョブが事前読み込みしたマニフェストだけを使います。コールドキャッシュは、
排他的なリースと 5 秒の制限時間のもと、リクエスト処理中に最大 1 回構築します。タイムアウトすると
アプリケーションはレンダリングせず、問題 `manifest_unavailable` を付与します。リクエストとしては
余裕のある時間ですが、コストがかかるのはリクエストごとではなくソースとプロセスの組み合わせごとに 1 回です。
また、遅延の大きい回線を使うインスタンスでは、次の定期ジョブまでアプリケーションが表示されないより、
最初のページだけが遅いほうが適切です。それ以外では、リクエスト処理中にソースを呼び出すことはありません。

### 4. 問題には重大度があり、ホストに依存しない {#4-problems-have-severities-and-are-host-independent}

キャッシュ済みのカタログは、アプリケーションごとに `{ code, severity, message }` の形式で問題を
記録します。問題は、マニフェスト、ホストの語彙、ソースだけに依存し、フィーチャーフラグやユーザーには
依存しません。そのため、すべてのリクエストでキャッシュを利用できます。

- 重大度が `error` の場合、マウント要素はレンダリングしません。`unknown_requirement`、
  `requirement_not_granted`、`unknown_client`、`manifest_invalid`、`manifest_unavailable`。
- 重大度が `warning` の場合、アプリケーションは引き続き配信します。`unknown_placement`（その項目は
  除外します）、`unknown_feature`（宣言されたフィーチャーフラグがホストに定義されていない場合。
  `false` として扱います。ADR 006 の第 3 節を参照）、`version_mutated`（掲載バージョンのダイジェストが
  変更されてから 24 時間）、`override_unavailable`、`override_digest_mismatch`、`source_unhealthy`。

### 5. リクエスト時に共通の判定でレンダリング可否を決める {#5-one-request-time-predicate-decides-rendering-everywhere}

`Renderable.can_render?(app, placement:, user:)` は、ナビゲーションメニュー、管理ページ、ページスロット、
機能パネル、管理者 API の `renderable` フィールドに共通の唯一の判定です。アプリケーションに
`error` の問題がある場合、ユーザーが配置先の権限の語で指定された条件を満たさない場合、またはアプリケーションが
このリクエストではホストが提供しないクライアントを宣言している場合は偽になります。たとえば、フラグが
無効なときの `module_api` はリクエストごとに `client_unavailable` として報告し、キャッシュしません。
レンダリング可否を別の場所で判定することはありません。

### 6. v1 の互換性は GitLab.com と足並みを揃える {#6-compatibility-in-v1-lockstep-with-gitlabcom}

v1 では、ソースに掲載されたバージョンは、それを配信するインスタンスと互換性があるものとします。唯一の
利用インスタンスが GitLab.com で、提供側がその環境に対してリリースする間は、この前提が成り立ちます。
マニフェストに互換性の範囲を設けることと、インスタンスをダウングレードすると互換性を失うバージョンを
除外することは、セルフマネージドへのロールアウト時に再び検討します。

## 検討した代替案 {#alternatives-considered}

- **`ApplicationSetting` にオーバーライドを JSON として保存する。** 却下しました。行単位の監査ができず、
  アプリケーションごとの一意性も保証できず、フィールドごとにスキーマ変更が必要なためです。
- **オーバーライドを Redis に保存する。** 却下しました。永続性や監査性がなく、他のすべてのインスタンス設定を
  保護するデータベースレビューの対象外になるためです。
- **ブラウザーがダイジェストを指定する**（ページが期待するダイジェストをサーバーに伝える）。
  却下しました。サーバーは検証済みのダイジェストを把握しており、クライアントから指定できる経路を追加しても、
  不一致の可能性が増えるだけです。
- **オーバーライドをロールバックと呼び、有効期限と理由を必須にする。**
  却下しました。オーバーライドはインシデント専用の回避策ではなく、管理者の選択を記録するものです。
  組織が固定バージョンを望む限り存続でき、デフォルトより新しいバージョンの固定も、古いバージョンの固定と同様に有効です。
  自由記述の理由や Work Item へのリンクは、後からモデルを変更せずに行に追加できます。
- **リクエストごとにその場で解決する。** 却下しました。管理用サイドバーのリクエスト処理中に、
  アプリケーション数だけソースを呼び出すことになります。
- **管理者 API に GraphQL を使う。** v1 では採用しません。REST は既存の管理者設定エンドポイントと
  一致し、インシデントからの復旧に必要なのはトークンと `curl` だけです。UI 用の GraphQL ファサードは
  後から追加できます。

## 影響 {#consequences}

- 管理者は 1 回の API 呼び出しで、インスタンスのバージョンを固定またはリセットし、配信中の
  バージョンが選ばれた理由を確認できます。これはソースやデプロイに依存しない、プラットフォームで
  最速のロールバック手段です。
- バージョン固定は、根拠となった情報が有効な間だけ適用されます。ソース上で固定バージョンが変更または
  削除されると、インスタンスはデフォルトにフォールバックし、その事実をメトリクスとログで示します。
- GitLab.com では、クラスタ全体の設定ができるまではセルごとにオーバーライドを適用する必要があります。
  API は、当該 API を配信するセルに対して操作します。
- 鮮度を保つには定期ジョブが不可欠です。Sidekiq が停止すると、インスタンスは最後に正常取得したカタログの
  配信を続け、鮮度低下をゲージで示します。
- マイクロフロントエンドをレンダリングするすべての画面が 1 つの判定を共有します。新しい画面が、重大度が
  エラーの問題を持つアプリケーションや必要な権限を満たさないアプリケーションを誤ってレンダリングすることを防ぎます。
- インスタンスのバージョン間の互換性は先送りします。これは GitLab.com が唯一の利用側である間に限って
  許容でき、セルフマネージドに向けてはブロッカーであるため、そのように追跡します。
- 足並みを揃える運用はテストの範囲も限定します。オーバーライドにより、どのアプリケーションの掲載バージョンも
  組み合わせられますが、その総当たりの組み合わせをスモークテストすることはできません。
  テストするのは、現行のデフォルト同士の組み合わせと、各アプリケーションの掲載上の直前バージョンを
  他のアプリケーションの現行デフォルトと組み合わせた場合です。オーバーライドでは直前バージョンが選ばれる
  可能性が最も高いからです。他の組み合わせはすべて、設計上テストの対象外です。
