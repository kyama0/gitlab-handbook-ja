## 要約 {#tldr}

各 MFE は gettext から独立し、自身の文字列を vue-i18n のカタログで管理します。文字列の変更は MFE とともに
リリースされるため、モノリスのリリースを待たずに済みます。開発者は gettext と同様に英語の原文を `t()` に
直接記述し、スクリプトが `locales/en.json` に抽出します。翻訳には、すべての MFE で専用の Crowdin
プロジェクト `gitlab-mfes` を共有します。モノリスの `gitlab-ee` プロジェクトには変更を加えません。

各リポジトリの CI ジョブが新しい文字列を Crowdin に送信し、翻訳をマージリクエストとして取り込みます。
これは Crowdin の組み込みインテグレーションではエクスポートした翻訳を整形できないためです。
モノリスからコードを移植する際は、msgid が一致する既存の翻訳を引き継ぎます。

各 MFE のバージョンは自身の翻訳を同梱します。実行時に外部から取得する必要がないため、エアギャップ環境の
インスタンスでも動作します。翻訳はチームが次にタグを付けるバージョンでリリースします。翻訳を書き込める
人やリポジトリが増える前に、翻訳を変更できる範囲を段階的に制限します。MFE 用に新しく記述した文字列を
誰が翻訳するかは、ローカリゼーションチームと引き続き検討します。

## 開発者の作業手順 {#what-it-looks-like-for-a-developer}

`s__()` と同様に、英語の原文を直接記述して `t()` に渡します。

```vue
<script setup>
import { useI18n } from 'vue-i18n';

const { t } = useI18n();
</script>

<template>
  <p>{{ t('Hi {name}, how can I help?', { name }) }}</p>
</template>
```

`pnpm i18n:extract` は英語の原文を `locales/en.json` に書き出します。このファイルをコードの変更と
一緒にコミットしてください。ファイルの内容がコードと一致していないと `check-translations` が失敗します。
その他の `locales/<locale>.json` ファイルは Crowdin が書き出します。

マージリクエストが `main` にマージされると、`push-translations` が変更された `en.json` を Crowdin の
`gitlab-mfes` プロジェクトに送信します。平日は `pull-translations` が翻訳済みの文字列をマージリクエストとして
取り込み、チームが次にタグを付けるバージョンで翻訳をリリースします。翻訳が済むまでは、ユーザーには英語の原文が表示されます。

モノリスからコードを移植する際は、`pnpm i18n:port` で書き換えを自動化します。codemod は
`s__('DuoChat|Close chat')` を `t('DuoChat|Close chat')` に変換し、gettext の msgid をキーとして保持します。
次に保護ブランチで `bootstrap-translations` ジョブを手動で実行します。このジョブはモノリスの
`locale/*/gitlab.po` から各 msgid を探して翻訳を取り込むため、移植した UI はリリース初日から翻訳済みです。
MFE 用に記述した文字列がモノリスの翻訳を引き継げるのは、その英語の原文がすでにモノリスの msgid として存在する
場合だけです（決定 4）。それ以外の文字列には翻訳者が必要です（決定 7）。

開発者自身がこの CI を設定する必要はありません。翻訳ジョブは `@gitlab/frontend-config` のプラットフォーム CI
テンプレートに移行する予定です（[ADR 004](004_packages_group_and_shared_setup.md)）。
`mfe-scripts create --into` は新しいすべての MFE にこのテンプレートを組み込むため
（[ADR 010](010_scaffolding.md)）、新規 MFE に必要なのは `locales/en.json` と `crowdin.yml` だけです。
この移行は提案段階で、検証はこれからです（決定 6）。現時点でジョブが動作するのは `gitlab-mfe` リポジトリだけです。

## 背景 {#context}

モノリスは gettext で UI を翻訳します。Ruby ツールが `__()`、`s__()`、`n__()` の呼び出しを
`locale/gitlab.pot` に抽出し、
[`crowdin-translation-sync`](https://gitlab.com/gitlab-org/frontend/crowdin-translation-sync)が Crowdin の `gitlab-ee` プロジェクト（288872）と双方向に同期します。このプロジェクトとツールは
ローカリゼーションチームが管理します。

この仕組みは MFE には適用されません。MFE のリポジトリにしかない文字列は `gitlab.pot` に入らないため、
翻訳する人がいません。MFE の文字列をモノリス経由で処理すると、文字列の変更がすべてモノリスのリリースに
依存します。この依存関係こそ、[設計ドキュメント](../_index.md)が解消しようとしているものです。

Duo Chat MFE はローカリゼーションチームと協力し、
[`gitlab-org/frontend/gitlab-mfe`](https://gitlab.com/gitlab-org/frontend/gitlab-mfe) でこの課題に対応する
パイプラインを作成し、検証しました。この ADR では、そのパイプラインをプラットフォームの標準として提案します。

- 利用方法 [`docs/i18n.md`](https://gitlab.com/gitlab-org/frontend/gitlab-mfe/-/blob/main/docs/i18n.md)
- 進捗管理とエンドツーエンドの検証 [作業アイテム 602651](https://gitlab.com/gitlab-org/gitlab/-/work_items/602651)
- ローカリゼーションチームの意思決定 [localization-team の作業アイテム 916](https://gitlab.com/gitlab-com/localization/localization-team/-/work_items/916)
- 仕様に基づく AI 事前翻訳 [localization-team の作業アイテム 920](https://gitlab.com/gitlab-com/localization/localization-team/-/work_items/920)

### 現状（2026-11-16） {#where-it-stands-2026-11-16}

- `gitlab-mfes`（923421）は公開されており、モノリスで表示できる英語以外の 26 言語が対象です。
- Duo Chat には 257 件の文字列があり、うち 230 件はモノリスから移植しました。11 ロケールでは 168 件以上が翻訳され、
  残り 15 ロケールでは 59 件以下です。
- 2026-08-31 から、定期取得ジョブで翻訳の MR を作成してマージしています。
- 翻訳の大半はモノリスからの取り込みか、翻訳メモリ（TM）の一致候補を使ったものです。2026-11-01 に
  コミュニティの翻訳者が参加し、183 件の文字列を繁体字中国語に翻訳したため、`zh-TW` は 100% に達しました。
  2026-11-17 時点でプロジェクトには 5 人のメンバーがおり、そのうち全 26 言語の翻訳者権限を持つのは
  ベンダーの窓口担当者とそのコミュニティの翻訳者の 2 人です。

### 制約 {#constraints}

- **独立したリリース。** 文字列の変更は MFE とともにリリースし、モノリスのリリースから独立させます。
- **エアギャップ環境への対応。** 翻訳はコードに同梱します。実行時にインスタンスから Crowdin に接続できるとは限りません。
- **不変のバージョン。** 翻訳を更新すると新しいバージョンになります
  （[ADR 003](003_module_carried_packaging_and_serving.md#1-one-source-protocol-for-every-surface)）。
- **ポリレポ。** `gitlab-mfe` モノレポ以外でも、リポジトリごとに動作する必要があります
  （[ADR 001](001_tooling_repository_strategy.md#mfe-application-code-open)）。
- **`gitlab-ee` の管理は管轄外。** 現在の同期と Webhook が引き続き同じように動作する必要があります。
- **同じ画面内での表示。** MFE はモノリスの UI と並んで表示されるため、同じ語句には両方で同じ訳を使う必要があります。
- **ロケールコード。** [ADR 006](006_mount_contract.md) の `preferences.locale` でホストが渡す値には、
  `Gitlab::I18n` のコード（`pt_BR`、`es`）を使います。BCP 47 タグは使いません。

## 決定事項 {#decisions}

### 1. 各 MFE が英語の原文をキーとする vue-i18n カタログを管理する {#1-each-mfe-owns-vue-i18n-catalogues-keyed-by-their-english}

各 MFE と、文字列を含む各共有パッケージは、フラットな `locales/en.json` を持ちます。コンポーネントは
[vue-i18n](https://vue-i18n.intlify.dev/) 11 の `t()` または `useI18n()` を呼び出し、英語の原文をキーとして
渡します。このため、テンプレートを読めばそこに表示される文言がわかります。

```json
{
  "Send": "Send",
  "Hi {name}, how can I help?": "Hi {name}, how can I help?",
  "DuoChat|Close chat": "Close chat"
}
```

- `pnpm i18n:extract` は文字列リテラルを渡すすべての `t()` 呼び出しから `en.json` を生成し、コードに追従していなければ
  `check-translations` が失敗します。現時点では PoC のスキャナーが移植したキーを抽出しており、全キーに対象を広げます。
- ロケールファイルは手動で編集しません。他のロケールのファイルは Crowdin が生成します。
- 同じ英語の原文が 1 つの MFE 内で 2 つの意味を持つ場合（`Open` ボタンと並ぶ `Status|Open` など）は、
  必要に応じて名前空間を使います。決定 4 では msgid の完全一致を使うため、移植した文字列の名前空間は保持します。
- `pnpm i18n:port` は `s__()` を `t()` に、`n__()` をパイプ区切りの複数形メッセージに書き換えます。
  新しい複数形には `t('{count} item | {count} items', count)` のように、パイプで区切られたメッセージ全体をキーとして
  使います。複数形の規則は gettext の語形順に従うため、取り込んだ複数形にはモノリスと同じ語形が選ばれます。

この方法を選んだのは、Vue 3 に対応するネイティブライブラリであり、Crowdin の `i18next_json` パーサーが
翻訳者による `{placeholders}` の変更を防ぎ、開発者が gettext と同様に文言を直接記述してスクリプトで抽出する
ワークフローを維持できるためです。

この方法では、次のコストを受け入れます。

- モノリスの国際化 API に加えて、もう 1 つの API が必要になります。
- gettext と同様に、英語の原文を編集すると新しいキーになり、既存の翻訳を引き継げません。事前翻訳を適用するのは、
  TM の一致率が 100% の場合だけです。
- キーの型チェックがないため、キーを入力し間違えると新しい英語の文字列として扱われ、コンパイル時には検出できません。
  動的なキー（`t(label)`）は抽出できないため、リントルールが必要です。
- Crowdin はパイプ区切りの複数形を、内訳のわからない 1 つの文字列として表示します。ウクライナ語やポーランド語の
  翻訳者には英語の 2 つの語形が表示され、自分の言語の 4 つの語形を gettext の順番で 1 行に入力する必要があります。
  CI は語形数を `en.json` の 2 つと比較するだけなので、正しい 4 語形の訳で警告が出て、間違った 2 語形の訳が通ります。
  翻訳者に Crowdin 上でどう見えるかは未検証です。MFE 専用の複数形を初めてリリースする前に、表示のテストと、
  ロケールごとの語形数を検証するチェックを用意します。
- `sprintf` はパラメーターをエスケープしていましたが、`t()` ではエスケープしません。パラメーターを含む移植済みの
  文字列は `v-html` と `v-safe-html` で使用しないでください。codemod はリスクのあるファイルにフラグを付けます。

検討した他の案は以下のとおりです。

- **手作業で編集する `en.json` で camelCase のキーを使う。** PoC の最初のルールです。キーを型チェックでき、
  英語の原文を編集しても翻訳を維持できます。一方でテンプレートから表示文言がわからなくなり、移植した文字列には
  別のキー形式も必要です。PoC でもほとんど使われておらず、Duo Chat の 27 個の camelCase キーは
  すべてデモ用のシェルのものです。
- **MFE で gettext を使う（Jed + PO ファイル）。** モノリスと同じ API を使えますが、Jed は 2015 年以降
  メンテナンスされていません。抽出にはモノリスの Ruby ツールを使っており、Crowdin との専用の同期も必要です。
  パイプラインが分かれるのは、リポジトリが別だからです。ファイル形式に依存しません。
- **ホストから翻訳を注入する**（`setConfigs({ translations })` を介する `@gitlab/ui` / `@gitlab/duo-ui` のモデル）。
  新しいパイプラインは不要ですが、すべての文字列がモノリスのリリースを待ちます。古いセルフマネージドの
  モノリスで新しい MFE を使うと、新しい文字列は英語で表示されます。すべての文字列が重複し、
  マウント契約のペイロードも増えます。
- **ICU MessageFormat（FormatJS）。** Crowdin で複数形を扱いやすくなりますが、3 つ目の構文が加わり、
  私たちの構成では未検証です。

### 2. すべての MFE で `gitlab-ee` とは別の Crowdin プロジェクトを共有する {#2-one-crowdin-project-for-every-mfe-separate-from-gitlab-ee}

当初は、翻訳者のコミュニティが 1 つにまとまり、ローカリゼーションチームが既存のレポートを引き続き利用でき、
新しいプロジェクトの管理も不要なため、`gitlab-ee` を共有する予定でした。Crowdin のサポートからの助言と
ローカリゼーションチームの監査を受け、この案は見送りました。

- 2 つ目のリポジトリを接続すると、プロジェクト内のすべてのインテグレーションで、ブランチに名前空間が付くように
  切り替わります。`crowdin-translation-sync` は `--branch master` を渡すため、翻訳者には `gitlab.pot` の
  2 つ目のコピーが作成されます。
- 新しい翻訳の保存先はデフォルトの TM に限られます。MFE の文字列が TM 82641（611,369 セグメント）に混入し、
  対象を限定する方法がありません。
- Webhook はパス単位で範囲を限定できないため、MFE のファイルに対して両方のパイプラインが起動します。
- `exportApprovedOnly` が有効で、私たちの取り込み処理では翻訳を承認しません。
- モノリスの翻訳も再利用できません。`%{name}` を含む `DuoChat|Delete this chat` は、
  `{name}` を含む `Delete this chat` には一致しません。

そのため、すべての MFE は `gitlab-mfes`（923421）を共有します。

| 設定 | 値 | 理由 |
| --- | --- | --- |
| デフォルトの TM | 738983。モノリスの PO ファイルから名前空間を除いた 2,306 セグメント | MFE の翻訳を 82641 から分離してここに保存します |
| 読み取り専用の TM | 82641（`gitlab-ee`） | 汎用的な文字列（`Send`、`Project`）をモノリスの翻訳に一致させます |
| 用語集 | 532447 | ローカリゼーションチームが 71952 を整理している間、71952 は割り当てません |
| `exportApprovedOnly` | オフ | 取り込み処理では翻訳を承認しません。決定 8 で承認の手順を変更するまでは MR でレビューします |
| `skipUntranslatedStrings` | オン | オフにすると、エクスポートで英語の原文が各カタログに書き込まれます |
| `useGlobalTm` | オフ | 対象の TM を明示します |
| 対象言語 | モノリスで表示する `en` を除いた 26 言語 | それ以外の言語のカタログはどこからも読み込まれません |

この方法には、次の課題があります。

- ベンダーが管理する言語も含めて、メンバーと校正者の権限を改めて設定する必要があります。
- 現在のローカリゼーションツールが読み取るのは `gitlab-ee` だけです。`contributions.py`、`comments.py`、
  `context.py` の拡張が必要で、`gitlab-string-search` では MFE の文字列が見つかりません。
- Crowdin トークンのアクセス範囲はディレクトリ単位で制限できないため、トークンを持つリポジトリは
  他のリポジトリのファイルを上書きできます（決定 8）。

**MFE ごとに 1 つのプロジェクトを設ける案**も検討しました。認証情報を分離できますが、MFE ごとに
上記の設定をすべて繰り返す必要があり、翻訳者がプロジェクトごとに分散します。

### 3. CI ジョブが Crowdin と同期する {#3-ci-jobs-sync-with-crowdin}

| ジョブ | 実行条件 | 処理 |
| --- | --- | --- |
| `check-translations` | カタログまたはソースの変更時 | `en.json` の内容がコードに追従していない場合、`{placeholders}` の欠落や追加、未知のロケール、翻訳中の HTML がある場合に失敗します（決定 8） |
| `push-translations` | `main` で `en.json` が変更されたとき | `crowdin push sources` |
| `bootstrap-translations` | 保護ブランチで手動実行 | 移植した文字列の翻訳をモノリスから取り込みます（決定 4） |
| `pull-translations` | 定期実行（平日） | 翻訳を取得、正規化、検証し、翻訳の MR を作成します |

ジョブは `crowdin.yml` を持つパッケージをすべて検出するので、新しい MFE の追加に伴うパイプラインの変更は不要です。
独自のジョブを実行することで、取得のたびに後処理し（`normalize-locales.mjs` が空の値、古いキー、未知のロケールを除外します）、
MR でレビューできます。

この方法には、次のコストがかかります。

- 決定 8 で Crowdin トークンを中央ジョブに移すまでは、リポジトリが Crowdin トークンと、プッシュおよび MR の作成が
  可能な GitLab トークンを保持します。
- 保護変数は MR パイプラインに渡らないため、取り込みジョブは保護ブランチで実行します。
- スケジュール実行では `changes:` が常に真となるため、定期ジョブには追加の実行条件が必要です。

**Crowdin の GitLab インテグレーション**は CI とリポジトリ内のトークンが不要です。私たちは一度試しましたが、次の理由で削除しました。

- Crowdin のエクスポート結果をそのままコミットします。`i18next_json` では、翻訳されていないキーは空の値になります。
  vue-i18n はそれらを空欄として表示し、英語にはフォールバックしません。後処理用のフックもありません。
- CLI はルートに原文を書き込みますが、このインテグレーションは専用の Crowdin ブランチに書き込みます。その結果、
  キーが 27 個のカタログに 54 件の文字列ができました。
- 設定パーサーが YAML アンカーを無視するため、`de.json` が必要なところで `de_DE.json` が作られました。
- 状態の確認や自動化に使える API がありません。

モノリスがパイプラインを採用したのも同じ理由です。インテグレーションでは対応できない後処理が必要です。
Crowdin Custom Exporter で対応できる可能性はありますが、はるかに大きな作業になります。

**`crowdin-translation-sync`** の対象を MFE リポジトリに広げれば認証情報を一元化できますが、このツールは
`gitlab.pot` と 1 つの対象リポジトリを前提にしており、すべての MFE リポジトリへの書き込みアクセスが必要になります。
私たちはこの案を試していません。

### 4. 移植した文字列はモノリスの翻訳を引き継ぐ {#4-ported-strings-keep-the-monoliths-translations}

モノリスから移植するコードの文字列は、大抵すでに翻訳されています。モノリスの `gitlab.pot` に msgid として存在する
キーを移植済みとみなし、`bootstrap-translations` はその msgid に完全一致するモノリスの翻訳を取り込みます。
複数形も対象です。取り込んだ翻訳は Crowdin では承認しません。決定 8 に従って Crowdin の承認を必須にするまでは、
人が MR の差分をレビューします。

現在の PoC では、キーが camelCase 形式でなければ移植済みと判断しています。すべてのキーを英語の原文にすると、
どのキーも移植済みとみなされ、取り込みジョブの実行時に MFE 専用の文字列に対する翻訳者の作業を上書きまたは
削除してしまいます。まず PoC に `gitlab.pot` で判定するルールを組み込む必要があります。

移植した文字列については、引き続きモノリスを正とします。次回実行時には `gitlab-mfes` にある異なる訳を
モノリスの訳で置き換えるため、翻訳者が変更したいときは `gitlab-ee` で編集します。英語の原文がすでにモノリスの
msgid にある新しい文字列（`Send` など）も移植済みとみなし、同じようにモノリスに従います。取り込みは翻訳を
削除しません。モノリスに翻訳がない場合は、`gitlab-mfes` にある翻訳を保持します。現時点の PoC では削除が発生します。
2026-11-19 にモノリスのデフォルトブランチを対象に実行した場合、2026-11-01 に追加された 183 件の繁体字中国語訳のうち
36 件が置き換わり、4 件が削除されます。

引き継ぎに追加の手順は不要です。取り込みジョブは実行のたびに `gitlab.pot` を読み込むため、モノリスから msgid が
削除されると、そのキーは移植済みとみなされなくなります。それ以降はジョブが翻訳に手を加えず、`gitlab-mfes` が
唯一のコピーを保持します。この変化を検出できるのは取り込みジョブの実行時だけで、報告する仕組みはありません
（未解決の質問 8）。

msgid で照合するため、移植した画面はリリース初日から翻訳され、周囲のモノリスの UI と同じ用語が表示されます。
そのためには、MR がマージされる前にジョブがブランチの `en.json` をプッシュする必要があり、翻訳者には先に
文字列が表示されます。

検討した他の案は以下のとおりです。

- **PO ファイルを JSON に変換してコミットする。** 当初の案で、Crowdin を呼び出さずに済むシンプルな方法です。
  Crowdin はその翻訳を認識しないため、次回の取得時に翻訳が消えます。
- **英語の原文で TM を照合して事前翻訳する。** msgid がない文字列も対象にできます。初回の実行では、201 件の値が
  モノリスの翻訳と異なり（ドイツ語の `MergeRequest|Approved` は `Genehmigt` に対して `Akzeptiert` が返りました）、
  712 件は無関係な画面の訳でした。現在も変数で有効にできますが、デフォルトでは無効です。

### 5. 各バージョンに翻訳を同梱する {#5-translations-ship-inside-each-version}

MFE のビルドでは、各ロケールを遅延読み込みするチャンクに分けます。MFE はマウント時に、ホストのロケールの
カタログに加え、使用する共有パッケージの同じロケールのカタログも読み込みます。キーが欠けている場合は、
キーごとに英語にフォールバックします。

翻訳の MR がマージされた時点ではリリースされません。`main` の他の変更と同様、翻訳はチームが次にタグを
付けるバージョンでリリースします。アプリケーションはタグからリリースするため
（[ADR 007 の決定 2](007_marketplace.md#2-producers-release-in-their-own-projects-the-marketplace-pulls)）、
ボットが作成する翻訳 MR にリリースメタデータは不要です。

この方法はエアギャップ環境で動作し、バージョンの不変性を維持します。CSP のオリジンは増えず、バージョンを固定すると
表示文言も固定されます。代わりに、Crowdin で修正してから反映されるまで、翻訳の MR のマージ、タグ付け、
マーケットプレイスのロックファイルを更新する MR のレビューを待ちます。タグ付けには期限がなく、更新が少ない
MFE では数週間かかることもあります。待ち時間を短縮するため、代わりとなるチェックが整ってから、次の順で
待機を減らします。

1. **現在**、翻訳は次にタグを付けたバージョンでリリースし、`check-translations` は HTML を含む翻訳を拒否します
   （決定 8）。
2. **Crowdin での承認が必須になったら**（決定 8 のステップ 3）、`en` 以外のカタログだけを変更する、ボット作成の
   翻訳 MR を自動マージします。最後のタグ以降、翻訳だけがマージされていれば、ボットが翻訳のみのバージョンに
   タグを付けます。ADR 007 ではタグとパッケージ自体のバージョンが一致する必要があります。そのため、ボットは
   まずバージョンを更新するコミットを作成し、ADR 004 のような承認ポリシーにより、人による承認が必要になります。
   ADR 004 のプレースホルダー `0.0.0-dev` を採用する場合は、タグを付けるだけで済みます。
3. **ADR 007 で自動マージが有効になったら**、カタログを JSON ファイルとして配信し、変更されたファイルがカタログに
   限られるロック MR を `discover` が自動マージします。JSON ファイルは文字列のフラットなマップか検証できますが、
   JS チャンクにメッセージだけが含まれていることは証明できません。ビルド時に vue-i18n のランタイム専用ビルド向けに
   メッセージを事前コンパイルするため、生の JSON を使うにはメッセージコンパイラーをバンドルに含めるか、
   事前コンパイル済みのメッセージを JSON として保存する必要があります。短期の技術検証が必要です。

検討した他の案は以下のとおりです。

- **Crowdin の OTA 配信。** リリースを待たずに修正をユーザーに届けられますが、実行時にサードパーティのオリジンを
  使用するため、エアギャップ環境ではアクセスできません。また、リリース後に文言が変わり、レビューの手順もありません。
- **コードとは別にバージョン管理する翻訳パック。** コードのリリースを省略できますが、ADR 003 と ADR 007 における
  すべてのバージョン解決処理に 2 種類目のアーティファクトが加わり、バージョンを固定しても表示文言が固定されなくなります。
- **モノリスから配信する。** 決定 1 のホストから翻訳を注入する案と同じ問題があります。

### 6. 他のリポジトリにはプラットフォームのツールからパイプラインを提供する {#6-other-repositories-get-the-pipeline-from-platform-tooling}

提案段階で、検証はこれからです。PoC は 1 つのリポジトリで動作します。

- `mfe-scripts create --into`（[ADR 010](010_scaffolding.md)）は `locales/en.json` と `crowdin.yml` を作成し、
  ref を固定したプラットフォームの CI テンプレートを組み込みます。
- 翻訳ジョブは、`@gitlab/frontend-config` で提供するそのテンプレートに移行します
  （[ADR 004](004_packages_group_and_shared_setup.md)）。
- 各リポジトリは自身の GitLab プロジェクトのパスを名前に使ったトップレベルディレクトリにプッシュします。
  これにより複数のリポジトリが同じファイルに書き込むことを防ぎます。PoC のパスはこのルールを決める前のものです。
- 複数の MFE が共有する文字列は、その文字列を所有するパッケージに置きます。PoC はビルド時にワークスペースの
  パッケージのカタログを結合します。npm パッケージへの対応はこれからです。

Crowdin の認証情報の保存先は決定 8 で扱います。

### 7. MFE の新しい文字列の翻訳担当は、ローカリゼーションチームが判断する {#7-who-translates-new-mfe-strings-open-the-localization-teams-call}

決定 4 は移植した文字列を対象としています。新しい文字列の翻訳担当は未定です。localization-team の作業アイテム 916
では、以下の案が提示されています。

- **Crowdin のコミュニティ翻訳者。** プロダクト UI の翻訳を実際に担う人たちですが、多くの言語では翻訳者が少なく、
  プロジェクトには改めてメンバーを追加する必要があります。コミュニティに参加してもらうには Contributor Success
  との協議が必要です。
- **TM の後に Crowdin AI で事前翻訳する。** パイプラインはすでに `method: "tm"` でエンドポイントを
  呼び出しており、`method: "ai"` への切り替えは小さな変更です。AI プロバイダーも設定済みです。
  TM ではカバーできない言語（ブルガリア語とフィリピン語はそれぞれ 4 件）を補えます。ただし、プロンプトは
  Crowdin の UI で管理するため、git での管理、レビュー、履歴がありません。
- **git で管理する仕様に基づいて AI で翻訳する。** ルールはマージリクエストでレビューします。
  ローカリゼーションチームの[エージェントによる翻訳ハーネス](https://gitlab.com/gitlab-com/localization/agentic-translation-harness)はこの方式で、[GDATP](https://gitlab.com/gitlab-com/localization/gitlab-duo-agent-translation-platform)から用語データベースと翻訳ルールを読み取り、未承認の翻訳候補を Crowdin に投稿します。2026-11-16 から
  `gitlab-ee` のウクライナ語の文字列を対象に毎日実行しており、`gitlab-mfes` にも拡張する必要があります。

2026-09-01 時点では、ローカリゼーションチームは当面 Crowdin AI を使い、その後に仕様を使う方向で検討していました。
2026-11-17 に[作業アイテム 920](https://gitlab.com/gitlab-com/localization/localization-team/-/work_items/920)をクローズし、MFE の文字列には翻訳ハーネスを使う可能性が高いとしました。まだ未決定で、決定内容は
[作業アイテム 916](https://gitlab.com/gitlab-com/localization/localization-team/-/work_items/916)に記録します。

どの案を採用してもパイプラインは変わりません。翻訳はすべて Crowdin に書き込み、Crowdin での承認を必須としたうえで、
`pull-translations` で取得し、同じ検証を経て取り込みます（決定 8 のステップ 3）。

### 8. 翻訳に対する制御を 3 段階で強化する {#8-control-over-translations-tightens-in-three-steps}

Vue は `{{ t() }}` をエスケープするため、不適切な翻訳でスクリプトを実行することはできません。ただし、誤解を招く
文言を表示したり、文字列が `v-safe-html` に渡された箇所でリンクを表示したりできます。ユーザーが信頼する同一オリジンの
文言ですが、マーケットプレイスのロック MR でレビューするのはダイジェストです。現時点では、Crowdin トークンを持つ
リポジトリは他のリポジトリのファイルを上書きできます（決定 2）。また、`gitlab-mfes` は未承認の翻訳を
エクスポートするため、レビューを担うのは翻訳の MR をマージする人だけです。ローカリゼーションチームは、開発者が翻訳を
レビューする前提ではありません。

各ステップは、それを必要とする変更に合わせて進めます。

1. **現在**、モノリスの `PoLinter` と同様に、`check-translations` で `<` と `>` を含む翻訳を拒否します。
   現時点の PoC にはこのチェックがありません。
2. **2 つ目のリポジトリが参加する前に**、唯一の Crowdin トークンを中央ジョブで保持し、各リポジトリに翻訳の
   MR を作成します。モノリスに対する `crowdin-translation-sync` と同じやり方です。ADR 007 のモデルに従い、
   提供側は認証情報を保持しません。ジョブの担当者と、すべての MFE リポジトリへの Developer 権限を持つ
   ボットが必要です。
3. **モノリスからの取り込み以外でも翻訳を書き込むようになったら**（決定 7）、Crowdin での承認を必須にします。
   `exportApprovedOnly` をオンにし、決定 4 の取り込み処理で取り込んだ翻訳を承認します。すでにモノリスの翻訳と
   一致している翻訳も承認します。そうしなければこれらの翻訳はリリースされなくなります。他の翻訳は
   校正者が承認するとリリースされます。

ステップ 3 の開始条件はすでに満たされています。2026-11-01 からコミュニティの翻訳者が `gitlab-mfes` に翻訳を
書き込んでいます。この翻訳者による 183 件の繁体字中国語訳は、他のレビューを経ずに翻訳の MR を通じて
2026-11-03 にリリースされました。プロジェクトは公開されているため、Crowdin のどのユーザーも翻訳者として
参加できます。校正者はまだいません。`exportApprovedOnly` をいつオンにするかは、ローカリゼーションチームが
[作業アイテム 916](https://gitlab.com/gitlab-com/localization/localization-team/-/work_items/916)で決めます。
オンにしても、移植した文字列の繁体字中国語訳にはモノリスの翻訳が引き継がれます。残りの文字列は校正者が承認するまで
英語で表示されます。

検討した他の案は以下のとおりです。

- **リポジトリごとにトークンを持ち続ける。** シンプルですが、どのリポジトリも他のすべてのリポジトリのファイルに
  書き込めます。
- **リポジトリごとに Crowdin プロジェクトを 1 つ作る。** Crowdin のプロジェクト境界で分離できますが、
  メンバー、校正者、TM、用語集、すべてのローカリゼーションレポートを MFE ごとに用意する必要があります。

## 影響 {#consequences}

- すべての MFE は `locales/en.json` と `crowdin.yml` を持ち、英語の原文を渡して `t()` を呼び出します。
  移植するコードは codemod で変換します。
- PoC には 5 つの変更が必要です。抽出の対象をすべてのキーに広げ、`gitlab.pot` に含まれるかどうかで移植済みか
  判断し、取り込み処理による翻訳の削除を廃止し、翻訳中の HTML を拒否し、ロケールごとの複数形の語形数を検証します。
- プロダクト UI は 2 つの Crowdin プロジェクトで管理します。ローカリゼーションツールを 2 つ目のプロジェクトにも
  対応させる作業の時期は、ローカリゼーションチームが決めます。
- 原文の文字列は GitLab の共有 Crowdin プランの使用量に含まれます。モノリスにコピーが残っている間、移植した
  文字列は 2 回カウントされます。
- 決定 5 のボットによるタグ付けを導入するまでは、更新が少ない MFE の翻訳は、誰かがタグを付けるまで
  `main` で待機します。
- 2 つ目のリポジトリが参加する前に、中央の Crowdin ジョブの担当者を決める必要があります（決定 8）。
- `@gitlab/duo-ui` はモノリスで使われている間、ホストからの翻訳の注入を維持します。MFE 内では、
  vue-i18n のメッセージを `setConfigs({ translations })` に渡すブリッジができるまで、
  348 個のキーを英語で表示します
  （[作業アイテム 612825](https://gitlab.com/gitlab-org/gitlab/-/work_items/612825)）。
  モノリスと MFE で共有するすべてのライブラリに、同じ課題があります。
- 3 つ以上の語形を持つ言語では、複数形の処理が引き続き翻訳者の負担になります。
