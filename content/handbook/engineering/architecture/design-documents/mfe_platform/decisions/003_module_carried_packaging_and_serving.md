## 背景 {#context}

[設計ドキュメント](../_index.md)には、最初の 2 つの ADR が扱っていない目標が 1 つあります。
個別にデプロイされるサービスである LabBench モジュールには、GitLab シェルに UI を追加するための
標準的な方法が必要です。現状では、各モジュールが独自の統合を考案することになります。
将来、スタンドアロンの MFE を配布するマーケットプレイス自体もこのようなモジュールなので、
ここでの決定は、マーケットプレイスやレジストリが存在する前から
機能しなければなりません。

この ADR は、Caproni リグでモジュール同梱の MFE を初めてエンドツーエンドで動かし、
検証した決定を記録します。`bench` でビルドしたモジュールは、
Vue アプリケーションと API を含みます。GitLab はアプリケーションを検出し、
Admin サイドバーとページ内のスロットに配置して、自身のオリジン経由で配信し、
開発時にはモジュールの開発サーバーから再読み込みします。このアプリケーションのために
GitLab を変更することはありませんでした。

実装と議論:

- デモ動画と既知の問題を含む検証用 Issue:
  [作業アイテム 634099](https://gitlab.com/gitlab-org/gitlab/-/work_items/634099)
- GitLab 側: [マージリクエスト 262539](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/262539)
- モジュール側（`bench`）: [マージリクエスト 192](https://gitlab.com/gitlab-org/lab-bench/bench/-/merge_requests/192)
- 参照モジュール: [bench-mfe-demo](https://gitlab.com/gitlab-org/frontend/playground/bench-mfe-demo)

### 制約 {#constraints}

- **モジュールの検出機能がありません。** モノリスはデプロイ済みモジュールを検出できません。
  ソース一覧はモノリスの設定であり、この設計は
  その一覧だけで機能する必要があります。
- **単一ドメインはまだありません。** GATE がルーティングを提供するまでは、ブラウザーが
  アクセスできるのはモノリスが配信またはプロキシできるものだけです。ソースは
  クラスター内部に存在する可能性があります。
- **レジストリがありません。** マーケットプレイスは、まだ出荷されていないモジュールです。
  プロトコルは、事前登録の手順なしでモジュールを表示できる必要があります。
  そうでなければ、マーケットプレイス自体を立ち上げられません。
- **モジュールがリリースサイクルを管理します。** モジュールとその UI は、モジュールのリポジトリから
  一緒にリリースします。ADR 001 ではすでに、構造上これをポリレポとして
  扱っています。

## 決定事項 {#decisions}

### 1. すべての統合箇所に共通するソースプロトコル {#1-one-source-protocol-for-every-surface}

LabBench モジュール、将来のマーケットプレイス、静的ディレクトリのいずれであっても、
すべての MFE ソースは同じ 3 種類のものを配信します:

- `/-/mfe/index.json`: ソースに含まれるアプリケーションの一覧。それぞれの
  バージョン、マニフェストのパス、マニフェストの SHA-256 を含みます。
- `/-/mfe/<app>/<version>/gitlab-mfe-manifest.json`: エントリーファイル、
  各ファイルとそのダイジェスト、配置ブロックを含むサイドカーマニフェスト
  （スキーマ 1）。
- `/-/mfe/<app>/<version>/*`: ファイル。あるバージョンのファイルは変更されません。

このプロトコルが統合の接点です。これらのパスを配信するものはすべて
ソースなので、純粋な静的ソースでも API プロキシ以外のすべてに対応できます。
また、これによりモノリスは、実行中のモジュールではなくフィクスチャソースに対して
仕組みをテストできます（決定事項 5）。

**採用しなかった代替案:** GitLab に表示する前にアプリケーションを登録しておく必要のある
レジストリ。モジュールとその UI の間にサービスを追加することになり、
最初に表示される必要があるマーケットプレイスをホストできません。

**意図的な未決定事項:** モノリス内の JSON スキーマが現在要求するもの以外の、
マニフェストの正確なフィールド。LabBench の `Assembly.ui` フィールドは、
LabBench 内で別途 LB-D として記録します。

### 2. モノリス内のカタログとプルモデル {#2-catalog-in-the-monolith-pull-model}

`gitlab.yml` の `mfe.sources` にソースを列挙します。カタログは各ソースの
インデックスを読み、各マニフェストを JSON スキーマで検証し、
マニフェストのダイジェストを検証して、ダイジェストをキーにマニフェストをキャッシュします。統合した一覧は
短時間キャッシュし、読み取り時に再構築します。

**採用しなかった代替案:** モジュールが GitLab に登録情報をプッシュする方法、または
データベース内にソーステーブルを設ける方法。どちらも、まだ存在しない登録手順を
必要とします。モノリスにモジュール検出機能が導入されたら、いずれかがプルモデルを置き換える可能性があります。
それはこのプラットフォームの対象範囲外であり、その場合もマニフェストの
プロトコルは変わりません。

**既知の簡略化:** デモでは、TTL を 1 分、ソースごとのタイムアウトを 5 秒として、
Web リクエスト内でカタログを更新します。ソースが遅い、または停止していると、
1 分に 1 回ページが待たされます。デモ以外の用途で使う前に、更新を
Sidekiq の cron に移します。「影響」を参照してください。

### 3. GitLab のオリジンを通じた配信 {#3-delivery-through-the-gitlab-origin}

Workhorse は `send_url` を使い、カタログが解決したソースから
`/-/mfe/<app>/<version>/*` と `/-/mfe/<app>/api/*` を配信します。ブラウザーが通信する相手は
GitLab だけです。モジュールはクラスターネットワーク内に置いたままにでき、CSP を
モジュールごとに増やす必要はありません。

**採用しなかった代替案:** ブラウザーが CORS でモジュールからファイルを読み込む方法、
または GitLab Pages 経由の配信。どちらもモジュールのオリジンをブラウザーに公開し、
モジュールごとに CSP とネットワーク到達性を必要とします。

将来、GATE がルーティング層で同じ特性を提供する可能性があります。その場合、
この決定はエッジで置き換えられ、Workhorse より上の層は何も変わりません。

### 4. モジュールが配置を宣言し、モノリスが語彙を管理する {#4-the-module-declares-its-placement-the-monolith-owns-the-vocabulary}

UI の `package.json` の `gitlabMfe.placement` ブロックには、`navigation`、
`routes`、`slots` があります。ビルド時にこのブロックをマニフェストへコピーします。GitLab はマニフェストから読み込み、
そのコードにはアプリケーション名を含めません。

責任を次のように分担します:

- **モノリスが語彙を管理します。** 存在するパネル（現時点では `admin`）、
  存在するスロット（現時点では `dashboard_top`）、エントリが要求できる
  権限（現時点では `admin`）を管理します。ページは `= mfe_slot('name')` でスロットを確保します。
  マニフェストで指定できるのは、モノリスが公開した場所だけです。
- **モジュールが使用する場所を宣言します。** 追加するパネルエントリ、
  埋めるスロット、各公開エントリーポイントをマウントする場所を宣言します。
- **モノリスが調停します。** モノリス内の予約リストは、ファーストパーティーの機能が
  使用する場所（ルート、スロット、サイドバーの
  `item_id`）を指定します。予約済みの場所に配置されるマニフェストエントリは警告とともに破棄し、
  登録済みアプリケーションを描画します。未予約の場所では、`mfe.sources` の
  ソース順で優先順位を決め、すべての衝突を記録してカウントします。
  黙って優先順位を適用することは認めません。

予約リストと衝突のメトリクスはデモに含まれていません。これらは
モノリス側で最初に行う後続作業です。「影響」を参照してください。

**モジュールが宣言する理由。** モジュールをインストールする人は、モノリスのリリースを待たずに
予測可能な場所に表示されることを期待します。Jira の拡張モジュール、
VS Code の `contributes.menus`、Backstage のプラグインでは、いずれも拡張側が
ホストの公開された拡張ポイントを指定し、ホストが
ポイントの集合を管理して調停します。これがなければ、マーケットプレイスは自分自身の
Admin エントリを追加できず、新しいモジュールが表示されるたびにモノリスの MR を待つことになります。

**採用しなかった代替案:** アプリケーションごとに GitLab 内で配置を
設定する方法。利用側が、何をどこにマウントするかの対応を一元的に確認できるので、
読み取りもテストも容易であり、決して置き換えられてはならないファーストパーティーの
機能には適切なモデルです。予約リストはこの利点を維持します。
ただし、これだけを唯一のモデルにすると、マーケットプレイスを立ち上げられず、
モジュールごとにモノリスの MR が再び必要になります。

### 5. テストの責任分担はプロトコルに従う {#5-testing-ownership-follows-the-protocol}

モノリスの仕様テストは、実行中のモジュールには一切依存しません。モノリスは、
静的なインデックスとマニフェストを配信するフィクスチャソースに対して仕組みをテストします。
スロット X を宣言したアプリケーションがスロット X にマウントされること、予約済みの場所が
保護されること、衝突が記録されることをテストします。モジュールは、自身のパイプラインの
コントラクトテストとして、公開された JSON スキーマに対してマニフェストをテストします。必須のファーストパーティー
アプリケーションはモノリスの予約リストに記載し、
存在しなければ、そこで明確に失敗させます。

これにより、モジュールのリポジトリでの変更がモノリスの
`master` を壊すことを防ぎます。これが、モジュールによる配置宣言への主な反論でした。
双方がチェックアウトしたコードではなく、相手の公開されたコントラクトに対してテストするという
ADR 002 の方針とも整合しています。

### 6. 1 つのアプリケーションで複数のエントリーポイントを公開する {#6-one-application-several-exposes}

アプリケーションは、`./App`、`./DashboardWidget` などのエントリーポイントを公開します。
マニフェストは、公開エントリーポイントごとに配置を指定します。ナビゲーションエントリは使用する公開エントリーポイントを指定でき、
デフォルトは `./App` です。ルールは、運用と
バージョン管理が独立した単位ごとに 1 つのアプリケーションとすることです。

**採用しなかった代替案:** 配置ごとに 1 つのアプリケーションを設ける方法。常に
一緒に出荷するもののバージョンとマニフェストが増えてしまいます。

### 7. マウントのコントラクトと共有ランタイム {#7-mount-contract-and-shared-runtime}

各公開エントリーポイントは、`mount(el, props)` と `unmount(el)` をエクスポートします。ページ上のすべての
アプリケーションに、1 つの Module Federation ランタイムを使用します。GitLab は自身のインスタンスから
注入するクライアントを構築するため、アプリケーションが GitLab の内部実装をインポートしたり、
独自の HTTP クライアントを構築したりすることはありません。

**未決定事項:** ホストが何を注入するかと、アプリケーションが必要なものを
宣言するかどうか。デモでは、アプリケーションの API プロキシに結び付けた `axios` インスタンスを
仮のものとして渡します。記録されている懸念は、「シェルがすべてを与え、
アプリケーションが必要なものを取る」という形では、HAML の
データ属性が肥大化したのと同じことを繰り返す点です。望ましい方向性は、すでに
宣言の窓口となっているマニフェストにアプリケーションが必要とするクライアントを列挙し、
ホストが遅延してインスタンスを作成することです。最初のコントラクトは、2 つ目の利用者が現れた時点で、
後の ADR で確定します。

### 8. セレクターの接頭辞による CSS の分離 {#8-css-isolation-with-a-selector-prefix}

ビルド時に、各セレクターに `.mfe-<app>` という接頭辞を付けます。`:root`、`html`、
`body` はそのクラスに置き換えます。ホストはマウント要素にそのクラスを追加します。
`@keyframes` の名前はグローバルのままです。アプリケーションが実行時に追加するスタイルは
分離されません。

モノリスのスタイルは引き続きアプリケーション内に作用します。その対策は、
MFE 層に 2 つ目の仕組みを構築することではなく、Frontend
Decomposition の取り組みですでに進めているように、モノリス層でグローバルセレクターを
減らし続けることです。`.mfe-<app>` の境界でのリセットは、部分的な対策として考えられますが、
ここでは採用しません。

**採用しなかった代替案:** `@scope`。GitLab がサポートするブラウザーでは、
2028 年半ばより前に Baseline にはなりません。Shadow DOM は検討していません。スタイルを
完全に分離しますが、`@gitlab/ui` のグローバルスタイルを遮断し、フォーカスと
ポータルの動作を複雑にします。

### 9. 信頼モデル {#9-trust-model}

モジュールに同梱するアプリケーションは、そのモジュールと同じ信頼を持ちます。これは GitLab オリジン上の
ファーストパーティー JavaScript です。プロキシに到達できる各ユーザーは
モジュールの API を呼び出せるため、そのプロキシの背後での認可はモジュールの責任です。

マニフェスト内のダイジェストは、マニフェスト自体については検証し、
ファイルについてはキャッシュキーとして使います。GitLab は、Workhorse がストリーミングするバイト列を、
マニフェストに記載されたダイジェストと比較しません。これは見落としではなく、意図的に範囲を限定したものです。
ソースはインスタンス運用者による設定であり、モジュールの公開したダイジェストに対して
モジュールのバイト列の整合性を検証しても、信頼は増しません。
この経路にサブリソース完全性が存在すると想定しないでください。

## 影響 {#consequences}

- LabBench モジュールは `bench ui create` で UI ユニットを取得し、
  `bench build` がサイドカーマニフェストを書き込み、`dist/` を
  バイナリに埋め込みます。このバイナリがソースプロトコルを提供します。現時点でファイルを配信するのは
  Go アセンブリだけです。
- モノリスには、カタログ、Workhorse のルート、ホストランタイム、
  `mfe_slot`、カタログを読み込むパネルごとのメニューが加わります。すべて既存の
  `mfe_enabled` キルスイッチの制御下に置きます。
- モノリス側の後続作業は、順に、Sidekiq の
  cron でのカタログ更新、決定事項 4 の予約リストと衝突メトリクス、決定事項 5 のフィクスチャ
  ソースと仕様テスト、ソース間の名前衝突を解消するためのアプリケーション名へのモジュール名の接頭辞の追加、
  リリースによってカタログの TTL 1 回分の間に 404 が発生しないよう、モジュールが
  以前のバージョンも配信し続ける短い
  重複期間の設定です。
- モジュール側の後続作業: `bench build` が、バージョンの引き上げ時ではなくコンテンツの
  変更時に UI を再ビルドし、同一のバージョンを
  マニフェスト、インデックス、バイナリに書き込むようにします。
- 開発時の再読み込みは、外部ツール（portless）とそのルート
  ファイルに依存します。GitLab は開発時だけこのファイルを読み、存在しない場合は
  デプロイ済みアプリケーションを読み込みます。開発者ごとの設定が不要という条件も満たす
  代替手段ができるまで、この依存関係を
  受け入れます。
- LabBench の `Assembly.ui` スキーマフィールドは、GitLab を
  指定された利用者として LB-D に記録します。
- 後の ADR で、マウントのコントラクト（決定事項 7）と共有モジュールの
  戦略を確定します。デモでは、意図的にアプリケーションごとに Vue 3 を同梱します。
