## 背景 {#context}

現在、マイクロフロントエンドのフロントエンドを作成するツールとして、3 つが考えられます。CI や規約を備えた新しい GitLab
プロジェクトをセットアップするリポジトリジェネレーター、モジュールが UI を宣言した際に使う LabBench の CLI、
そしてプラットフォーム自体のツールです。ADR 004 が扱っているのは再利用可能なパッケージのライフサイクルで、
アプリケーションが有効なマイクロフロントエンドになるために必要なファイルは対象外です。ADR 004 のレビューでは、
各ツールでテンプレートエンジン（copier）を使ってひな形を生成するか、1 つの共有コマンドに委ねるかが未決定でした。

各ツールが独自のテンプレートを保持すると、同じ `rspack` 設定、`package.json` のメタデータ、CI の include、
契約のバージョン固定が 3 組存在し、契約のマイナーバージョンが変わるたびに乖離します（ADR 006）。
すると、提供側はどのツールから作り始めるかによって異なるひな形を受け取り、検証ツールはそのすべてを受け入れる
必要があります。

同じ課題はビルド後にもあります。ADR 003 では、モジュールが自身のマイクロフロントエンドをソースプロトコルに
従って配信すると定めています。ADR 007 では、この方法を標準とし、マーケットプレイスの対象をモジュールを持たない
マイクロフロントエンドに限定しています。ソースを構成する作業（全バージョンとデフォルトを記載するインデックス、
バージョンごとのサイドカーマニフェスト、`/-/mfe/<app>/<version>/` 以下のファイルの配置）はどのモジュールでも
同じです。LabBench アセンブリ以外のモジュールにも、この作業を手動で行わせないようにする必要があります。

### 制約 {#constraints}

- 生成されたアプリケーションは、生成した日に現行の契約に準拠している必要があります。マニフェストのメタデータ、
  宣言されたクライアント、CI での検証、リリースジョブが対象です。
- リポジトリの構成は一様ではありません。LabBench モジュールでは Go のソースと並べて `ui/<name>` に UI を置き、
  パッケージのワークスペースでは `mfes/<name>` にアプリケーションを置きます。通常のリポジトリでは、
  ルートに 1 つのアプリケーションを置きます。
- ひな形生成を組み込むツールは CI でオフライン実行されるため、別のものを黙って生成するのではなく、
  理由を明示して失敗する必要があります。
- テンプレートは、実在するプラットフォームパッケージのバージョンを固定する必要があります。未公開の
  バージョンを固定したひな形は、生成直後から動作しません。
- LabBench アセンブリでも、別の技術で構築されたサービスでも、どのモジュールもプラットフォームのツールを
  使って自身のマイクロフロントエンドを配信できる必要があります。プラットフォームはどちらの提供側も同等にサポートします。

## 決定事項 {#decisions}

### 1. すべての構成で `@gitlab/mfe-scripts create --into` がフロントエンドをセットアップする {#1-gitlabmfe-scripts-create---into-owns-the-frontend-setup-everywhere}

このコマンドは、マイクロフロントエンドとしてアプリケーションをビルド、検証、リリースするために必要な
ものをすべて既存のディレクトリに書き出します。`gitlabMfe` パッケージメタデータ（名前、配置場所、クライアント）、
`@gitlab/mfe-shell` のプラグインを利用する `rspack` 設定、テストのセットアップ、契約テスト、
シェルの開発サーバーを実行する `dev` スクリプト、`mfe:validate` スクリプト、プラットフォームの CI テンプレートを
読み込む CI スニペットです。リポジトリから構成（`bench`、`workspace`、`plain`）を検出し、既存ファイルは
上書きしません。既存の `package.json` があれば、置き換えるのではなく内容をマージします。

プラットフォームパッケージの未公開バージョンを指定すると拒否するため、ひな形は必ず提供側が
インストールできるバージョンを参照します。

### 2. リポジトリジェネレーターはひな形を複製せず、コマンドを呼び出す {#2-repository-generators-call-it-they-do-not-copy-it}

新しい GitLab プロジェクト（CI、所有権、規約）を作成するジェネレーターは、マイクロフロントエンドを
選択肢として提供できます。その場合、独自のフロントエンドテンプレートを保持せず、リポジトリの作成後に
`mfe-scripts create --into` を呼び出します。ジェネレーターがリポジトリを管理し、プラットフォームが
アプリケーションのひな形を管理します。

### 3. LabBench はモジュールを担当し、フロントエンドを委譲する {#3-labbench-owns-the-module-side-and-delegates-the-frontend}

LabBench は、UI を持つモジュール固有の処理を引き続き担当します。アセンブリの `ui` フィールド、
構成済みのソースをモジュールのバイナリに組み込み、ADR 003 のソースプロトコルに従って配信する処理、
アプリケーションの開発サーバーを実行する開発タスクです。
宣言された UI のディレクトリがまだなければ、LabBench はモジュール名と構成を指定して、バージョンを**固定した**
`npx @gitlab/mfe-scripts@<version> create --into <dir>` を実行します。
ビルド時には、ビルド出力に対して `mfe-scripts source`（決定事項 4）を実行し、その生成物を組み込みます。
出力が有効なマイクロフロントエンドでなければ、ビルドを失敗させます。

LabBench は独自のひな形を保持しません。オフラインの CI や誤ったバージョン指定でひな形生成ツールを取得できない場合は、
後でプラットフォームに拒否されるアプリケーションを生成せず、理由を示すメッセージを出してビルドを
失敗させます。

### 4. `mfe-scripts source` がモジュールの配信用ソースを構成する {#4-mfe-scripts-source-lays-out-the-source-a-module-serves}

このコマンドは 1 つ以上のビルド済みアプリケーション（それぞれサイドカーマニフェストを含むディレクトリ）を受け取り、
ADR 003 のソース構成に従ってファイルを配置します。全アプリケーションについて、含まれる全バージョンとデフォルトを
`/-/mfe/index.json` に記載し、バージョンごとのサイドカーマニフェストとファイルを `/-/mfe/<app>/<version>/` 以下に
配置します。まずすべてのアプリケーションを検証し、無効なアプリケーションの配置は拒否します。モジュールは
そのディレクトリを埋め込むかマウントし、自身のオリジンから配信します。配信方法はモジュールに任されており、
同じディレクトリを静的ファイルサーバーから配信してもソースになります。マーケットプレイスのサイトも同じ構成で、
モジュールのビルド出力の代わりにロック済みのバージョンから生成します（ADR 007 の決定事項 4）。

これにより、LabBench アセンブリ、別の技術スタックで構築されたサービス、静的ディレクトリのいずれも
同じコードパスを通り、プロトコルの変更は 1 つのコマンドの変更で済みます。

### 5. 検証ツールと CI テンプレートはそれぞれ 1 つ {#5-one-validator-one-ci-template}

ビルド済みのディレクトリ、配信中のソース、サイトのいずれについても、「有効なマイクロフロントエンド」の判定は
`mfe-scripts validate` に集約します。プラットフォームの CI テンプレートは、提供側のすべての
マージリクエストでこれを実行します。自身のマイクロフロントエンドを配信するモジュール向けにはソースを構成し、
マーケットプレイスの提供側ではタグが付くとリリースアセットをパッケージ化します（ADR 007）。
どのツールが生成したひな形にも、参照先を固定して同じテンプレートを組み込みます。

## 検討した代替案 {#alternatives-considered}

- **ツールごとに copier テンプレートを持つ。** 却下しました。契約の変更のたびに 3 組のフロントエンド設定を
  同期する必要があり、使い始めるツールによってひな形が異なります。
- **ADR 004 を改訂してアプリケーションのひな形生成を扱う。** 却下しました。ADR 004 が扱うのはツールキット内の
  再利用可能なパッケージのライフサイクルです。ここで決めるのは、どのツールがアプリケーションのファイルを
  管理するかであり、独立した記録にする価値があります。
- **オフライン用に LabBench に代替のひな形を持たせる。** 却下しました。代替のひな形は同期がずれていく 2 つ目の
  テンプレートになります。異なるアプリケーションを黙って生成するより、理由を示して失敗するほうが適切です。
- **モノリス内でひな形を生成する。** 却下しました。アプリケーションは設計上モノリスの外に存在し
  （ADR 003）、モノリスから提供側のリポジトリは見えません。

## 影響 {#consequences}

- 提供側は、新規リポジトリ、パッケージのワークスペース、LabBench モジュールのどこから始めても、
  同じアプリケーションのひな形を受け取ります。ひな形は生成された日から検証に合格します。
- 契約のマイナーバージョンが変わる際は、1 つのパッケージのテンプレートと検証ツールを変更します。
  委譲する各ツールは、固定したバージョンを 1 つ更新すればその変更を取り込めます。
- LabBench の CLI が担当するのは、モジュール固有の処理と外部コマンドの呼び出しに絞られます。テストでは、
  フロントエンドファイルの内容の代わりに、渡す引数が正確かを検証します。
- LabBench アセンブリ以外のモジュールも、LabBench と同じコマンドを使って自身のマイクロフロントエンドを
  配信します。マーケットプレイスは ADR 007 が定めるとおり、モジュールを持たないマイクロフロントエンドのソースです。
- ひな形を生成するツールは npm レジストリにアクセスできる必要があります。アクセスできないと、理由を明示して
  ビルドを失敗させます。エアギャップ環境でのひな形生成が必要になった場合は、別途決定します。
