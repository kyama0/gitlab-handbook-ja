## 目的 {#purpose}

この文書では、Organizations が何であり、何ではないか、また機能の構築を規定するルールを定義します。Organizations レイヤーに関するアーキテクチャと製品の意思決定における唯一の情報源です。

この憲章は、チームが足並みを乱さず迅速に進めるためにあります。パートナーチームが機能を提案するとき、エンジニアリング上の決定でトレードオフが明らかになったとき、ステークホルダーがスコープ変更を求めるとき、答えはここにあります。憲章がその状況を扱っていなければ、その場で判断するのではなく憲章に追記する必要があるという合図です。

パートナーチームは、この憲章を Organizations のハンドブック設計文書および関連する ADR と併せて使ってください。憲章は意思決定の枠組みです。ハンドブックは実装設計の参照資料です。

この文書の変更には Tenant Scale PM と engineering lead の承認が必要です。特に不変条件のセクションの変更には、engineering leadership と product leadership の承認が必要です。

## ユーザー種別と用語 {#user-types-and-terminology}

Organizations レイヤーは、Org レベルで 2 つの主要な顧客ユーザー種別、Org Admin と Org Member を定義します。ユーザー種別は、テナントレベルでその人がどのような立場かを示します。アクセスを付与する仕組みであるロールとは明確に区別されます。どちらのユーザー種別も、それ自体はロールではありません。Org Admin は Org Admin であることによって常時の権限を持ちますが、Org Member は Org のメンバーシップだけではいかなるアクセス権も持ちません。

**Org Admin。** 高い権限を持つ Org ユーザー種別です。Org Admin は Organization の全資産に対して、常時、完全な CRUD 権限を持ちます。対象には、管理エリア（請求、設定、ユーザー管理、利用権）、テナント全体のポリシー設定、パートナー製品が所有するリソースを含む Organization に紐付くすべてのリソースの読み取り、作成、更新、削除権限が含まれます。これにより、顧客が現在 TLG Owner（GitLab.com）および Instance Admin（Self-Managed と Dedicated）で持つ機能を維持します。リリース時の Org Admin は、これらを元に設定されます。Org Admin は、すでに持っていたもの以外は何も得ず、何も失いません。GitLab.com SaaS では、Org Admin と GitLab Instance Admin は異なるユーザーであることを想定しており、Instance Admin は必要に応じて Org Admin の操作を覆せます。Instance Admin は、Org Admin が持たない追加のインフラストラクチャのプロビジョニング権限と設定権限を保持します。Org Admin はテナント内で最上位の顧客権限ですが、GitLab が運用するインスタンス管理より上位ではありません。「Org Owner」ではなく「Org Admin」という名称を意図的に使っています。「Owner」はアクセスを付与する Group Owner ロールと衝突し、権限モデルが回避するために作られたアクセスの混乱を再び招くためです。

**Org Member。** 基本となる Org ユーザー種別です。Org Member であるとは、その Organization に所属することを意味します。ユーザーは、Organization 内の Group または Project に所属することで Org Member になります。Org Member は、Org 内で Group または Project のメンバーシップを持つための必須の前提条件ですが、それだけで Group、Project、リソースへのアクセス権が付与されることはなく、読み取りも含まれません。これは最初の関門であり、権限付与ではありません。アクセス権はロールに由来します。単一製品にスコープを限定した製品機能ロール、および既存の Group と Project のロールモデルです。Org Admin は Org Member を削除でき、これにより、ユニバーサルな取り消しを通じて Org 内のあらゆる場所でそのユーザーの実効権限が無効になります。

この文書全体で、これらのユーザー種別を一貫して使います。「ロール」という語は、アクセスを付与する仕組みに限定し、Org ユーザー種別の説明には決して使いません。緊急アクセスや管理者モードという表現は、不変条件に記載する例外的なアクセスパターンに限定し、標準のユーザー種別の定義には使いません。

## 1. Organizations とは {#1-what-organizations-are}

Organizations は、GitLab のテナントコンテナです。製品としての GitLab との顧客関係が存在する単位です。

Organizations は、次の役割を担います。

利用権の境界。Organization は、顧客のライセンス対象を定義します。サブスクリプションティア、シート割り当て、GitLab 資産全体のクレジット、利用権を持つ機能やアドオンの能力が含まれます。

ガバナンス、管理、可視性のレイヤー。Organization は、顧客の資産全体を貫く管理の背骨です。Org Admin は組織全体のポリシーを定め、Organization レベルの設定を構成し、Org メンバーシップを管理し、請求、クレジット管理、利用権の決定に責任を持ちます。Org Admin はさらに、Org に紐付く Group、Project、パートナー製品リソースの内容を含む資産全体に対して、常時、完全な CRUD 権限を持ちます（I5 を参照）。Org メンバーシップ自体は Group、Project、リソースへのアクセス権を付与しません。Group と Project レベルのアクセスは、引き続き標準の権限モデルを通じて行います（I6 を参照）。

単一のデプロイ単位。Organization は、GitLab.com SaaS、Self-Managed、Dedicated のすべてのデプロイ種別に共通するデプロイ単位です。.com の Cell、Self-Managed インスタンス、Dedicated インフラストラクチャのいずれで物理的に実行されるかに関係なく、顧客、管理者、開発者が扱う抽象化です。この基本要素には、基礎となるエンジニアリング要件があります。すべての機能が、すべてのデプロイ種別で Org 互換でなければなりません。あるデプロイ種別で動作しても、別の種別で Organization という基本要素を壊す機能は提供できません。最近公開されたエンジニアリング要件の Org 互換性が、これを実際の運用に落とし込むものであり、パートナーチームが Organizations レイヤーから引き継ぐ最も重要な制約です。

Org レベルの構成要素に対するアイデンティティのスコープ。SSO 設定、SCIM プロビジョニング、監査イベント、コンプライアンス設定、Org 全体のポリシーは Organization をスコープとします。

オブジェクト階層の最上位の親。構造モデルは Organization から Group、Project へと続きます。Group と Project は現在と同様に機能し続け、Organizations が新しい管理上の親レイヤーとなります。Project を Organization に直接作成することはありません。Group と Project は、その配下の運用レベルとして存続します。

移行単位。顧客が Cell 間、ティア間、またはプラットフォーム間を移動するとき、移行する対象は Organization です。

ここまでが、明示的に含まれるスコープです。それ以外のすべては、以降で説明します。

### 非分離 Organization と分離 Organization に関する補足 {#a-note-on-non-isolated-and-isolated-organizations}

GitLab.com では、Organization は非分離の状態から始まります。分離は、Organization が後から到達できる状態であり、このモデルの前提条件ではありません。Organization をスコープとするデータに依存する機能は、分離が常に有効だと仮定せず、Organization の境界ルールを適用する前に、現在の Organization の状態を確認する必要があります。分離時にしか成り立たない前提に依存する提案は、セクション 4 のワークフローに従ってレビューに回してください。

### 設定の配置場所 {#where-settings-live}

これは網羅的な一覧ではなく、例示です。以降の文書で使うガバナンス、ワークフロー、機能の配置に関する表現の基準となります。

| レベル | ここに置くもの |
|---|---|
| Organization | テナント全体のガバナンス、Organization レベルの設定、SSO と SCIM、監査とコンプライアンスの設定、利用権の状態。従来のインスタンスレベルの機能の大半と、一部のトップレベルグループの機能がここへ移ります。 |
| Group | 権限、ワークフロー、Project 階層、チームのナビゲーション、Group 設定。現在と同様に動作します。 |
| Project | リポジトリ、Issue、マージリクエスト、パイプライン、Project 設定。現在と同様に動作します。 |

## 2. Organizations に含まれないもの {#2-what-organizations-are-not}

このセクションは、憲章の中でもより価値のある半分です。最も高くつくスコープ上の誤りは、Organizations に属するように聞こえても、実際は別の場所に属する機能、あるいはまだどこにも属さない機能から生じます。

Organizations は、次のものではありません。

Group の代替。Group は、Organization 内の主要な構造単位であり続けます。権限、ワークフロー、Project 階層、チームのナビゲーションは、引き続き Group レベルで動作します。Organizations は Group 構造を平坦化したり、その責務を引き継いだりしません。

メンバーシップを通じた権限の起点。Organization のメンバーシップは、その中の Group や Project のメンバーシップを意味しません。Org メンバーシップは Group、Project、リソースへのアクセス権を一切付与しません。Group と Project レベルのアクセスは、引き続き標準の権限モデルによる明示的な付与を通じて行います。Org Admin は、Organization メンバーシップの帰結としてではなく、Org Admin ユーザー種別に結び付いた管理権限として、資産全体に常時、完全な CRUD 権限を持ちます（I5 を参照）。この区別は根幹を支えるものです。Org メンバーシップ自体をアクセスの仕組みに変えることなく、TLG Owner と Instance Admin の機能を維持します。

リソースの紐付け先。Issue、エピック、マージリクエスト、リポジトリ、パイプライン、その他の作業成果物は、Organization ノードに紐付きません。Organization が持つのはガバナンス、設定、可視性です。作業は User、Group、Project レベルにあります。これらの既存の紐付け先を使ってください。新しい紐付け先には慎重な設計とアーキテクチャレビューが必要です。承認済みの例外はありますが、設計上、まれなものとしています。

ワークフローの境界。Issue、マージリクエスト、CI/CD、デプロイ、その他のワークフロー構成要素は、Project と Group レベルで動作します。Organization レベルの Issue トラッカー、Organization レベルのパイプライン、Organization レベルのボードはありません。

横断的な機能の標準の配置先。機能が Organization 内の複数の Group にまたがる場合、標準の対応は、Org レベル版を新設することではなく、Group 間のナビゲーションを備えた Group レベルのスコープとすることです。Org レベルのスコープは、実質的にテナント全体のグローバルなスコープを必要とする機能に限られます。その基準は高く設定されています。

それ自体がユーザーのアイデンティティプロバイダー。ユーザーはメンバーシップを通じて Organization に所属します。SSO と SCIM は Organization レベルで動作します。基礎となるユーザーのアイデンティティモデルは、引き続き既存のアイデンティティアーキテクチャに従います。

エンドユーザー向けの請求 UI。請求を閲覧するのは Org Admin です。Project メンバーは Project を通じて請求を閲覧しません。Group メンバーは Group を通じて請求を閲覧しません。請求は Organization 内の 1 か所に置きます。

現在のエスカレーションを解決する手段。顧客やパートナーチームが「これは Org レベルに置く必要がある」と機能を要求した場合、最初の問いは、本当に Org レベルのスコープが必要か、それとも適切な UX があれば Group レベルで機能するかです。大半の要求は Group レベルで解決します。解決しないものが、セクション 4 の拡張モデルの候補となります。

フィーチャーフラグシステムや利用権システム。Organizations はテナントモデルです。ティア、利用権、展開状態によって異なる機能は、引き続き既存のフィーチャーフラグシステムと利用権システムで管理します。Organization は利用権の状態を保持しますが、利用権システムそのものにはなりません。

## 3. 不変条件 {#3-invariants}

これらは、正式なレビューなしには変更できない、アーキテクチャ上の確約です。Organizations レイヤーが今後数年の GitLab のテナントモデルの基盤となり、このレイヤーでのアーキテクチャの逸脱は元に戻すコストが高いため、定めています。

提案が不変条件に違反する場合、標準の回答は却下です。不変条件を変更する根拠を示す責任は提案者にあり、維持する根拠をチームが示す責任はありません。

**I1. 階層は Organization から Group、Project へと続きます。** Organization は Group の上位にあります。Group は Project の上位にあります。平坦化、逆転、それらの間に入る代替の構造レイヤーはありません。

**I2. 1 つの Organization に、1 つのデプロイ。** GitLab.com では、Organization は正確に 1 つの Cell に存在します。Self-Managed と Dedicated では、Organization はインスタンスです。いずれの場合も、Organization は単一のデプロイに収まり、Cell やインスタンスにまたがって分割されることはありません。Cell 間やインスタンス間の機能は、Organization レベルのスコープ外です。

**I3. Organization は利用権の境界であり、請求の紐付け先は移行段階にあります。** 利用権は Organization をスコープとします。請求はまだ Organization に紐付かず、リリース時にはトップレベルグループに残ります。目標状態では請求を Org レイヤーへ移しますが、Billing チームとの作業が完了するまでは、Org レベルの利用権と TLG レベルの請求という両モデルが共存します。この領域の機能は、Org レベルの請求が存在すると仮定してはならず、既存の TLG の請求構成要素と互換性を保つ必要があります。たとえば請求を Org に移さないと決めるなど、最終目標の変更にはアーキテクチャレビューが必要です。

**I4. 設定の継承は下向きに流れます。** Organization の設定は Group と Project に波及します。Group の設定はサブグループと Project に波及します。上向きの継承や、Group 間での同階層の継承はありません。

**I5. Org Admin はテナント内で最上位の顧客権限であり、Organization の全資産に対して、常時、完全な CRUD 権限を持ちます。** Organization 内では、テナントレベルのポリシー、設定、管理について、Org Admin より上位の権限を持つ顧客ユーザー種別やロールはありません。Org Admin の権限は、パートナー製品が所有するリソースを含め、Organization に紐付くすべてのリソースに対する常時の読み取り、作成、更新、削除です。これにより、顧客が現在 TLG Owner（GitLab.com）および Instance Admin（Self-Managed と Dedicated）で持つ機能を維持します。リリース時の Org Admin はこれらのロールを元に設定され、すでに持っていたもの以外は何も得ず、何も失いません。パートナー製品は、個別の権限付与なしに、すべてのリソースで Org Admin を権限のある操作主体として受け入れ、監査イベントで Org Admin の権限に基づく操作であることを正しく記録する必要があります。SaaS では、インスタンス管理については GitLab Instance Admin が Org Admin の上位に位置し、必要に応じて Org Admin の操作を覆せます。Organization をまたぐ管理がある場合、それは顧客ではなく GitLab 自身が運用する仕組みです。

**I6. Org メンバーシップはアクセス権ではありません。** Organization のメンバーシップは、その中の Group、Project、リソースへのアクセス権を付与せず、読み取りも含まれません。アクセス権は、Group と Project レベルの既存の権限モデル、または Org<>Product の接点での製品固有のロールを通じて明示的に付与します。暗黙的な Org レベルのアクセス権でこれを迂回しようとする機能は、アーキテクチャレビューを必要とし、原則として却下します。この不変条件は I5 と対になっています。Org Admin の権限は Org Admin ユーザー種別の特性であり、Org メンバーシップの特性ではありません。Org メンバーシップ自体は関門であり、権限付与ではありません。

**I7. Organization はリソースの紐付け先ではありません。** Issue、エピック、マージリクエスト、リポジトリ、パイプライン、その他の作業成果物は、Organization ではなく Group または Project に紐付きます。作業は User、Group、Project レベルにあります。新しい作業リソースを Org ノードに紐付けると提案する機能には、アーキテクチャレビューと、そのリソースを Group レベルに置けない理由の文書化が必要です。承認済みの例外はありますが、まれです。

**I8. Org レベルのエンティティは、Org 内の名前空間に属します。** Org レベルで作成するもの（設定、インテグレーション、ポリシー、監査構成）はすべてその Organization に属し、Organization 間で漏れ出しません。

**I9. 移行は契約です。** Organizations のデータモデルや階層を変更する場合は、既存顧客のために定義された移行経路を含める必要があります。顧客に状態の再作成を求める Org レベルの変更は提供しません。

**I10. すべてのデプロイ種別での Org 互換性は、譲れない条件です。** Org レベルで構築する機能は、GitLab.com SaaS、Self-Managed、Dedicated で動作する必要があります。デプロイ種別固有の Org 機能は認めません。ある機能が本当に 3 種類すべてで動作できない場合、その機能を Org レベルでは提供しません。これは、Org 互換性のエンジニアリング要件と関連するチェックによって徹底します。

不変条件の追加、削除、変更は、パートナーチームとの交渉ではなく、アーキテクチャレビューを通じて行います。engineering leadership、product leadership、Tenant Scale PM の承認が必要です。

## 4. 拡張モデル：認識合わせとレビューワークフロー {#4-extension-model-alignment-and-review-workflow}

パートナーチームは、Organizations に触れるたびに立ち止まってレビューを予定する必要があってはなりません。作業がモデルに適合する場合は、引き続き独立して構築することが標準です。このワークフローは、チームが判断に迷う場合、提案がモデルの範囲を広げる可能性がある場合、新しい Org パターンを導入する場合という、より少数のケースのためにあります。

モデルはシンプルです。提案が Org レベルの動作を新設または変更する可能性があれば、PREP レビューを開始します。PREP が受付経路となり、Tenant Scale がトリアージします。大半の項目は、適合しているという回答を迅速に得て、そのまま進めるはずです。新しいパターンを導入するか、不変条件に抵触する提案という、より限られたものだけをアーキテクチャレビューに回します。

パートナーチームは、このワークフローを Organizations のハンドブック設計文書および関連する ADR と併せて使ってください。それらには、この憲章で重複して記載しない実装レベルの詳細があります。

### ワークフローの進め方 {#how-the-workflow-works}

**1. パートナーチームが簡単な自己確認を行います。**
オーナー：Partner PM と EM。タイミング：解決策が固まる前。

自己確認は、意図的にシンプルにしています。チームは次を問いかけます。

- 本当に Org レベルのスコープが必要ですか。それとも、UX を改善した Group レベルのスコープで問題を解決できますか。
- 新しい Org レベルのエンティティ、設定、権限、ワークフローを導入しますか。
- 作業リソースや記録の正本となるシステムを Org ノードに直接紐付けますか。
- 階層、継承、請求、アイデンティティ、アクセスに関する憲章ルールの変更に依存しますか。
- 現在の Organization の状態を確認せず、分離時にしか成り立たない前提に依存しますか。
- 他チームが模倣しそうなパターンを導入しますか。

すべての答えが明らかに「いいえ」なら、チームはそのまま構築してください。いずれかが「はい」または「可能性あり」なら、PREP を開始してください。

**2. PREP を受付経路とします。**
オーナー：Partner PM。タイミング：Org レベルへの影響の可能性にチームが気付いた時点。

PREP Issue は短くしてください。小規模な設計文書にする必要はありません。Tenant Scale が正しく振り分けるために十分な背景情報だけが必要です。

- チームが構築したいもの
- Org レベルのスコープが必要かもしれない理由
- 憲章のどの部分が関連しそうか
- 既存パターン、新しいパターン、例外の可能性のいずれだとチームが考えるか
- UX の草案や技術メモがあれば、そのリンク

重要なのはタイミングです。実装にすでに着手してからではなく、早期に PREP を開始してください。

**3. Tenant Scale が PREP Issue をトリアージします。**
オーナー：Tenant Scale PM と engineering lead。タイミング：3 営業日以内に初回トリアージ。

Tenant Scale は Issue をレビューし、3 つの経路のいずれかに振り分けます。

| 経路 | 意味 | 対応 |
|---|---|---|
| 適合 | 提案が憲章に適合し、既存のパターンを使っています。 | Tenant Scale が PREP で適合を確認し、チームは進めます。 |
| 対象を絞ったレビュー | 提案はおそらく問題ありませんが、一部に議論や明確化が必要です。 | フィードバックは PREP 内に残します。チームは提案を更新し、懸念が解消したら進めます。 |
| アーキテクチャレビュー | 提案が新しいパターンを導入するか、不変条件に抵触するか、モデルとの間に大きな不整合を生じさせます。 | PREP がアーキテクチャレビューへの引き継ぎとなり、最終決定を同じスレッドに記録します。 |

これにより、通常のケースを軽く保ちつつ、判断が明白でない作業でもチームに明確な経路を提供できます。

**4. 常にアーキテクチャレビューが必要なもの。**

いくつかのカテゴリは、単なる実装上の選択ではないため、自己判断で通過させてはいけません。これらはモデル自体を変更する提案です。

次のものは、常にアーキテクチャレビューへ回します。

- Organization から Group、Project へと続く階層の変更
- Org メンバーシップを通じた Group、Project、リソースへのアクセス権の付与（I5 で認める正式な経路である Org Admin の常時 CRUD 権限を通じたものとは異なります）
- Issue、エピック、マージリクエスト、パイプライン、リポジトリ、同様の作業リソースの Org ノードへの直接の紐付け
- 継承モデルの迂回
- デフォルトで Org をまたぐ可視性を導入すること
- Org レベルの請求モデルの提供前に、それが存在すると仮定すること
- Group レベルに置くべきものに Org レベルのスコープを提案すること
- Org Admin を上回る製品内独自の権限を新設すること

これらは、この憲章が防止しようとしている、高くつく誤りです。

### 自動化に関する補足 {#a-note-on-automation}

このワークフローの一部は、時間をかけて自動化するべきです。明確な例は、機能が作業リソースを Org ノードに直接紐付けていないか、サポートされていない請求の動作を前提にしていないかのチェックです。ただし、このプロセスは、まだ存在しないツールに依存してはいけません。PREP を使って今日から機能し、時間とともに自動化を進められるワークフローにしてください。

### 意思決定の記録 {#decision-record}

PREP が記録の正本です。Issue の最終状態から、提案が次のどれに該当するかを容易に判断できるようにします。

- 適合
- 対象を絞ったレビュー後に承認
- アーキテクチャレビューへエスカレーション
- 理由を添えて却下

提案によって再利用可能な Org パターンが確立した場合、Tenant Scale はそのパターンを憲章または補足ガイダンスに追記してください。複数のチームが同じ曖昧な領域に繰り返し直面するなら、各チームに同じ議論を繰り返させるのではなく、文書を改善してください。

### 実用的な判断基準 {#practical-rule-of-thumb}

- 作業が明らかにモデルに適合するなら、構築します。
- チームが判断に迷うなら、PREP を開始します。
- 提案がモデルを変更するなら、アーキテクチャレビューに回します。

ワークフローはこれだけです。

## 5. 決定権 {#5-decision-rights}

- 憲章の変更（不変条件以外のセクション）：Tenant Scale PM と engineering lead。
- 不変条件の変更：engineering leadership、product leadership、Tenant Scale PM。アーキテクチャレビューを通じて行います。
- PREP トリアージ：Tenant Scale PM と engineering lead。受付から 3 営業日以内。
- アーキテクチャレビューの決定：アーキテクチャレビュー参加者。理由とともに PREP に記録します。
- 憲章または補足ガイダンスへのパターン追加：Tenant Scale engineering lead。ユーザーに見える影響については PM の承認が必要です。
- Org と Group のどちらかの判断：自己確認と憲章で解決しない場合、Tenant Scale PM。
- ロードマップの優先順位付け：パートナーチームの需要とプラットフォームの対応能力を考慮し、Tenant Scale PM。
- 権限戦略（Org レベルのロール、割り当てロジック、常時 CRUD 権限の調整）：Tenant Scale PM と連携して AuthZ PM。憲章の不変条件（I5、I6、I7）が境界を定め、その内部のモデルは AuthZ が所有します。

## 6. この憲章の v1 で意図的にスコープ外とするもの {#6-deliberately-out-of-scope-for-v1-of-this-charter}

後の改訂に延期した項目：

- 分離のロードマップとアーキテクチャ上の扱い。
- 複数の Organization にまたがる機能（Org 間のナビゲーション、Org 間のレポート）。ロードマップにはなく、ここでは扱いません。
- Org 間の移行、統合、分割のフロー。将来の必要性は認識していますが、ここでは仕様を定めません。
- Teams の具体的なデータモデル。Teams 設計文書で扱うため、参照はしても重複して記載しません。
- Org レベルの請求：クレジットのプール、管理エリアでの利用権のレビューと調整、請求の紐付け先を TLG から Organization へ移すこと。これは Billing チームとの進行中の作業であり、初回リリースには含みません。完了するまでは請求は TLG に紐付いたままで、最終的な設計では、Org レベルの利用権と TLG レベルの請求が共存する移行状態を考慮する必要があります。
- Group と Project のロールモデルの変更。リリース時のスコープ外です。Org<>Product のロール UI で明らかになった衝突は、すべて PREP を通じて扱います。

## 7. この文書の使い方 {#7-how-to-use-this-document}

Tenant Scale のチームメンバー向け：これは、アーキテクチャに関するあらゆる議論の背骨です。根幹を支えると思われる決定を憲章が扱っていない場合は、その場限りのチャネルで決めずに追記を提案してください。

パートナーチーム向け：Org 関連の作業を提案する前に、セクション 1 から 4 を読んでください。セクション 4 の拡張モデルは、大半の要求にとって適切な入口です。Organizations のハンドブック設計文書と関連する ADR と併せて使ってください。

リーダーシップとステークホルダー向け：セクション 3 が、アーキテクチャ上の確約に異議を唱えたり、拡張したりする場所です。文書の残りは、そこから導かれます。

質問、提案、異論は `#g_organizations` チャネルに寄せてください。憲章への異論は有益な意見です。憲章を迂回することは、そうではありません。
