## 目的 {#purpose}

このドキュメントは、Organization が何であり、何ではないか、そして機能を構築する際に従うルールを定義します。Organization レイヤーに関するアーキテクチャとプロダクトの意思決定における唯一の情報源です。

この憲章は、チームが足並みを乱さずに迅速に進むためにあります。連携先チームが機能を提案するとき、エンジニアリング上の意思決定でトレードオフが明らかになったとき、ステークホルダーがスコープの変更を求めるとき、その答えはここにあります。憲章がその状況を扱っていなければ、その場しのぎで対応するのではなく、憲章に追記すべきという合図です。

連携先チームは、この憲章を Organization のハンドブック設計文書および関連する ADR と併せて使用してください。憲章は意思決定の枠組みであり、ハンドブックは実装設計の参照資料です。

このドキュメントの変更には、Tenant Scale PM と engineering lead の承認が必要です。特に不変条件セクションの変更には、エンジニアリングとプロダクトのリーダー層による承認が必要です。

## ユーザータイプと用語 {#user-types-and-terminology}

Organization レイヤーは、Org レベルの主要な顧客ユーザータイプとして Org Admin と Org Member の 2 つを定義します。ユーザータイプは、その人がテナントレベルでどのような立場にあるかを表します。アクセスを付与する仕組みであるロールとは、明確に区別される別のものです。どちらのユーザータイプも、それ自体はロールではありません。Org Admin は、Org Admin であることに基づいて常時の権限を持ちます。Org Member は、Org のメンバーであることだけではアクセス権を持ちません。

**Org Admin。** 特権を持つ Org ユーザータイプです。Org Admin は、Organization の全資産に対して、常時の完全な CRUD 権限を持ちます。対象は、管理エリア（請求、設定、ユーザー管理、エンタイトルメント）、テナント全体のポリシー設定、および連携プロダクトが所有するリソースを含む、Organization に関連付けられたすべてのリソースへの読み取り、作成、更新、削除権限です。これにより、顧客が現在 TLG Owner（GitLab.com）や Instance Admin（Self-Managed と Dedicated）として持っている機能が維持されます。ローンチ時の Org Admin は、これらのロールから初期設定されます。Org Admin がそれまで持っていなかった権限を得ることも、失うこともありません。GitLab.com SaaS では、Org Admin と GitLab Instance Admin は別のユーザーであることを想定しており、必要な場合は Instance Admin が Org Admin の操作に優先する操作を行えます。Instance Admin は、Org Admin が持たない追加のインフラプロビジョニングと設定の権限を引き続き持ちます。Org Admin はテナント内で最高の顧客権限を持ちますが、GitLab が運用するインスタンス管理より上位ではありません。「Org Owner」ではなく「Org Admin」という名称を使うのは意図的です。「Owner」は、アクセスを付与する Group Owner ロールと衝突し、この権限モデルが避けるために作られたアクセスの混乱を再び招くからです。

**Org Member。** 基本となる Org ユーザータイプです。Org Member であることは、その Organization に所属していることを意味します。ユーザーは、Organization 内のグループまたはプロジェクトに所属することで Org Member になります。Org 内のグループやプロジェクトのメンバーシップを持つには、Org Member であることが前提条件ですが、それだけでは、読み取りを含め、どのグループ、プロジェクト、リソースへのアクセスも付与されません。これは最初の関門であり、権限の付与ではありません。アクセスは、単一プロダクトにスコープされたプロダクト機能ロールと、既存のグループおよびプロジェクトのロールモデルから得られます。Org Admin は Org Member を削除でき、その結果、全体にわたる失効処理によって、そのユーザーの実効権限が Org 内のあらゆる場所で無効化されます。

このドキュメント全体を通じて、これらのユーザータイプを一貫して使用します。「ロール」という言葉はアクセスを付与する仕組みにのみ使用し、Org のユーザータイプを表すためには決して使用しません。緊急アクセスや管理者モードに関する表現は、不変条件で説明する例外的なアクセスパターンにのみ使用し、デフォルトのユーザータイプの定義には使用しません。

## 1. Organization が担うもの {#1-what-organizations-are}

Organization は、GitLab のテナントコンテナです。プロダクトとしての GitLab と顧客との関係が成立する単位です。

Organization は次の役割を担います:

エンタイトルメントの境界。Organization は、顧客がどのライセンスを持つかを定義します。対象は、サブスクリプションティア、シートの割り当て、顧客の GitLab 資産全体のクレジット、および利用権のある機能や追加機能です。

ガバナンス、管理、可視性のレイヤー。Organization は、顧客の資産全体を通じた管理の軸です。Org Admin は、organization 全体のポリシーを設定し、Organization レベルの設定を構成し、Org メンバーシップを管理し、請求、クレジット管理、エンタイトルメントの決定を担当します。また、Org Admin は、Org に関連付けられたグループ、プロジェクト、連携プロダクトのリソースの内容を含む、全資産に対する常時の完全な CRUD 権限を持ちます（I5 を参照）。Org メンバーシップ自体は、グループ、プロジェクト、リソースへのアクセスを付与しません。グループとプロジェクトレベルのアクセスは、引き続き標準の権限モデルを通じて付与されます（I6 を参照）。

単一のデプロイ単位。Organization は、GitLab.com SaaS、Self-Managed、Dedicated のすべてのデプロイタイプに共通するデプロイ単位です。物理的に稼働している場所が .com 上の Cell、Self-Managed インスタンス、Dedicated のインフラのいずれであっても、顧客、管理者、開発者が扱う抽象化です。このプリミティブには、基礎となるエンジニアリング要件があります。すべての機能は、すべてのデプロイタイプで Org と互換性を持たなければなりません。あるデプロイタイプでは動作しても、別のタイプで Organization プリミティブを壊す機能は出荷できません。Org 互換性は、これを運用に落とし込むために最近公開されたエンジニアリング要件であり、連携先チームが Organization レイヤーから引き継ぐ最も重要な制約です。

Org レベルの構成要素のアイデンティティスコープ。SSO 設定、SCIM プロビジョニング、監査イベント、コンプライアンス設定、Org 全体のポリシーは、Organization にスコープされます。

オブジェクト階層の最上位の親。構造モデルは、Organization、グループ、プロジェクトの順です。グループとプロジェクトは引き続き現在と同じように機能し、Organization が新たな管理上の親レイヤーになります。Organization 内に直接プロジェクトを作成することはありません。グループとプロジェクトは、その下の運用レベルとして存続します。

移行の単位。顧客が Cell 間、ティア間、プラットフォーム間を移動するとき、移行するのは Organization です。

ここまでが、担う役割として定めるスコープです。それ以外は、以下の内容によって説明します。

### 非隔離と隔離済みの Organization に関する注記 {#a-note-on-non-isolated-and-isolated-organizations}

GitLab.com では、Organization は非隔離の状態で始まります。隔離は、後から Organization が到達できる状態であり、モデルの前提条件ではありません。organization スコープのデータに依存する機能は、隔離が常に有効だと仮定するのではなく、organization の境界ルールを強制する前に現在の organization の状態を確認しなければなりません。隔離されていることだけを前提とする提案は、セクション 4 のワークフローに従ってレビューに回してください。

### 設定の配置場所 {#where-settings-live}

これは例示であり、網羅的なものではありません。ガバナンス、ワークフロー、機能の配置について、このドキュメントの他の箇所で使う表現の基準となります。

| レベル | ここに置くもの |
|---|---|
| Organization | テナント全体のガバナンス、Organization レベルの設定、SSO と SCIM、監査とコンプライアンスの設定、エンタイトルメントの状態。従来のインスタンスレベルの機能の大部分と、一部のトップレベルグループの機能は、ここに移動します。 |
| グループ | 権限、ワークフロー、プロジェクト階層、チームのナビゲーション、グループ設定。現在と同じように機能します。 |
| プロジェクト | リポジトリ、Issue、マージリクエスト、パイプライン、プロジェクト設定。現在と同じように機能します。 |

## 2. Organization が担わないもの {#2-what-organizations-are-not}

このセクションは、憲章の中でもより価値の高い部分です。最もコストの高いスコープの誤りは、Organization に属するように聞こえても、実際には別の場所に属する機能や、まだどこにも属すべきでない機能から生じます。

Organization は、次のものではありません:

グループの代替。グループは、引き続き Organization 内の主要な構造単位です。権限、ワークフロー、プロジェクト階層、チームのナビゲーションは、引き続きグループレベルで機能します。Organization は、グループ構造を平坦化したり、その責務を引き継いだりしません。

メンバーシップによる権限の起点。Organization に所属していても、その内部のいずれかのグループやプロジェクトに所属していることにはなりません。Org メンバーシップは、どのグループ、プロジェクト、リソースへのアクセスも付与しません。グループとプロジェクトレベルのアクセスは、引き続き標準の権限モデルによる明示的な付与を通じて得られます。Org Admin は、Org Admin ユーザータイプに結び付いた管理権限として、全資産に対する常時の完全な CRUD 権限を持ちます（I5 を参照）。これは Organization メンバーシップに伴うものではありません。この区別は、モデルの根幹を支えます。Org メンバーシップ自体をアクセスの仕組みに変えることなく、TLG Owner と Instance Admin の機能を維持するためです。

リソースの関連付け先。Issue、エピック、マージリクエスト、リポジトリ、パイプライン、その他の作業成果物を Organization ノードに関連付けることはありません。Organization は、ガバナンス、設定、可視性を担います。作業は、ユーザー、グループ、プロジェクトレベルに置きます。これらの既存の起点に関連付けてください。新しい起点には慎重な設計が必要であり、アーキテクチャレビューを受けなければなりません。承認された例外はありますが、意図的に少数に抑えています。

ワークフローの境界。Issue、マージリクエスト、CI/CD、デプロイ、その他のワークフローの構成要素は、プロジェクトとグループレベルで機能します。Organization レベルの Issue トラッカー、Organization レベルのパイプライン、Organization レベルのボードはありません。

横断的な機能のデフォルトの配置先。ある機能が Organization 内の複数のグループにまたがる場合、デフォルトの対応は、Org レベル版を新設することではなく、グループ間のナビゲーションを備えたグループレベルのスコープにすることです。Org レベルのスコープは、テナント全体のグローバルなスコープが実質的に必要な機能に限ります。その基準は高く設定します。

それ自体がユーザー ID プロバイダーとなるもの。ユーザーは、メンバーシップを通じて Organization に所属します。SSO と SCIM は Organization レベルで機能します。基盤となるユーザー ID モデルは、引き続き既存の ID アーキテクチャによって管理されます。

エンドユーザー向けの請求 UI。請求情報を見るのは Org Admin です。プロジェクトメンバーがプロジェクトを通じて請求情報を見ることはありません。グループメンバーがグループを通じて請求情報を見ることもありません。請求は、Organization 内の 1 か所に置きます。

目先のエスカレーションを解決するための手段。顧客や連携先チームが「これは Org レベルに置く必要がある」という形で機能を求めたとき、最初に問うのは、本当に Org レベルのスコープが必要なのか、それとも適切な UX があればグループレベルで機能するのかということです。ほとんどの要求はグループレベルで解決します。そうならないものが、セクション 4 の拡張モデルで扱う候補になります。

フィーチャーフラグやエンタイトルメントのシステム。Organization はテナントモデルです。ティア、エンタイトルメント、ロールアウト状態によって異なる機能は、引き続き既存のフィーチャーフラグとエンタイトルメントのシステムで管理します。Organization は、エンタイトルメントの状態を保持します。エンタイトルメントシステムそのものになるわけではありません。

## 3. 不変条件 {#3-invariants}

これらは、正式なレビューなしに変更できないアーキテクチャ上の約束です。Organization レイヤーは、今後数年にわたる GitLab のテナントモデルの基盤であり、このレイヤーでのアーキテクチャの逸脱を元に戻すには大きなコストがかかるため、設けています。

提案が不変条件に違反する場合、デフォルトの回答は却下です。不変条件を維持する理由をチームが示すのではなく、変更する理由を提案者が示す責任があります。

**I1. 階層は Organization、グループ、プロジェクトの順です。** Organization はグループの上位にあり、グループはプロジェクトの上位にあります。平坦化、逆転、それらの間への代替の構造レイヤーの追加はありません。

**I2. 1 つの Organization に 1 つのデプロイです。** GitLab.com では、Organization は厳密に 1 つの Cell に存在します。Self-Managed と Dedicated では、Organization がインスタンスです。いずれの場合も、Organization は単一のデプロイを占め、Cell 間やインスタンス間に分割されることはありません。Cell 間やインスタンス間にまたがる機能は、Organization レベルではスコープ外です。

**I3. Organization はエンタイトルメントの境界であり、請求の関連付け先は移行途上にあります。** エンタイトルメントは Organization にスコープされます。請求はまだ Organization に関連付けられておらず、ローンチ時にはトップレベルグループに残ります。目標とする状態では請求を Org レイヤーに移しますが、Billing チームとの作業が完了するまでは、Org レベルのエンタイトルメントと TLG レベルの請求という 2 つのモデルが共存します。この領域の機能は、Org レベルの請求が存在すると仮定せず、既存の TLG の請求の仕組みとの互換性を維持しなければなりません。たとえば、請求を Org に移さないと決めるなど、最終的な目標を変更する場合は、アーキテクチャレビューを受けます。

**I4. 設定の継承は下方向に流れます。** Organization の設定は、グループとプロジェクトに引き継がれます。グループの設定は、サブグループとプロジェクトに引き継がれます。上方向への継承や、グループ間の同列の継承はありません。

**I5. Org Admin はテナント内で最高の顧客権限を持ち、Organization の全資産に対する常時の完全な CRUD 権限を持ちます。** Organization 内のどの顧客ユーザータイプやロールも、テナントレベルのポリシー、設定、管理において Org Admin より上位の権限を持ちません。Org Admin の権限は、連携プロダクトが所有するリソースを含む、Organization に関連付けられたすべてのリソースへの常時の読み取り、作成、更新、削除権限です。これにより、顧客が現在 TLG Owner（GitLab.com）や Instance Admin（Self-Managed と Dedicated）として持っている機能が維持されます。ローンチ時の Org Admin は、それらのロールから初期設定され、それまで持っていなかった権限を得ることも、失うこともありません。連携プロダクトは、対象を指定した権限付与なしに、いずれのリソースについても Org Admin を権限のある操作主体として受け入れなければならず、監査イベントではその権限が Org Admin に基づくことを正しく記録しなければなりません。SaaS では、インスタンス管理に関して GitLab Instance Admin が Org Admin の上位に位置し、必要な場合は Org Admin の操作に優先する操作を行えます。Organization 間の管理が存在する場合、それは顧客ではなく、GitLab 自身が運用する仕組みです。

**I6. Org メンバーシップはアクセスではありません。** Organization に所属していても、読み取りを含め、その内部のどのグループ、プロジェクト、リソースへのアクセスも付与されません。アクセスは、グループとプロジェクトレベルの既存の権限モデル、または Org<>Product の接点におけるプロダクト固有のロールを通じて、明示的に付与されます。Org レベルの暗黙のアクセスによってこれを回避しようとする機能は、アーキテクチャレビューが必要であり、デフォルトでは却下されます。この不変条件は I5 と対を成します。Org Admin の権限は Org Admin ユーザータイプの性質であり、Org メンバーシップの性質ではありません。Org メンバーシップ自体は関門であり、権限の付与ではありません。

**I7. Organization はリソースの関連付け先ではありません。** Issue、エピック、マージリクエスト、リポジトリ、パイプライン、その他の作業成果物は、Organization ではなくグループやプロジェクトに関連付けます。作業は、ユーザー、グループ、プロジェクトレベルに置きます。新しい作業リソースを Org ノードに関連付ける提案をする機能は、アーキテクチャレビューを受け、リソースをグループレベルに置けない理由を文書化する必要があります。承認された例外はありますが、少数です。

**I8. Org レベルのエンティティは、Org 内の名前空間に属します。** Org レベルで作成したもの（設定、インテグレーション、ポリシー、監査設定）は、その Organization に属し、Organization 間に漏れ出すことはありません。

**I9. 移行は契約です。** Organization のデータモデルや階層への変更には、既存顧客向けの移行経路の定義を含めなければなりません。顧客が状態を作り直さなければならない Org レベルの変更は出荷しません。

**I10. すべてのデプロイタイプにわたる Org 互換性は、交渉の余地がありません。** Org レベルで構築する機能は、GitLab.com SaaS、Self-Managed、Dedicated で動作しなければなりません。デプロイタイプに固有の Org 機能は認められません。3 つすべてではどうしても動作できない機能は、Org レベルでは出荷しません。これは、Org 互換性のエンジニアリング要件と、それに関連するチェックによって強制されます。

不変条件の追加、削除、変更は、連携先チームとの交渉ではなく、アーキテクチャレビューを通じて行います。エンジニアリングとプロダクトのリーダー層、および Tenant Scale PM の承認が必要です。

## 4. 拡張モデル: 合意形成とレビューのワークフロー {#4-extension-model-alignment-and-review-workflow}

連携先チームが Organization に触れるたびに作業を止めてレビューを予定する必要はないはずです。作業がモデルに適合する場合は、引き続き独立して構築することをデフォルトとすべきです。このワークフローは、チームが判断に迷う場合、提案がモデルの範囲を広げる可能性がある場合、新しい Org のパターンを導入する場合という、より少数のケースのためにあります。

モデルは単純です。提案によって Org レベルの動作を新設または変更する可能性があれば、PREP レビューを開始します。PREP が受付経路となり、Tenant Scale がトリアージします。ほとんどの項目には、適合しているという回答をすぐに返し、先へ進められるべきです。新しいパターンを導入したり、不変条件に関わったりする、さらに少数の提案だけをアーキテクチャレビューに回すべきです。

連携先チームは、このワークフローを Organization のハンドブック設計文書および関連する ADR と併せて使用してください。これらは、この憲章では重複して記載しない実装レベルの詳細を扱います。

### ワークフローの進め方 {#how-the-workflow-works}

**1. 連携先チームが簡単なセルフチェックを行います。**
オーナー: 連携先の PM と EM。タイミング: 解決策が確定する前。

セルフチェックは、意図的に単純なものにしています。チームは次を確認します:

- 本当に Org レベルのスコープが必要か、それとも UX を改善したグループレベルのスコープで問題を解決できるか。
- 新しい Org レベルのエンティティ、設定、権限、ワークフローを導入するか。
- 作業リソースや記録の正本となるシステムを、Org ノードに直接関連付けるか。
- 階層、継承、請求、ID、アクセスに関する憲章のルールの変更に依存するか。
- 現在の organization の状態を確認せず、隔離されていることだけを前提とするか。
- 他のチームが模倣する可能性の高いパターンを導入するか。

答えが明らかにすべて「いいえ」であれば、そのまま構築を進めてください。いずれかが「はい」または「その可能性がある」であれば、PREP を開始してください。

**2. PREP が受付経路となります。**
オーナー: 連携先の PM。タイミング: Org レベルへの影響の可能性に気付いたらすぐ。

PREP の Issue は簡潔にしてください。小さな設計文書にする必要はありません。Tenant Scale が正しく振り分けるために、次の十分な背景情報があればよいのです:

- チームが何を構築したいか
- Org レベルのスコープが必要かもしれない理由
- 憲章のどの部分が関連しそうか
- チームは既存のパターン、新しいパターン、または例外の可能性があるもののどれだと考えているか
- UX のドラフトや技術メモがあれば、そのリンク

大切なのはタイミングです。実装がすでに進行してからではなく、早い段階で PREP を開始してください。

**3. Tenant Scale が PREP の Issue をトリアージします。**
オーナー: Tenant Scale PM と engineering lead。タイミング: 最初のトリアージは 3 営業日以内。

Tenant Scale は Issue をレビューし、次の 3 つの経路のいずれかに振り分けます。

| 経路 | 意味 | 次に行うこと |
|---|---|---|
| 適合 | 提案が憲章に適合し、既存のパターンを使用している。 | Tenant Scale が PREP で適合を確認し、チームは作業を進めます。 |
| 論点を絞ったレビュー | 提案はおそらく問題ないが、一部に議論や明確化が必要。 | フィードバックは PREP 内で扱います。チームは提案を更新し、懸念が解決したら先へ進みます。 |
| アーキテクチャレビュー | 提案が新しいパターンを導入する、不変条件に関わる、またはモデルとの間に大きな緊張関係を生む。 | PREP を通じてアーキテクチャレビューへ引き継ぎ、最終決定は同じスレッドに記録します。 |

これにより、よくあるケースを軽量に保ちながら、判断が難しい作業についても明確な経路をチームに提供できます。

**4. 必ずアーキテクチャレビューが必要なもの。**

いくつかのカテゴリは、単なる実装上の選択ではなく、モデル自体の変更提案なので、自分たちの判断だけで進めてはいけません。

次のものは、必ずアーキテクチャレビューに回します:

- Organization、グループ、プロジェクトの階層を変更する
- Org メンバーシップを通じてグループ、プロジェクト、リソースへのアクセスを付与する（I5 によって認められた経路である、Org Admin の常時の CRUD 権限を通じた付与とは異なります）
- Issue、エピック、マージリクエスト、パイプライン、リポジトリ、または同様の作業リソースを Org ノードに直接関連付ける
- 継承モデルを迂回する
- デフォルトで Org 間の可視性を導入する
- Org レベルの請求モデルが出荷される前に、それが存在すると仮定する
- グループレベルに置くべきものに Org レベルのスコープを提案する
- Org Admin より上位の権限をプロダクト内に独自に設ける

これらは、この憲章によって防ごうとしている、コストの高い誤りです。

### 自動化に関する注記 {#a-note-on-automation}

時間の経過とともに、このワークフローの一部は自動化すべきです。分かりやすい例として、機能が作業リソースを Org ノードに直接関連付けていないか、サポートされていない請求の動作を前提としていないかのチェックが挙げられます。ただし、プロセスをまだ存在しないツールに依存させてはいけません。ワークフローは、現在 PREP を使って機能し、時間とともに自動化を進められるべきです。

### 意思決定記録 {#decision-record}

PREP が記録の正本です。Issue の最終状態を見れば、提案が次のどれであったかを容易に判断できるようにしてください:

- 適合していた
- 論点を絞ったレビューを経て承認された
- アーキテクチャレビューにエスカレーションされた
- 理由を添えて却下された

提案によって再利用できる Org パターンが確立された場合、Tenant Scale は、そのパターンを憲章または補足ガイダンスに追加してください。チームが同じ曖昧な領域に繰り返し直面するなら、毎回同じ議論をさせるのではなく、ドキュメントを改善すべきです。

### 実用的な目安 {#practical-rule-of-thumb}

- 作業が明らかにモデルに適合していれば、構築を進めます。
- チームが判断に迷ったら、PREP を開始します。
- 提案によってモデルが変わるなら、アーキテクチャレビューに送ります。

これがワークフローのすべてです。

## 5. 意思決定権 {#5-decision-rights}

- 憲章の変更（不変条件以外のセクション）: Tenant Scale PM と engineering lead。
- 不変条件の変更: エンジニアリングのリーダー層、プロダクトのリーダー層、Tenant Scale PM。アーキテクチャレビューを通じて行います。
- PREP のトリアージ: Tenant Scale PM と engineering lead。受付から 3 営業日以内。
- アーキテクチャレビューの決定: アーキテクチャレビューの参加者。理由とともに PREP に記録します。
- 憲章または補足ガイダンスへのパターンの追加: Tenant Scale engineering lead。ユーザー向けの影響について PM の承認を得ます。
- Org とグループのどちらに置くかの判断: セルフチェックと憲章で解決しない場合は Tenant Scale PM。
- ロードマップの優先順位付け: Tenant Scale PM。連携先チームの需要とプラットフォームのキャパシティを踏まえます。
- 権限戦略（Org レベルのロール、割り当てロジック、常時の CRUD 権限の改善）: Tenant Scale PM と連携する AuthZ PM。憲章の不変条件（I5、I6、I7）が境界を定め、AuthZ がその内部のモデルを所有します。

## 6. この憲章の v1 で意図的にスコープ外とするもの {#6-deliberately-out-of-scope-for-v1-of-this-charter}

後の改訂に延期した項目:

- 隔離のロードマップとアーキテクチャ上の扱い。
- 複数の Organization にまたがる機能（Org 間のナビゲーション、Org 間のレポート）。ロードマップにはなく、ここでも扱いません。
- Org 間の移行、統合、分割のフロー。将来必要になることは認識していますが、ここでは定義しません。
- Teams の具体的なデータモデル。Teams の設計文書で扱い、参照するにとどめて重複記載しません。
- Org レベルの請求: クレジットのプーリング、管理エリアを通じたエンタイトルメントのレビューと調整、請求の関連付け先を TLG から Organization へ移すこと。これは Billing チームと進めている作業であり、初回ローンチには含めません。この作業が完了するまでは、請求は TLG に関連付けたままとし、最終的な設計では、Org レベルのエンタイトルメントと TLG レベルの請求が共存する移行状態を考慮しなければなりません。
- グループとプロジェクトのロールモデルの変更。ローンチ時にはスコープ外です。Org<>Product のロール UI で衝突が明らかになった場合は、PREP に回します。

## 7. このドキュメントの使い方 {#7-how-to-use-this-document}

Tenant Scale のチームメンバー向け: これは、アーキテクチャに関するあらゆる対話の軸です。ある意思決定が根幹に関わると感じられ、憲章で扱っていなければ、その場限りのチャンネルで決めるのではなく、追記を提案してください。

連携先チーム向け: Org に関する作業を提案する前に、セクション 1 から 4 を読んでください。セクション 4 の拡張モデルが、ほとんどの要求にとって適切な入口です。Organization のハンドブック設計文書および関連する ADR と併せて使用してください。

リーダー層とステークホルダー向け: アーキテクチャ上の約束に異議を唱えたり、それを拡張したりする場所はセクション 3 です。ドキュメントの残りの部分は、そこから導かれます。

質問、提案、意見の相違は `#g_organizations` チャンネルに寄せてください。憲章に対する異論は貴重な意見です。憲章を迂回することはそうではありません。
