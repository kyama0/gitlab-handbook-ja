## 概要 {#summary}

意思決定ログは、ワークアイテムに関する決定の記録です。各決定の理由をワークアイテムのそばに保持し、履歴がチャットやコメントスレッドに埋もれないようにします。人とエージェントの両方が読み書きします。

複雑なワークアイテムで多くの調整が必要なとき、保留中の質問は埋もれがちです。また、解決済みの決定をすべて説明に追加すると、説明が長くなりすぎます。後から参加した人は、状況の把握に長い時間を費やします。エージェントが加わるとコラボレーションはさらに速く進むため、人と他のエージェントは、人とエージェントの会話で行われた決定を確認する必要があります。

今回のイテレーションでは、意思決定ログは長期間存続するアーティファクトではありません。その存続期間はワークアイテムに結び付いています。

エピック：[WS-5：意思決定ログ](https://gitlab.com/groups/gitlab-org/-/work_items/21552)

ユーザードキュメント：[意思決定ログ](https://docs.gitlab.com/user/work_items/workplan/#decision-log)

## 対象範囲 {#scope}

- Issue とタスク、およびそれらに基づくカスタムのワークアイテムタイプで利用できます。
- ワークアイテムに意思決定ログを設けるために、Workplan や AI 計画は必要ありません。
- 決定の表示と記録は、Planner、Reporter、Security Manager、Developer、Maintainer、Owner の各ロールで利用できます。より厳格な権限モデルについては、引き続き議論中です。
- 意思決定ログは、ワークアイテムのヘッダーからサイドパネルで開きます。ヘッダーのボタンには、解決済みでアーカイブされていない決定の件数を表示します。今回のイテレーションでは、未解決の決定は保存しますが、パネルには表示しません（[Issue 631883](https://gitlab.com/gitlab-org/gitlab/-/work_items/631883)）。

## データモデル {#data-model}

決定は、専用のテーブル `work_item_decisions` と `work_item_decision_options` に保存し、ワークアイテムと結合します。バックエンドの作業は、[データモデルとバックエンドのエピック](https://gitlab.com/groups/gitlab-org/-/work_items/22374)で追跡しています。

既存のモデルでは、タイムスタンプから決定の状態を判定します。

- `active`：解決とアーカイブのタイムスタンプがない、未解決の決定です。
- `resolved`：解決のタイムスタンプがあり、アーカイブのタイムスタンプがない決定です。
- `archived`：アーカイブのタイムスタンプがある決定です。

このライフサイクルでは、選択肢を持つ未解決の質問を作成し、後から解決できます。また、結果を直接記録するために、初めから解決済みの決定を作成することもできます。

API とモデルでは、決定が答える質問に `question` を使用します。移行中は、作成と更新のミューテーションが、従来の `title` 引数とともにこの引数を受け付けます（[マージリクエスト 259900](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/259900)）。データベースのカラム名の変更は、別のフォローアップとして行います。

## 操作 {#interactions}

[フロントエンドのエピック](https://gitlab.com/groups/gitlab-org/-/work_items/22375)で追跡している最初のイテレーションは、次のとおりです。

- 決定を手動で記録します。必須の項目は、決定、決定者、背景情報です。任意の項目は、理由と出典へのリンクです。
- 各決定をカードとして表示します。決定、その決定が答える未解決の質問、決定者と決定時期、決定の出典、背景情報と理由を含めます。
- 決定を、その決定に至ったスレッドとコメントにリンクします。
- 決定のテキストと決定者を編集したり、決定を削除またはアーカイブしたりします。アーカイブされた決定は、表示切り替えで表示できます。
- ワークアイテムの UI で Duo の質問を解決すると、対応する決定も解決します。決定を作成または選択することで、任意のスレッドを解決する汎用的なアクションは、引き続き [Issue 603073](https://gitlab.com/gitlab-org/gitlab/-/work_items/603073)で追跡しています。
- 決定用のクイックアクションと、決定を使って解決するオプションが [Issue 634656](https://gitlab.com/gitlab-org/gitlab/-/work_items/634656)で提案されています。この提案は引き続き議論中であり、まだ決定していません。この Issue では現在、1 つのスレッドから複数の決定が生まれる可能性があるため、スレッドから決定を作成しても、そのスレッドを解決する必要はないという方向で検討しています。
- 決定を記録または解決すると、そのカードに直接リンクするシステムノートをアクティビティフィードに作成します。ノートは、意思決定ログの可視性ルールに従います（[マージリクエスト 259191](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/259191)）。
- アーカイブされた決定へのリンクを開くと、アーカイブ済みの決定を表示する切り替えをオンにし、そのカードが見える位置までスクロールします。存在しない決定へのリンクを開くと、閉じられる警告を表示し、他の決定は引き続き表示します（[マージリクエスト 263112](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/263112)）。

後のイテレーションに先送りしたものは、次のとおりです。

- 否定的な決定も含め、既存の active、resolved、archived の状態を超える承認のライフサイクル。
- 決定の担当者と、それにより作成する To-Do アイテム。
- 子ワークアイテムの決定を最上位のエピックまで伝播させること。
- 決定のカテゴリ、順序、決定を別の決定で置き換えること。

## エージェント {#agents}

- Workplan フローのサービスアカウントが有効な明確化のための質問を投稿すると、バックエンドは未解決の決定を作成します。質問、選択肢、ディスカッション、ワークフローへの参照を保存します。
- ユーザーがワークアイテムの UI で質問スレッドを解決すると、フロントエンドは対応する決定を解決します。このためには、ワークアイテムで意思決定ログが利用可能である必要があります。エラーへの対応や以前の質問については、[人の関与](human-in-the-loop.md#relationship-to-the-decision-log)を参照してください。

## 可観測性 {#observability}

内部イベントで、解決済みとしての決定の記録、未解決の決定の解決、意思決定ログのパネルのオープンを追跡します。解決イベントには、どのように決定したかを含めます。未解決の質問を作成しただけでは、解決済みの決定として集計しません（[マージリクエスト 261013](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/261013)）。

## 未解決の質問 {#open-questions}

- パネルで未解決の決定とその選択肢をどのように表示するか（[Issue 631615](https://gitlab.com/gitlab-org/gitlab/-/work_items/631615)）。
- 解決済みの決定を再オープンする際に、その決定を直接変更するか、別の決定で置き換えるか（[Issue 632762](https://gitlab.com/gitlab-org/gitlab/-/work_items/632762)）。
- アーカイブされたプロジェクトでの動作も含め、ワークアイテムの更新権限と内部ノートへのアクセス権の両方を要求すること（[Issue 632270](https://gitlab.com/gitlab-org/gitlab/-/work_items/632270)）。
