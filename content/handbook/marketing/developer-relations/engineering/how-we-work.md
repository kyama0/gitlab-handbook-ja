## このページの目的 {#why-this-exists}

私たちは、[コントリビューターのフライホイールと成長の成果](/handbook/marketing/developer-relations/engineering/#strategy)を軸に作業を整理します。
このページでは、バックログ、計画、デリバリーのつながりを示し、私たちが何に、なぜ取り組んでいるのか、誰が担当しているのかを誰でも把握できるようにします。
成果、報告のカテゴリ、成果の解釈に役立つ指標については、[報告と測定](/handbook/marketing/developer-relations/engineering/reporting/)を参照してください。

## 作業の整理 {#structure-work}

### プロジェクトと Issue {#projects-and-issues}

私たちの[チームプロジェクト](https://gitlab.com/gitlab-org/developer-relations/contributor-success/team-task)は、チームのタスクとバックログを確認する起点です。
作業の内容に応じて Issue の作成先を選びます。

- **GitLab 製品とコントリビューションの流れ：** オープンソースプロジェクトの GitLab を改善する公開 Issue は、原則として [gitlab-org/gitlab](https://gitlab.com/gitlab-org/gitlab)に作成してください。
  コントリビューターもチームメンバーも同じように取り組める状態にしてください。
- **チーム運営と調整：** チームの内部業務、オンボーディング、GitLab 製品プロジェクトと分けて扱うべきお客様との調整には [team-task](https://gitlab.com/gitlab-org/developer-relations/contributor-success/team-task)を使用してください。
- **コントリビュータープラットフォームの開発：** 範囲が明確で実行可能な小規模の技術タスクには、[contributors-gitlab-com](https://gitlab.com/gitlab-org/developer-relations/contributor-success/contributors-gitlab-com/-/issues)を使用してください。
  プラットフォームの大規模な取り組みや、計画、調整は `team-task` で追跡し、同じ実装タスクを重複して登録せず、実装先の Issue にリンクしてください。
  必要に応じてグループエピックを使用し、大規模な作業を整理してください。
- **コントリビュータープラットフォームのアラート：** [オブザーバビリティアラートのトリアージ](/handbook/marketing/developer-relations/engineering/observability-alert-triage/)の手順に従ってください。
  アラートは `contributors-gitlab-com` に作成されます。機密情報は、アラートの機密 Issue 内に留めてください。

### エピックとデリバリーの分類 {#epics-and-delivery-groups}

関連するデリバリー作業はエピックでまとめ、具体的な成果物は Issue に記載してください。
デリバリー作業は、該当する[フライホイールの段階またはアドボカシーのエピック](/handbook/marketing/developer-relations/engineering/#contributor-flywheel)の下にまとめ、必要に応じて子エピックを使用してください。

- [目標外の取り組み](https://gitlab.com/groups/gitlab-org/developer-relations/contributor-success/-/work_items/59)には、複数の領域にまたがる作業をまとめます。
- [運営とチームの効率化](https://gitlab.com/groups/gitlab-org/developer-relations/contributor-success/-/work_items/60)には、運営に関する作業をまとめます。
  どちらもファネルの段階には含まれません。

[顧客アカウントの成長](https://gitlab.com/groups/gitlab-org/developer-relations/contributor-success/-/work_items/35)と[製品の成長](https://gitlab.com/groups/gitlab-org/developer-relations/contributor-success/-/work_items/36)の記録は成果を定義するもので、デリバリー作業をまとめる枠ではありません。

[工数が大きい Issue](#effort)は、1 つの大きなデリバリータスクにまとめず、エピックと、それぞれが単独で役に立つ小さな Issue に分けることを検討してください。
工数が大きいエピックについては、子エピックや小規模な Issue、段階ごとのデリバリーマイルストーンを検討してください。
これらは進捗を確認しやすくするための方法です。見積もりだけで実施の要否が決まるわけではありません。

### ボードと作業の可視性 {#boards-and-visibility}

[コントリビューターのフライホイールボード](https://flywheel-97bd65.gitlab.io/)では、デリバリー作業を段階とエピックごとにまとめます。
現在は GitLab のエピックボードや Issue ボードを使用していません。今後は、優先度や担当者ごとにまとめるなどの使い方を検討します。

フライホイールボードは、全プロジェクトのバックログを網羅していません。
[集計ルール](https://gitlab.com/gitlab-org/developer-relations/contributor-success/flywheel/-/blob/main/README.md#what-counts)で対象となるのは、`contributor-success` のオープンなエピックと `team-task` のオープンな Issue のみです。
ほかのプロジェクトの Issue は、対象のエピックに紐づいていても表示されません。
閲覧者に何が表示されるかは、サインインの状況や権限にも左右されます。
ボード上の仮の項目ではなく成果を報告する方法は、[報告と測定](/handbook/marketing/developer-relations/engineering/reporting/#report-progress)を参照してください。

`team-task` 外の作業を報告する際は、ボードに表示されていない作業も、該当する Issue にリンクしてください。
大規模なプラットフォームの取り組みは `team-task` に調整用の Issue を作成すればボードに表示できますが、`contributors-gitlab-com` にある実装用の Issue は引き続き対象外です。
各担当プロジェクトの Issue をすべてプロジェクト横断のバックログに載せるかどうかは、まだ決まっていません。ボードの対象範囲によって、上記の Issue 作成先のルールが変わることはありません。

## 評価と優先順位付け {#assess-and-prioritise}

デリバリーを確約する前に、チームの戦略に対して見込まれる影響と工数を比較して妥当性を確認してください。

### 影響と工数 {#impact-and-effort}

新しい Issue では、Issue テンプレートを使って当初の判断の根拠を記載してください。

- **[影響](#impact)** では、誰にメリットがあり、何が変わるかを、根拠のある削減効果も含めて記載してください。
- **[工数](#effort)** では、明示した計画期間におけるデリバリーと継続作業の合計を、前提と不確実性とともに記載してください。
- **コントリビューターの参加**について、コミュニティのコントリビューターが提供できる成果物とチームが提供する支援、または現時点でコミュニティに任せるのが難しい理由を記載してください。
- **[優先度](#priority-labels)。**

影響と工数は、低・中・高の 3 段階で評価してください。
これらは今後調整していくための当初の目安です。GitLab 全体で使用する `Impact::` や `Effort::` ラベルの定義とは異なります。
新しいエピックの説明にも同じ内容を記載してください。

[週次トリアージレポート](#weekly-triage-report)の対象項目には、作成時や内容を具体化する際に、必要なスコープ付きラベルを付けてください。
ラベルは根拠を補足するものです。根拠も記載してください。
AI が生成した評価は、人が判断するための参考資料として扱ってください。人によるレビューは別途必要です。
既存のラベルだけでは、人が判断の根拠を確認したかどうかは分かりません。

既存の Issue やエピックを再評価する際は、作業の順序やスコープに影響する場合など、評価が実質的に変わるときに、その理由をコメントで説明してください。
作業のスコープが変わる場合は、説明欄に残しておくべき背景情報を更新してください。
機械的なラベル修正や、評価に影響しないラベルの一括付与では、コメントを控えてください。

作業内容を具体化する際は、数値による採点式を使わず、概算を比較して判断してください。
原則として[優先度マトリクス](#priority-labels)に従い、例外は記録してください。
より小さな成果物で前提を検証したりブロッカーを解消したりできる場合は、作業を分割してください。
根拠となる情報が変わったときにほかの人が判断を見直せるよう、優先度を決めた理由を記録してください。
影響や工数が不明な場合に、低と評価しないでください。
評価とその確度は別々に記録し、不確実性を解消するために必要な最小限の調査を特定してください。

#### 影響 {#impact}

各項目に見込まれる効果が必要です。誰にメリットがあるのか、どのような問題やブロッカーがあるのか、成長の成果やその解釈に役立つ指標にどう貢献するのかを記載してください。
コントリビューターからのフィードバックや実際に確認されたボトルネックなどの根拠にリンクし、見立ての確度と前提を明記してください。
観察された問題と、問題を解消した場合に見込まれる効果は区別してください。
時間やサポート工数の削減が見込まれる場合は、根拠、発生頻度、明示した計画期間とともに、影響の評価に含めてください。
削減分を工数から差し引いたり、同じ効果を別々の名目で二重に計上したりしないでください。
[成果報告のガイダンス](/handbook/marketing/developer-relations/engineering/reporting/#report-progress)に従い、成果が得られたとどう判断できるかを記載してください。根拠のない基準値や目標値は設定しないでください。

| 評価 | 判断基準 | 判断を説明する根拠 |
| --- | --- | --- |
| 低 | 利便性が少し向上する、または一部が改善する。変更がなくても対象のタスクは実行でき、成果にも到達できます。繰り返し発生する大きな障害を解消する変更ではありません。 | どのような不便があり、誰が直面するかを記載してください。現状のままでも影響が限られる理由を説明してください。 |
| 中 | 対象が明確なグループにとって、繰り返し発生する実質的なブロッカーを解消するか、共通のワークフローを改善し、たびたび発生する遅延や回避策の必要性を減らします。共用されているというだけでは不十分です。利便性の向上以上の効果が必要ですが、高に該当するほど成果そのものが大きく変わるわけではありません。 | 繰り返し発生する問題の例、影響を受けるワークフロー、見込まれる変化へのリンクを示してください。一部に限られた改善にとどまらない理由を説明してください。 |
| 高 | 価値のあるコントリビューションやお客様にとって重要な成果を妨げる重大な障壁を取り除く、共通の大きなボトルネックを解消する、または成長における重要な成果を後押しします。ワークフローが改善するだけでは不十分です。見込まれる変化が成果そのものに大きく影響することが必要です。 | どの重要な成果が誰にとって妨げられているか、または大きく制約されているかと、その変更による解消方法を示してください。再利用可能なケイパビリティでは、実際の利用や導入の必要性を裏付ける根拠にリンクしてください。再利用の仮説だけでは不十分です。中では影響を過小評価することになる理由を説明してください。 |

影響の及ぶ範囲、効果の大きさ、発生頻度、再利用の可能性を併せて考慮してください。人数だけで影響は決まらず、お客様に関する作業も一律に高と評価するわけではありません。
隣接する区分と照らし合わせ、選んだ区分を根拠が裏付ける理由を説明してください。
対象者が少なくても、得られる効果が大きければ、影響は高になり得ます。広範囲に及んでも、効果が小さければ、一律に高とは評価しません。
緊急度と実装規模は、影響の評価に含めないでください。
戦略的、再利用可能、成長に関係すると説明するだけでは、影響を高と評価する根拠にはなりません。
価値ある実験を行うのに確実性は必要ありません。影響が不明な場合は、その不確実性を明記し、何を学ぶかを定めた小規模な実験を提案してください。

以下は評価の目安をそろえるための仮の例です。チームが現在取り組んでいる作業の根拠にはなりません。

- **低**に該当する例は、コントリビューターがすでに問題なく利用しているオンボーディング手順を改善し、ときどき寄せられる確認の質問をなくすことです。
- **中**に該当する例は、同じ手順を改善して、特定のコントリビューターグループで繰り返し発生するセットアップの失敗を解消し、サポートを受けながら回避策を取る必要をなくすことです。
- **高**に該当する例は、コントリビューターが価値のあるコントリビューションに進めず、現実的な回避策もないことを根拠が示す場合に、同じ手順を修正することです。

作業のカテゴリだけで影響は決まりません。各項目の効果と根拠を評価してください。

#### 工数 {#effort}

関係者全員の実作業にかかる工数を見積もってください。明示した計画期間におけるデリバリーと継続的な保守、サポート、運用が対象です。
デリバリーにかかる工数と、繰り返し発生する工数を、頻度や前提とともに分けて記録し、その合計で工数の区分を決めてください。
代替案は同じ期間で比較してください。カレンダー上の経過時間や、期間を明示しない長期の負担は比較に使わないでください。
1 人日は、1 人が通常の勤務日 1 日で完了できる作業量を指します。時間数は固定しません。
関係者全員の工数を合計してください。並行して作業すると経過時間を短縮できますが、工数の合計は減りません。
調査、設計、実装、テスト、レビュー、ドキュメント作成、調整、展開に加え、成果物を有用な状態に保つための継続作業も含めてください。
依存する作業の完了を待つ時間は実作業の工数に含めません。その作業との調整は含めます。
役に立つ最小の成果物、依存関係、不確実性を記載してください。
継続的な負担が不明な場合など、不確実性が大きく見積もれないときは、調査の範囲を定めてください。工数を安易に低と評価しないでください。

| 項目の種類 | 低 | 中 | 高 |
| --- | --- | --- | --- |
| Issue | 明示した期間のデリバリーと継続作業の合計が数時間。確認とレビューも含みます。 | 明示した期間のデリバリーと継続作業の合計が約 1 人日。短時間の作業や数日にわたる作業はこの区分に入りません。 | 明示した期間のデリバリーと継続作業の合計が数人日。実装に数時間しかかからなくても該当します。 |
| エピック | 明示した期間の対象範囲全体で、デリバリーと継続作業の合計が数人日。 | 明示した期間のデリバリーと継続作業の合計が数人週。複数の成果物を調整して届ける作業で、数日では終わりません。 | 明示した期間のデリバリーと継続作業の合計が数人週を超えます。範囲をレビューしやすくするため、段階に分けるか子エピックを使うことを検討してください。 |

これらの区分はおおまかな目安です。厳密な境界やデリバリーの確約を示すものではありません。
数時間と約 1 人日の間、または数日と数週間の間にある工数は、個別に判断してください。以下の例を使うと、チームで境界の解釈をそろえられます。
境界に近い場合は、見込まれる工数の幅を示し、デリバリーと継続作業を合わせた工数を最もよく表す区分を選んでください。
どのような条件なら隣の区分になるのかを説明してください。必要なテスト、調整、繰り返し発生する作業を除いて低い区分を選ばないでください。
複雑さと依存関係は見積もりの判断材料です。それだけで区分が決まるわけではありません。
エピックの見積もりは、明示した期間の対象範囲全体を扱います。工数が低のエピックと工数が低の Issue を直接比較したり、集計時に両方を数えたりしないでください。

実装が数時間で済む場合でも、繰り返し発生する作業の負担が大きければ、全体の工数の区分が上がることがあります。
見込まれる削減効果は影響として評価してください。削減分を差し引いて工数を少なく見積もったり、工数をマイナスとしたりしないでください。
自動化の場合、構築、保守、運用の作業は工数に含め、省ける手作業は影響として評価してください。

コミュニティが参加すると、誰が作業を担うかが変わります。工数の合計が変わるとは限りません。
コミュニティのコントリビューターが提供できる成果物と、チームが提供すべき支援を特定してください。
適している場合は、範囲を限定した成果物と、チームが担うスコープの設定、オンボーディング、メンタリング、調整、レビューの作業を定義してください。
引き継ぎも含め、継続的な保守とサポートを誰が担当するか合意してください。
全員のデリバリーと継続作業を見積もりに含め、チームが割ける工数を計画するためにチームの分担を明記してください。
コントリビューターが実際に関心を示しているか、時間を割けるか、不確実な点は何か、参加がなかった場合にどう対応するかを記録してください。
コミュニティが参加する可能性だけで、担当者の工数を確保できたと見なさないでください。
たとえば、数日かかる Issue をコミュニティが実装しても、全体の工数は高のままです。チームにはレビューとサポートのための工数が引き続き必要です。
コントリビューターが作業しやすくなること、責任を共有できること、再利用可能なケイパビリティが得られることなどの効果は、影響として別途評価してください。根拠に基づいて判断し、コミュニティが参加するだけで評価を引き上げないでください。

上と同じオンボーディング手順の変更例で、明示した計画期間における継続作業が無視できる程度だと仮定します。

- 修正箇所が分かっている段落を編集し、記載された手順の検証から変更のレビューまでを合計数時間で行う場合、工数は **低** です。
- 記録された不具合を再現し、手順の改訂、修正の検証、レビューまでを合計約 1 人日で行う場合、工数は **中** です。
- サポート対象の複数の構成を調査し、それぞれで改訂した手順を検証するのに複数人日かかる場合、工数は **高** です。

一方、仮に実装が数時間で済む変更でも、明示した期間内に繰り返し発生するサポートに数人日かかるなら、工数は高です。
その評価を説明するために、サポートが発生する見込みの頻度と、1 回あたりの工数を記録してください。
繰り返し発生する手動サポートをなくす自動化は、大きな影響をもたらし得ます。その場合も、工数にはデリバリーと継続的な保守を含め、削減分は差し引きません。

これらの変更の影響は、解消する問題に応じて評価してください。工数の区分で影響は決まりません。

`contributors-gitlab-com` では、工数が低または中に収まるアクションを目指してください。
工数が高の Issue は、分割や、[作業全体を `team-task` で追跡すること](#projects-and-issues)を検討し、[必要に応じてエピックを使用](#epics-and-delivery-groups)してください。

### 優先度ラベル {#priority-labels}

通常は、以下の表を使って、影響と工数から優先度を決めてください。
チームが割ける工数に応じて作業順序を決めた場合や、ほかの理由で原則から外れる場合は、その判断を説明してください。説明なしに影響や工数の評価を変更しないでください。

| 影響 | 工数：低 | 工数：中 | 工数：高 |
| --- | --- | --- | --- |
| 高 | `priority::1` | `priority::1` | `priority::2` |
| 中 | `priority::1` | `priority::2` | `priority::3` |
| 低 | `priority::2` | `priority::3` | `priority::4` |

`priority::1` が最も高く、`priority::4` が最も低い優先度です。
優先度は相対的な重要性を示します。デリバリーの確約、期日、担当の割り当ては別に扱います。
緊急度、依存関係、戦略上のコミットメントに応じて、表の優先度を変更できます。
表の優先度を変更する理由は、当初の判断の根拠に含めてください。既存の作業を再評価する場合は、コメントで説明してください。
優先度を変更する根拠となった期限、依存関係、またはコミットメントと、遅延した場合の影響を明記してください。

## 作業のデリバリー {#deliver-work}

規模の大きい項目には、戦略と報告に責任を持つ [DRI](/handbook/marketing/developer-relations/engineering/reporting/#who-decides-and-who-owns)がいます。DRI がすべての実装タスクを担当する必要はありません。

### ワークフローラベル {#workflow-labels}

現在、私たちは作業の追跡にワークフローラベルを使用していません。
今後は作業項目のステータスを採用する可能性がありますが、従来のワークフローラベルの使用は避けます。

### Issue の選び方 {#how-to-pick-issues}

優先度に基づいて Issue を選んでください。
当四半期は `priority::1` と `priority::2` に注力してください。
大規模なプロジェクトの合間に、優先度の低いタスクに取り組むこともできます。
タスクを選ぶときは、GitLab の効率性とイテレーションの原則に従い、Manager of One として行動してください。

作業の進捗に合わせて、Issue のステータス、実装計画、ブロッカーを最新の状態に保ってください。
[チームのスタンドアップ](#stand-up)を活用し、作業を進めたりブロッカーを解消したりするために協力してください。

## チームの定例活動 {#team-cadence}

### 週次トリアージレポート {#weekly-triage-report}

トリアージの自動処理は月曜日の 02:00 UTC に実行されるよう設定されており、[team-task](https://gitlab.com/gitlab-org/developer-relations/contributor-success/team-task/-/issues)に機密 Issue として **Contributor Success 週次トリアージレポート**を作成します。
指摘事項がなければレポートは作成されません。

レポートは、Contributor Success グループ直下のオープンなエピックと、`team-task` のオープンな Issue を対象に、次の点を確認します。

- `Impact::*`、`Effort::*`、`priority::*` のいずれかのラベルが欠けている。
- 担当者が割り当てられている作業の最終更新から 14 日を超えている。
- [デリバリーの分類](#epics-and-delivery-groups)につながる上位エピックがないか、階層が間違っている。

ラベルのチェックでは、必要なラベルがそろっているかどうかだけを確認します。
サブグループのエピックや他のプロジェクトの Issue は、対象のエピックに紐づいている場合も対象外です。
[トリアージレポートのヘルパー](https://gitlab.com/gitlab-org/quality/triage-ops/-/blob/master/lib/contributor_success_triage_report_helper.rb)はチェック項目と例外を定義し、[レポートポリシー](https://gitlab.com/gitlab-org/quality/triage-ops/-/blob/master/policies/groups/gitlab-org/contributor-success/weekly-triage-report.yml)は Issue の作成方法を定義します。

レポートの自分のセクションにある項目を確認し、対象の Issue やエピックでラベルやエピックの階層を修正してください。
更新が滞っている担当作業は、具体的な進捗を共有してください。担当を外れている場合は、自分の割り当てを解除してください。
指摘事項に対応したら、それぞれのチェックボックスにチェックを入れてください。チェックを入れても、対象の項目は更新されません。

レポートの自分のセクションで割り当てられるのは、トリアージ後の対応です。実装の担当を割り当てるものではありません。
自動処理によって、対象項目の担当者やその他のデータが変わることはありません。

### 人によるバックログのレビュー {#human-backlog-review}

**提案**として、人によるレビューが明示的に記録されていないか、前回のレビューから 90 日以上経過した Issue を対象に、`needs retriage` のキュー（ラベル）を検討します。
重要な変更があった場合は、より早く再確認します。
レビューからどれだけ時間が経ったかは、人によるレビューの記録日（ラベルを外した日）で判断します。`updated_at` やボットのアクティビティは基準にしません。
これはプロセスの提案段階であり、キューや自動処理はまだ実装されていません。
