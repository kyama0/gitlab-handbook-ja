## 概要 {#summary}

Data Team は、誰も読み取らない dbt モデルを削除します。利用状況は `prod.workspace_data.wk_dbt_model_inventory` で測定し、90 日、180 日、365 日間の利用者による読み取り回数、ビルドとテストのコスト、下流のモデルを集計します。

見つからなくなったモデルを探している場合は、[エピック gitlab-data&1850](https://gitlab.com/groups/gitlab-data/-/epics/1850)の削除済みモデルの一覧を確認してください。削除したすべてのモデル、それが構築した Snowflake のリレーション、削除したマージリクエストを記載しています。

## 階層 {#tiers}

すべてのモデルは、必ず 1 つの階層に属します。階層によって、削除前にどの程度の予告期間を設けるかを決めます。

| 階層 | ルール | 承認 |
|---|---|---|
| 1 削除 | 365 日間、利用者による読み取りがなく、下流のモデルがなく、少なくとも 30 日間稼働している | オプトアウト方式です。Data Team が一覧を確認し、その後 1 週間の異議申し立て期間を設けます。反応がなければ同意とみなします。 |
| 2 休眠 | 90 日間、利用者による読み取りがないものの、365 日以内にはあり、下流のモデルがない | 過去の読み取り利用者にダイレクトメッセージを送り、2 週間の返信期間を設けます。季節的な利用を Finance と事業部門に確認します。主な読み取り利用者の確認後にのみ削除します。 |
| 3 最小利用 | 下流のモデルがなく、階層 1 または 2 に属さず、90 日間の利用者による読み取りが 5 回未満、または読み取り利用者が 2 人未満の PROD テーブル | 読み取り利用者にダイレクトメッセージを送り、必要なら 1 回リマインダーを送ります。主な読み取り利用者の確認後にのみ削除します。 |
| 4 基盤処理 | 365 日間、利用者による読み取りがなく、他のモデルにデータを供給するものの、どの深さの下流にも読み取られるモデルがない | 下流のモデルとともに削除します。それらすべてが承認された場合にのみ承認します。 |

階層は順番に確認するため、前の階層に当てはまるモデルは、そちらに分類します。

階層 2 と 3 のモデルを、反応がないことを理由に削除することはありません。リマインダーの後も主な読み取り利用者の確認が得られなければ、モデルを稼働したままにし、所有者が次回のレビューに向けてレビューシートに記録します。モデルにクエリした全員が確認できるよう、削除するマージリクエストではすべての読み取り利用者をタグ付けしますが、確認が必要なのは主な読み取り利用者だけです。

これらの階層に当てはまらないモデルは、稼働中です。

## モデルの削除 {#removing-models}

これらの手順は、計画されたバッチ（フォルダーごとにまとめ、それぞれ専用の Issue を持つ約 30 〜 40 個のモデル）でも、少数のモデルを個別に削除する場合でも、すべての dbt モデルの削除に適用します。モデルを削除する人が所有者です。削除用の Issue はバッチの Issue を使い、なければ新しく作成します。新しいモデルで置き換えたものなど、どの階層にも属さないモデルは、手順 1 と読み取り利用者への通知を省略します。その他の手順とロールバックは引き続き適用します。`wk_dbt_model_inventory`（`downstream_model_count`）で下流のモデルを自分で確認し、先に削除するか参照先を変更します。階層を「None」として、置き換えるモデルなどの理由を記録します。

1. **一覧を取得します。** 階層のクエリを再実行し、各モデルが承認ルールを満たしていることを確認します。階層 2 と 3 の判断は、削除用の Issue からリンクしたレビューシートに記録します。
2. **モデル一覧を保存します。** 何かを削除する前に、以下のクエリを実行します。モデルを dbt から削除すると、インベントリからも消えます。
3. **コードを削除します。** 階層に属するモデルでは、下流で何も読み取られない場合にのみインベントリが候補として挙げるため、下流の依存関係はすでに考慮されています。analytics リポジトリで、各モデルの SQL ファイルと `schema.yml` および `sources.yml` のエントリを削除し、プロジェクトを検索して参照が残っていないことを確認します。参照が残っていれば、CI は失敗します。削除するモデルに対して 1 つのマージリクエストを作成し、説明にすべてのモデルと階層を記載して、階層 2 と 3 の各モデルの読み取り利用者をタグ付けします。
4. **モデルをエピックの一覧に追加します。** [エピック gitlab-data&1850](https://gitlab.com/groups/gitlab-data/-/epics/1850)の削除済みモデルの一覧に、モデルごとに 1 つのエントリを追加し、Snowflake のリレーション、階層、削除するマージリクエストを記載します。
5. **14 日間待ちます。** [Snowflake でのテーブルの削除](#dropping-tables-in-snowflake)を参照してください。
6. **Snowflake で削除します。** 最短の削除可能日を過ぎた後、トリアージを担当する Data Engineer が、マージリクエストのマージ時に所有者が削除用の Issue で依頼したリレーションを削除します。

```sql
select
  model_name,
  lower(full_table_name) as snowflake_relation,
  materialization,
  model_path
from prod.workspace_data.wk_dbt_model_inventory
where model_name in ('<model_1>', '<model_2>')
order by model_name
```

### 階層 2 と 3 の読み取り利用者への通知 {#notifying-tier-2-and-3-readers}

所有者がメッセージを送信します。階層 2 では `consumer_readers_365d` に記載された読み取り利用者に、階層 3 ではそのモデルの読み取り利用者に送信します。階層 1 と 4 は #data Slack チャンネルで告知し、個別のメッセージは不要です。

> dbt から `<model>` を削除することを検討しています。利用データによると、過去 `<365 or 90>` 日間に `<N>` 回クエリしており、直近は `<date>` でした。まだ必要かどうか、`<date>` までにこちらかレビューシートで返信してください。返信なしに削除することはありません。不要との返信をいただいた場合は削除しますが、後で何か分かれば git から復元できます。

期日までに返信がなければ、所有者は 1 回リマインダーを送ります。それでも確認が得られなければ、モデルは削除しません。

各判断（削除、維持、返信なし）、判断した人、日付をレビューシートに記録します。削除用の Issue ではシートの行にリンクし、内容は繰り返し記載しません。

## Snowflake でのテーブルの削除 {#dropping-tables-in-snowflake}

dbt からモデルを削除しても、Snowflake からは何も削除されません。ビューやテーブルはその場所に残り、更新が止まります。削除は元に戻せないため、独自の担当者を持つ別の手順とします。

1. 削除するマージリクエストがマージされたら、所有者は、削除用の Issue で、トリアージを担当する Data Engineer にリレーションの削除を依頼します。依頼には、マージ日と最短の削除可能日（マージ日から 14 日後）を記載します。
2. 14 日間は、更新が止まったリレーションが安全網になります。まだ読み取っている人には、エラーではなく古いデータが返ります。リレーションのクエリ履歴を確認し、想定外の読み取りがないか調べます。
3. 最短の削除可能日を過ぎ、所有者が想定外の読み取りがなかったことを確認したら、トリアージを担当する Data Engineer が `DROP` を実行します。
4. モデルを削除した後も、履歴として保持するテーブルがあります。その場合は削除せず、エピックの一覧に記載します。

増分モデルも、他のモデルと同様にフルリフレッシュで再構築します。削除前に、所有者は、モデルでフルリフレッシュが無効になっておらず、生のソースに履歴が残っており、フルリフレッシュで再現できることを確認します。この確認を満たさない場合は、削除用の Issue で提起し、個別に判断します。

## ロールバック {#rolling-back}

コードの削除は git での削除であるため、ロールバックはマージリクエストをリバートすることです。

- **テーブル削除前：** マージリクエストをリバートします。次の実行でビューとテーブルを再構築します。増分モデルは既存のテーブルから再開するため、データに欠落期間がないか確認し、あればバックフィルします。
- **テーブル削除後：** マージリクエストをリバートし、フルリフレッシュを実行します。ビューとテーブルが復元します。増分モデルは、前述のフルリフレッシュの確認を満たしていた場合に復元します。

リバートしたら、エピックの一覧のモデルのエントリを更新し、復元したことを示します。

## 別途 deprecated タグを付けない {#no-separate-deprecated-tag}

削除前にモデルへ deprecated タグは付けません。階層 1 のオプトアウト期間、階層 2 の通知、階層 3 の確認で、読み取り利用者にすでに予告しており、タグを付けるとモデルごとにマージリクエストが増えます。
