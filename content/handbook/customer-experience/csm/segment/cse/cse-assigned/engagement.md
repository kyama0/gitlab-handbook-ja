顧客とのやり取りと支援モデルの違い。

## 顧客エンゲージメント {#customer-engagement}

CSE は、業務上必要な場合、顧客と直接関わり、兆候を検証したり、製品データからは得られない背景情報を集めたり、リスクへの対応やイネーブルメントのアクションを進めたりします。その間、アカウントチームとも情報を共有します。CSE のヘルス評価は、アカウントチームがすでに把握している情報を補足するものです。

AE または RM が CSE を紹介した後は、顧客は CSE と直接やり取りします。担当 CSE は、アカウントのポストセールスの技術担当者であるため、顧客は CSE Assigned の範囲内で支援が必要になったときには、アカウントチームを経由せずにいつでも連絡できます。顧客との関係全般については、引き続き AE が主要な窓口となります。

**エンゲージメント**とは、顧客との、範囲とトピックを限定した一連の作業です。例えば、技術的な質問への回答、利用定着に関するトピックへの対応、技術的な問題の解決が含まれます（ただし、障害対応・修復はサポートチームが担当するため含まれません）。通常は 1 〜 3 回のやり取り（通話、メール、作業セッション）で完結し、継続的な関係ではありません。これは、必須の四半期ごとの顧客との接点とは異なります。接点はアカウントとの関係を保つためのものであり、エンゲージメントは個別の作業です。目安として、Assigned アカウントには**四半期あたり最大 3 回のエンゲージメント**を提供します。この目安は厳格な上限ではありません。プロアクティブであるということは、顧客が支援を必要としたときに支援するということです。RACI と比較表に記載した制限は、判断の目安であって、支援を制限する条件ではありません。ほぼ毎日のサポートなど、他のアカウントよりもはるかに多くの支援を必要とする場合は、その顧客には Success Tier の方が適している可能性を示しており、CSE は更新前にアカウントチームにその点を提起します。

CSE は、顧客が参加する常設の Slack チャンネルに参加しないでください。エンゲージメントは、範囲とトピックを限定するように設計されています。常設の顧客用 Slack チャンネルは、このモデルにそぐわない、際限なく常時対応する関係を生み、Success Tiers の支援との境界を曖昧にします。代わりに、メールや事前に予定した通話を使用してください。

> **顧客がエンゲージメントに対応できない場合：** ヘルス評価は、入手可能なデータ（利用状況の兆候、アカウント履歴、AE/SA から得られる背景情報）を使用して引き続き実施し、CSE は対応可能な状態を保ちます。

## CSE Assigned と Success Tiers の比較 {#cse-assigned-vs-success-tiers}

CSE Assigned と Success Tiers は、競合するものではなく、補完し合うものです。CSE Assigned は、顧客の契約に含まれる、リスクを重視した四半期ごとの支援モデルです。Success Tiers は、有料で手厚い支援を提供します。顧客が CSE Assigned の提供内容よりも踏み込んだ支援を求める場合、それは AE にとって Success Tiers の商談機会であり、CSE の担当範囲を拡大するものではありません。

| | Pooled (CSE) | CSE Assigned | Success Tiers (Essentials / Advanced / Signature) |
|---|---|---|---|
| **エンゲージメントモデル** | 依頼に応じた、ケース単位の対応 | プロアクティブ、四半期ごと | プロアクティブ、継続的 |
| **専任担当者** | - | ✔ | ✔ |
| **頻度** | オンデマンド | 四半期ごと | 月次以上 |
| **エンゲージメントの上限** | アカウントあたり半年ごとに最大 3 ケース | アカウントあたり四半期ごとに 3 回のエンゲージメント（目安） | 上限なし（標準の実施頻度に従う） |
| **ヘルスモニタリング** | - | ✔ | ✔ |
| **エスカレーション管理** | - | ✔ | ✔ |
| **サクセスプランニング** | - | - | ✔ |
| **EBR / QBR** | - | - | ✔ |
| **ワークショップ** | 公開日程のもののみ | 公開日程のもののみ | 個別に調整 |
| **顧客の費用負担** | 契約に含まれる | 契約に含まれる | 有料 |
